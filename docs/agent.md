# 项目、容器与节点

项目和容器的配置以面板为准（见 [panel.md](panel.md#项目数据)），节点按面板下发的配置运行容器，并保存容器的运行文件、数据和快照。节点由 `nagi agent` 启动（或作为 `nagi server` 的内嵌 agent），只支持 Linux（amd64 / arm64），以 systemd 服务运行。

## 节点的职责

- 按面板下发的配置部署、更新、删除分配给本节点的容器，调用 `docker compose` 执行
- **缓存自己那部分容器的配置**：面板不可达时照常运行、重启、快照、顶替；面板彻底丢失时，新面板从各节点的缓存把项目拼回来（见 [failover.md](failover.md#面板故障)）
- 内嵌 Caddy（含 layer4 模块）：本节点上容器的对外出口，占用节点的 80/443（见 [exposure.md](exposure.md)）
- 项目内网的跨节点部分：为不在本节点上的同项目容器、已连接项目的容器放代理（见下文"网络"）
- 容器的版本文件、快照与恢复（见本文和 [snapshot.md](snapshot.md)）；把副本同步给顶替节点或备份节点，作为顶替节点时参与租约投票（见 [failover.md](failover.md)）
- WireGuard 组网（见 [mesh.md](mesh.md)）
- 采集监控数据存在本地，在本地判断并发送告警（见 [monitoring.md](monitoring.md)）

## 节点目录 `/var/lib/nagi`

- `identity/`：证书、WireGuard 私钥、信任的面板列表（`panels.json`）、面板告诉的 mesh 成员（`mesh-peers.json`）、mesh 端口、告警配置和待补发的告警
- `node.db`：分配给本节点的容器（所属项目、容器目录）和它们的配置缓存（见下文）；容器网段的分配；监控数据
- `snapshots/<项目 ID>-<容器名>/`：快照仓库的连接配置和缓存
- `replicas/`：作为备份节点或热备时收到的副本
- `failover/`：本节点参与的顶替设置（也包括作为见证人的）
- `caddy/`：Caddy 的证书和状态
- `run/`：代理容器连进来用的 unix socket

**配置缓存**：面板每次修改或部署本节点上的容器时，把它的完整记录推给节点，节点存进 `node.db`：

- 容器：当前部署的配置、版本记录、端口映射、顶替和备份设置、修订号；
- 所属项目：名称、网络名、已部署的共享变量、镜像仓库认证、项目连接、部署记录、项目修订号。

项目的信息在它的每个节点上各存一份，以修订号大的为准。草稿只在面板上，不缓存。

## 项目与容器

- **项目**是一个逻辑分组，存在面板上，不属于哪台机器：前端、后端、数据库这些一起工作的东西放在一个项目里。项目也是网络的边界：项目里的容器互通，项目之间默认隔离。
- 项目里放的是**容器**，分两种：
  - **容器**：一个镜像跑起来的单个容器（可以附带文件），例如自己的后端。
  - **容器组**：一份 compose，里面有几个容器，例如自带数据库的开源应用（compose 里的一个服务就是组里的一个容器）。
- 层级就是 **项目 → 容器 / 容器组**，容器组展开才看到里面的容器。下文说"容器"时，如果说的是部署的单位，也包括容器组。
- **每个容器指定一个节点**：添加容器时选节点，之后可以迁移到别的节点。容器组整组在同一个节点上。项目里的容器可以都在一个节点上，也可以分散在几个节点上。
- **各自独立**：每个容器单独部署、单独启停、单独记版本和回滚、单独快照、迁移和顶替，有自己的草稿。改前端只重建前端，不碰数据库；数据库所在的节点坏了，只有数据库顶替到热备。
- **容器组整组部署**：组里的容器是同一份 compose，一起改配置、一起部署、一起记版本和回滚。状态、日志、终端、监控、环境变量、端口映射则按组里的每个容器分开。
- **也可以一起部署**：互相依赖的改动（例如后端改了接口、前端跟着改）可以一次部署几个，即使它们在不同节点上。每次部署都在项目上记一条部署记录，可以把整个项目回到某次部署时的状态（见"版本与回滚"）。
- 每个容器、每个容器组底层都是一个独立的 compose 项目，单个容器由表单生成 compose。部署行为和用户手动执行 compose 完全一致。
- 代码里对应的名字：`Container`（`kind` 是 `single` 或 `group`）；容器组里的容器就是 compose 的 service；Docker 实际运行的容器在代码里叫 `docker.Instance`。

## 标识与名字

- **项目 ID**：创建项目时由面板生成，全局唯一。项目名只用于显示，可以重名、可以修改。
- **网络名**：每个项目一个，在面板上唯一，只能用小写字母、数字和 `-`。创建项目时默认由项目名生成（汉字转成拼音）。别的项目连接本项目以后，用"容器.网络名"访问本项目的容器。改网络名时提示：连接了本项目的项目里用到旧地址的地方要跟着改。
- **容器名**（容器组的名字也一样）在项目内唯一，创建后不能改（目录、内网地址、映射都用它）。只能用小写字母、数字和 `-`，例如 `web`、`api`、`umami`。
- 每个容器或容器组的 compose 项目名是 `nagi-<项目 ID>-<容器名>`，Docker 里的容器名形如 `nagi-<项目 ID>-<容器名>-<服务>-1`，容器上带 `nagi.project`、`nagi.container` 标签。

## 容器目录

每个节点有一个**项目根目录**（节点设置，默认 `/srv/nagi`）。添加容器时，容器目录默认是 `<项目根目录>/<项目名>/<容器名>`（项目名转成拼音和小写字母、数字、`-`，例如"我的博客"是 `wo-de-bo-ke`；项目在这个节点上已有容器时沿用同一个项目文件夹；被别的项目用了时加 `-2`、`-3`），可以改成别的绝对路径。目录建好以后固定，项目改名不影响已有容器。目录必须不存在或为空，不能位于另一个容器的目录内。迁移、顶替、重新部署到别的节点时，默认用目标节点的项目根目录按同样的规则生成。例如 `/srv/nagi/shop/api`：

```
/srv/nagi/shop/api/
├── format             目录的格式版本号
├── compose.yml        当前版本的 compose（用户写的，或由表单生成）
├── override.yml       Nagi 的叠加配置
├── .env               变量：替换 compose 里的 ${变量}（权限 0600）
├── shared.env         这个容器当前版本用的共享变量（部署时生成，权限 0600）
├── env/<服务>.env     容器组里每个容器的环境变量（权限 0600）
├── docker/            项目的镜像仓库认证（权限 0600）
├── ssh/               从 git 拉取文件用的 deploy key
├── data/              运行文件（compose 里相对路径的根）
├── volumes/           命名 volume 的数据
└── backups/           kopia 快照仓库（每个容器一个）
```

除 `data/`、`volumes/`、`backups/` 以外的文件都由节点按面板下发的配置生成，部署时重写，手动修改会被覆盖。

**格式版本号**：容器目录会跟着容器在节点之间搬（顶替、迁移、备份节点），两边的节点版本可能不一样，所以 `format` 记着目录的格式版本：

- 节点打开容器目录时，格式比自己认识的旧，就先快照再就地升级（只往新升）；比自己认识的新，就不碰这个容器，提示先升级节点。
- 同步副本时带上格式版本号，接收方不认识就拒绝并告警，不会用看不懂的格式恢复。

## 网络

### 项目内网

项目里的所有容器，不论在哪个节点上，都用名字互相访问：

- 单个容器：用**容器名**，例如后端连 `db:5432`。
- 容器组里的容器：用**容器.容器组**，例如 `db.umami`。两个容器组里都有叫 `db` 的容器也不会冲突。
- 容器组内部仍然有自己的默认网络，组里的容器照常用 compose 里的服务名（如 `db`）互相访问，网上拿来的 compose 不用改。

项目内网一直开着，没有开关；需要隔离的东西放进不同的项目。

**同一节点上**：节点为每个在本节点上有容器的项目建一个 Docker 网络 `nagi-<项目 ID>`（/24，从节点本地的容器网段池分配，见 [mesh.md](mesh.md#容器网段只在节点内分配)）。

- 单个容器由 override 加入项目内网，表单生成的 compose 里服务名就是容器名，compose 自动把它注册为别名。
- 容器组**不**在 override 里加项目内网，而是由节点在容器启动后用 `docker network connect --alias` 接入，只带"容器.容器组"这个别名；容器重建后，节点根据 Docker 事件自动重新接入。原因：compose 会把服务原名也注册到它加入的每个网络上（实测），两份 compose 都有 `db` 时，项目内网里就会有两个 `db`。
- **名字不能撞**：单个容器的名字不能和项目里任何容器组里的容器（compose 服务名）相同，否则容器组内部查 `db` 时，可能查到项目内网里的单个容器 `db`。添加容器、改 compose 时由面板检查，撞了就拒绝并说明原因。

**跨节点**：项目里在别的节点上的每个容器，本节点都在项目内网里放一个**代理容器**，它在网络里的名字就是那个容器的名字。本节点的容器访问这个名字时连到代理，代理把连接交给本节点的 Nagi（经挂进代理容器的 unix socket），Nagi 经 mesh 交给对方节点的 Nagi，再由它连到真正的容器（mesh 的 7001 端口，见 [mesh.md](mesh.md#mesh-上的服务)）。

- 不建网卡、不改路由和 iptables，各节点的容器网段重叠也没关系，名字解析照常靠 Docker 自带的 DNS。
- 代理容器用节点本地生成的空镜像（不用拉取），运行的是挂进去的 nagi 本身，内存占用很小。所以发布的 nagi 是静态编译的（`CGO_ENABLED=0`）。节点升级后代理容器自动重建。
- **只转发 TCP**。端口：容器声明的端口（镜像的 `EXPOSE`、compose 的 `ports`、`expose`）自动带上（面板记在容器的记录里，所在节点暂时断开时代理照旧）；没声明的，在项目设置的"内部端口"里补，例如 `pg:5432`（容器组写 `容器.容器组:端口`）。
- **代理名单由面板下发**：面板知道每个容器在哪个节点、开着哪些端口，容器增删、迁移、部署后端口变化时，把"本节点要放哪些代理"推给相关节点；节点照着增删代理容器。名单缓存在节点上，面板不在时照旧。
- **跟着顶替走**：代理在每次连接时才确定对方现在在哪个节点：面板给的名单里带着容器的所在节点和顶替节点，代理先连所在节点，对方说"不在我这里"（已被顶替）再连顶替节点。所以容器顶替到热备以后，即使面板不在，十几秒内别的节点上的代理就指向新位置，名字不变。
- 每个代理容器占项目内网的一个地址：项目内网是 /24，本节点的容器和代理加起来最多 250 个左右。

### 项目连接

项目之间默认隔离。需要时，在项目的"网络"页**连接**另一个项目（例如多个应用共用一个数据库项目）。连接是双向的：连上以后，两个项目的容器都能访问对方的容器，名字是**容器.网络名**（例如 `pg.base`；容器组里的容器是 `容器.容器组.网络名`）。网络名在面板上唯一，所以不会和别的项目重名。

- **实现**：和跨节点一样用代理。项目 A 连接了项目 B，A 在每个节点上的项目内网里，为 B 的每个容器放一个代理，名字是"容器.B 的网络名"；B 那边同理。B 的容器和 A 的容器在同一个节点上时，代理由本节点的 Nagi 直接转发，不经 mesh。
- 只连接两个项目本身，不传递：A 连了 B、B 连了 C，A 和 C 之间仍然隔离。这也是为什么不把 B 的容器直接接进 A 的网络：那样 B 的容器也会看到 A 连接的其他项目。
- **名字不能撞**："容器.网络名"和项目内网里的"容器.容器组"格式一样，所以项目里有容器组的名字等于某个已连接项目的网络名时，拒绝连接（或拒绝添加这个容器组）并说明原因。
- 项目的"网络"页列出本项目每个容器在连接方看到的地址，照着填到别的项目里就行。
- **授权**：节点只接受面板告诉它的、有权访问的连接：同一项目的容器所在的节点，或者已连接项目的容器所在的节点；连进来以后只能连到对应项目里的容器。

## 创建方式

项目创建时可以是空的，之后往里加容器；也可以创建时就带上第一个容器。添加容器时选节点（默认上一次选的节点），加容器有两种方式，底层都是 compose：

1. **容器（镜像表单）**：填镜像（必填）、运行命令、端口、环境变量、持久化目录，以及可选的内存上限（MB）、CPU 上限（核数）、健康检查命令和间隔，Nagi 生成它的 `compose.yml`（服务名就是容器名；资源限制写成 `mem_limit`、`cpus`，健康检查写成 `healthcheck`，用 `sh -c` 执行，连续失败 3 次算不健康）。
   - **不提供文件**：就是直接运行在线镜像，例如 `nginx`、`redis`。
   - **提供文件**：文件放进容器的 `data/`，并挂进容器作为工作目录，适合运行构建好的程序。
   - **持久化目录**：填容器内的路径（如 `/var/lib/redis`），数据落到容器的 `volumes/<名字>`，和命名 volume 的处理一致。
2. **compose**：用户直接粘贴或编辑 compose，整份作为一个容器组，例如自带数据库的开源应用。
   - 暂不支持把一份 compose 拆成几个单独的容器：拆开要处理 `depends_on`、共用 volume、共用的 `.env`、自定义网络等，容易出错。自己的系统可以一个个容器地加；以后有真实需求再做拆分导入。

应用模板（一键安装 WordPress、Postgres 等）MVP 不做。模板本质上就是预填好的容器组，以后加模板库不影响架构。

## 环境变量

分三层，与 compose 自身的语义一致：

| 层级 | 作用 | 生效方式 |
| --- | --- | --- |
| 项目共享变量 | 项目里所有 compose 都能用 `${变量}` 引用，例如数据库密码 | 部署时写成容器目录的 `shared.env`，先传给 compose |
| 容器组变量 | 替换这个容器组 compose 里的 `${变量}` | 写成容器目录的 `.env`，再传 `--env-file`，同名时以它为准 |
| 容器的环境变量 | 传进容器（容器组里按组内的每个容器分别设） | 单个容器在镜像表单里；容器组的写成 `env/<服务>.env`，override 里为对应的服务加 `env_file` |

- 所有变量都存在面板上（密钥用面板主密钥加密），部署时随配置下发给容器所在的节点。
- 共享变量改一处，所有引用它的容器都能用上，不用在后端和数据库里各填一遍，即使它们在不同节点上。
- **共享变量也先存草稿**：改了先存为项目的草稿，不影响任何容器。部署这份草稿时，默认把引用了改动变量的容器一起部署（可以取消勾选），记一条部署记录。没跟着部署的容器标出"共享变量有更新"，下次部署它时用上。
- **每个容器的版本记下部署时用的共享变量**，所以镜像更新、git webhook 这类自动部署只会用已经部署过的共享变量，不会悄悄带上没部署的改动；回滚时也回到版本里记的值。
- 容器的环境变量只进入对应的容器，数据库密码不会出现在不需要它的容器里。

## 修改与部署

- **先存草稿，点部署才生效**。修改容器的 compose、变量等，都先保存为这个容器的草稿，存在面板上。页面提示"有未部署的修改"，用户可以继续修改、放弃草稿，或者点部署一次性生效。
- **部署一个容器**：面板把草稿定为这个容器的新版本，连同共享变量、镜像仓库认证、deploy key 一起下发给容器所在的节点；节点写好容器目录里的文件、执行 compose、观察 10 秒，把结果和镜像摘要报回面板，面板据此把版本标为已部署，再更新节点上的配置缓存。只影响它自己（容器组是组里的容器）。
- **一起部署**：可以一次选多个容器部署（例如有草稿的都部署），可以跨节点。由面板按依赖顺序逐个部署：容器可以设置"先部署的容器"（例如后端依赖数据库），一起部署时排在它们后面，没设置的按容器创建顺序；依赖有循环时拒绝。某个容器失败就停下，已经部署的保留，在日志里说明哪些成功、哪些没动。一起部署记为一条部署记录。
- **修订号**：每个容器有自己的修订号，保存它的草稿或部署它时加一；项目设置（名称、网络名、共享变量、项目连接）另有一个修订号。浏览器提交修改时带上它所基于的修订号，面板上的已经变了就拒绝，刷新后重新提交。两个浏览器窗口同时改不同的容器不会冲突。
- 项目设置（名称、网络名、项目连接、内部端口）不进版本，改了立即生效：面板更新相关节点的代理名单。共享变量是例外，走草稿（见"环境变量"）。
- **面板不可达时**：节点不接受修改，容器照常运行；节点上的配置缓存只用来重启、恢复和顶替，不能改。

## 部署方式

```
docker compose -p nagi-<项目 ID>-<容器名> \
  --project-directory <容器目录>/data \
  -f <容器目录>/compose.yml -f <容器目录>/override.yml \
  --env-file <容器目录>/shared.env --env-file <容器目录>/.env \
  up -d --remove-orphans
```

- **相对路径以容器的 `data/` 为准**：compose 里的 `./uploads` 就是 `<容器目录>/data/uploads`，网上拿来的 compose 不用改路径。
- **命名 volume 落到容器的 `volumes/<名字>`**：由 override 把命名 volume 绑定到这个目录，用户的 compose 不用改。这样容器的所有数据都在容器目录里。声明为 `external` 或使用了自定义 driver 的 volume 保持原样，界面上提示"这个 volume 不在快照范围内"。
- **文件更新后重启容器**：只更新了 `data/` 里的文件、compose 本身没变时，`compose up` 不会重建容器，所以部署时对挂载了 `data/` 的容器强制重建，确保运行的是新文件。
- **部署后观察 10 秒**：`compose up` 成功只说明容器启动了，程序可能几秒后就崩溃。部署完观察 10 秒，期间有容器以非 0 退出码退出，或者被 Docker 重启了，这次部署算作失败：输出它最后 20 行日志，版本不标记为已部署（和 `compose up` 失败一样）。以 0 退出、不重启的容器（执行一次就结束的任务）不算失败。
- **开始了就做完**：面板发来的删除、部署这类操作，开始执行以后不跟着调用方取消，避免留下"容器停了、记录还在"这样的半截状态。只有日志、终端这类一直跟着看的流，对方走了就停。
- **磁盘满了照样能看**：磁盘满了时节点照常上报状态，查看状态、日志、终端都能用；修改、部署、快照这些要写入的操作提示是哪块盘满了。
- **常见错误说人话**：节点返回给面板的错误先过一遍改写，原始错误附在后面。磁盘满说明是哪块盘满了；拉取镜像失败按 Docker 的输出区分镜像不存在或需要登录、没有这个标签、Docker Hub 限流、连不上镜像仓库、没有适合的 CPU 架构。部署过程中和节点的连接断了，面板提示"操作可能没做完，也可能已经做完"，让用户看容器状态和部署记录。
- **`network_mode: host` 的容器**：允许使用，但它不经过 Caddy、不在项目内网里、端口直接对外。容器页面上醒目提示。

## 镜像

- **镜像更新**：节点每天检查一次本节点上各容器用到的镜像有没有新版本（只查询镜像摘要，不下载，也不消耗 Docker Hub 的拉取次数），上报面板标出来，不自动升级。用户点"更新"时拉取新镜像并重新部署这个容器，记为这个容器的新版本，出问题可以回滚。
- **版本记录镜像摘要**：容器的每个版本记录部署时每个镜像的实际摘要（digest）。回滚时用旧摘要，即使镜像标签是 `latest`，也能回到当时那一份镜像。
- **镜像加速**：可以在面板上按节点配置镜像加速地址，国内节点配置、海外节点不配。只有用户配置了，Nagi 才会写入 Docker 的配置（`/etc/docker/daemon.json`），并提示需要重启 Docker。重启 Docker 会让容器短暂中断，建议同时开启 Docker 的 `live-restore`。
- **私有仓库认证**：每个项目有自己的认证（项目里所有容器共用），存在面板上（主密钥加密），部署时写进容器目录的 `docker/config.json`，通过 `DOCKER_CONFIG` 指向它，不碰全局的 `~/.docker`。两个项目用同一个仓库的不同账号也不会冲突。
  - 在项目上登录仓库时，由一个在线节点用 `docker login` 向仓库验证账号（接口只返回仓库地址，不返回密码）。项目登录过仓库才设置 `DOCKER_CONFIG`；没有时照旧用机器全局的配置。认证随配置下发给顶替节点和备份节点，热备提前拉镜像时也用它。
- **镜像更新的实现**：节点启动 5 分钟后检查一次，之后每 24 小时一次，也可以在容器上手动检查。对每个正在运行的容器，用 Docker 的 distribution 接口（HEAD 请求清单）查询标签当前的摘要，和本地镜像的仓库摘要比较。回滚时固定了摘要的镜像、本地构建（没有仓库摘要）的镜像跳过。"更新"就是带 `pull_images` 的容器部署：先 `docker compose pull` 再启动。

## 容器的文件怎么进入 `data/`

| 方式 | 说明 |
| --- | --- |
| 面板上传压缩包 | 上传 zip / tar.gz / tar，经 mesh 传到容器所在的节点，替换文件后直接部署（见下） |
| 从 git 仓库拉取 | 每个容器有一对 SSH deploy key（面板生成并保存），用户把公钥加到仓库的只读 deploy key。默认手动点"拉取并部署"，也可以开启 webhook（每个容器一个地址），push 后自动部署这个容器。拉取在容器所在的节点上进行，节点需要能访问 git 服务器 |
| 用户自己放 | 用 scp / rsync 直接放进 `<容器目录>/data/` |

- **更新时整体替换，保留指定目录**：新文件先放到临时目录，再替换容器 `data/` 的内容。用户列出的保留路径（如 `uploads/`、`logs/`）不动。这样不会残留已删除的旧文件，也不会误删运行中产生的数据。
- **保留路径第一次出现时用新文件初始化**：保留路径在节点上还不存在时（例如第一次部署），照常用新文件里的内容创建；之后就以节点上的为准。
- **面板上传**：浏览器把压缩包 POST 到面板的 `/api/upload`（要带 `X-Nagi-Upload` 请求头，跨站页面发不出），面板经 mesh 调用容器所在节点的 `MeshService.Upload` 流式转发，节点只接受信任面板的 mesh 公钥。节点解压到 `<容器目录>/.upload/files` 暂存，界面随后用 `use_upload` 部署这个容器，和 git 拉取走同一条路（部署前快照、保留路径、版本文件快照、回滚都一样）。
  - 压缩包里只有一个顶层目录时自动去掉这一层（例如 `dist/`）。
  - 只解出普通文件和目录，跳过符号链接；路径一律限制在解压目录内（`..` 在根目录处截止）；跳过 `__MACOSX/` 和 `.DS_Store`；解压后总大小上限 10 GiB。
  - 解出的文件一律保证所有用户可读（至少 0644），保留可执行位：容器里的进程常以非 root 用户运行，而很多打包工具默认写 0600。
  - 新的上传会替换上一次还没部署的上传；部署时文件进了 `data/` 就删除暂存，部署失败要重新上传。
- **自动保护挂载目录**：compose 里挂载进容器的 `data/` 下的目录（如 `./pgdata:/var/lib/postgresql/data`）一律自动加入保留路径，防止更新文件时把数据库目录冲掉。如果新上传的文件里也包含某个保留路径，以现有内容为准，并在部署日志里提示"上传中的这部分被忽略"。
- **不在节点上构建**：MVP 只运行构建好的文件，构建交给用户本地或 CI。

## 有状态的判定

用了命名 volume 或者有保留路径的容器，自动视为有状态，其余视为无状态。界面上显示判定结果，用户可以手动覆盖。有状态与否按容器算，决定：

- 部署这个容器前是否自动保存它的数据；快照时是否暂停它（见 [snapshot.md](snapshot.md#一致性)）；
- 顶替这个容器是否需要人工确认（见 [failover.md](failover.md)）。

## 版本与回滚

- **版本按容器记**：每次部署一个容器都生成它的一个新版本（包括没有修改、只是重新部署或拉取了新文件）。最新版本还没成功部署过时（刚创建，或者上次部署失败）复用它的版本号。
- **一个版本 = 配置 + 文件 + 镜像摘要**。配置是容器的 compose、变量、密钥，以及部署时用的共享变量（端口映射和项目设置不在版本里，改了立即生效）；文件是部署那一刻容器 `data/` 里除保留路径以外的内容；镜像摘要是部署时每个镜像的实际 digest。不管文件是上传、git 拉取还是手动放进来的，都在点"部署"时记为新版本。
- **版本记录在面板上，版本文件在节点上**：版本的配置和摘要存在面板（也缓存在容器所在的节点上）；版本文件存在容器的 kopia 仓库里，靠去重只占变化的部分，随容器同步给顶替节点和备份节点，顶替、迁移以后可以接着回滚。每个容器保留最近 20 个版本。
- **回滚 = 用旧版本的配置、文件和镜像生成这个容器的一个新版本并部署**，回滚本身也是一个版本，可以再回滚。镜像固定到旧版本记录的摘要。只影响这个容器。版本文件已经不在了（例如节点坏了、容器被重新部署到别的节点）的版本不能回滚，界面上标出。
- 运行数据（`volumes/` 和保留路径）默认不动。有状态容器每次部署前自动保存一份它的数据，回滚到版本 N 时可以勾选"同时恢复数据"：先停止这个容器，恢复版本 N 被替换前的那份数据，再启动。
- 草稿不受回滚影响。
- **部署记录**：每次部署（一个或多个容器）在项目上记一条，内容是部署完成后**所有容器**各自的版本，以及这次动了哪些容器、来源（手动、git、镜像更新、回滚）。保留最近 100 条。
- **回到某次部署时的状态**：选一条部署记录，版本和它不一样的容器都回滚到记录里的版本（各自生成新版本），作为一次一起部署执行，本身也记一条部署记录。之后才加的容器不动，界面上提示。

## 删除

- **删除容器（或容器组）**：节点停止并删除它（容器组是组里所有容器），面板把它从项目里移除；容器目录默认保留，想一起删除需要确认。它的版本记录一并删除，部署记录里保留它的名字，指向它的端口映射一并删除；其他节点上指向它的代理随之删除。
- **删除项目**：删除所有容器和项目连接，**容器目录默认保留**（含数据和快照）。想连目录一起删除，需要输入项目名确认。容器所在的节点离线时，删除照常进行，节点上线后由面板通知它清理。

## override 叠加配置

agent 为每个容器或容器组生成 `<容器目录>/override.yml`，部署时叠加在它的 compose 之上。用户的 compose 不会被修改，导出时仍是原版。

生成 override 前，agent 先解析用户的 compose（用 compose 官方的 Go 解析库），只为用户没写的字段补默认值。因为 override 里写的值会覆盖用户的值，不能无差别地写入默认值。

**Nagi 必须加的**：

- 容器组默认网络的网段（从节点本地的容器网段池分配的 /26，见 [mesh.md](mesh.md#容器网段只在节点内分配)）；单个容器不建自己的网络
- 单个容器：加入项目内网（`external`）。容器组由节点用 `docker network connect` 接入（见"网络"）
- 命名 volume 绑定到容器的 `volumes/<名字>`
- 容器环境变量的 `env_file`
- 管理标签：`nagi.project`（项目 ID）、`nagi.container`（容器名或容器组名）、`nagi.single`（单个容器）、`nagi.version`
- 去掉所有 `ports` 映射，对外访问统一由 Caddy 按端口映射转发（见 [exposure.md](exposure.md)）

**默认值（用户在 compose 里写了就以用户的为准）**：

| 项目 | 默认值 | 理由 |
| --- | --- | --- |
| 日志 | json-file，每个容器最多 3 个 10MB 文件 | Docker 默认不轮转，日志会撑满磁盘 |
| 重启策略 | `unless-stopped` | 容器挂了或机器重启后自动拉起，手动停止的不拉起 |
| 资源限制 | 不限制，界面上可设 | 应用差异太大，默认值容易误杀；监控里显示用量，内存吃紧时告警 |

去掉 `ports` 依赖 compose 的 `!reset` 语法，要求 docker compose 2.24 或更新版本。
