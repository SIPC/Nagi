# 节点

节点由 `nagi agent` 启动（或作为 `nagi server` 的内嵌 agent），是自己项目的**数据主人**。只支持 Linux（amd64 / arm64），以 systemd 服务运行。

## 职责

- **保存自己项目的数据**：项目和成员的 compose、环境变量、密钥、历史版本都以节点本地的为准
- 主动连接信任列表中的每一个面板，接收用户的修改，存到本地后执行，再把结果和最新数据上报给所有面板（见 [control-plane.md](control-plane.md)）
- 调用 `docker compose` 部署和更新项目
- 内嵌 Caddy（含 layer4 模块）：所有对外流量的统一出口，占用节点的 80/443（见 [exposure.md](exposure.md)）
- 版本、快照与回滚（见本文和 [snapshot.md](snapshot.md)）；手动迁移（见 [failover.md](failover.md)）
- 把快照同步给顶替节点或备份节点；作为顶替节点时，提前准备好要顶替的项目并参与租约投票（见 [failover.md](failover.md)）
- WireGuard 组网（见 [mesh.md](mesh.md)）
- 采集监控数据存在本地，在本地判断并发送告警（见 [monitoring.md](monitoring.md)）

## 节点目录 `/var/lib/nagi`

节点自身的数据，项目数据都在各自的项目目录里：

- `identity/`：证书、WireGuard 私钥、信任的面板列表（`panels.json`）、各面板告诉的 mesh 成员（`mesh-peers.json`）、mesh 端口、告警配置和待补发的告警
- `node.db`：本节点有哪些项目、各自的项目目录在哪；容器网段的分配；共享网络和它们的跨节点连接；监控数据
- `snapshots/<项目 ID>/`：快照仓库的连接配置和缓存
- `replicas/`：作为备份节点或热备时收到的副本
- `failover/`：本节点参与的顶替设置（也包括作为见证人的）
- `caddy/`：Caddy 的证书和状态
- `run/`：跨节点共享网络的代理连进来用的 unix socket

## 项目与成员

- **项目**是一个分组，也是网络和搬迁的边界：前端、后端、数据库这些一起工作的东西放在一个项目里。迁移、顶替、备份节点、定时快照、删除都按整个项目进行。
- **成员**是项目里独立部署的单位，有两种：
  - **单容器成员**：一个镜像（可以附带文件），例如自己的后端。
  - **compose 成员**：一份 compose，里面可以有多个服务，例如自带数据库的开源应用。
- **成员各自独立**：每个成员单独部署、单独启停、单独记版本和回滚，有自己的草稿。改前端只重建前端的容器，不碰数据库；回滚一个成员也不影响别的成员。
- **也可以一起部署**：互相依赖的改动（例如后端改了接口、前端跟着改）可以一次部署多个成员。每次部署都在项目上记一条部署记录，可以把整个项目回到某次部署时的状态（见"版本与回滚"）。
- 每个成员底层都是一个独立的 compose 项目，单容器成员由表单生成 compose。部署行为和用户手动执行 compose 完全一致。

## 项目标识

- 每个项目创建时生成一个全局唯一的**项目 ID**，项目名只用于显示，可以重名、可以修改。项目迁移或顶替到其他节点、多个面板同时管理时，都靠项目 ID 识别同一个项目。
- **成员名**在项目内唯一，创建后不能改（容器名、内网地址、映射都用它）。只能用小写字母、数字和 `-`，例如 `web`、`api`、`umami`。
- 每个成员的 compose 项目名是 `nagi-<项目 ID>-<成员名>`，容器名形如 `nagi-<项目 ID>-<成员名>-<服务>-1`。

## 项目目录

创建项目时由用户**手动填写**，没有默认值。目录不能位于另一个项目的目录内。例如 `/mnt/qmt`：

```
/mnt/qmt/
├── config/                项目级配置
│   ├── format             项目目录的格式版本号
│   ├── project.db         成员、版本历史、部署记录、草稿
│   ├── .env               项目共享变量（权限 0600，所有成员都能引用）
│   ├── routes/            端口映射，每条一个文件，改了立即生效（见 exposure.md）
│   ├── docker/            本项目的镜像仓库认证（权限 0600，所有成员共用）
│   └── backup.key         快照仓库密码
├── members/<成员>/        每个成员一个目录
│   ├── compose.yml        当前版本的 compose（用户写的，或由表单生成）
│   ├── override.yml       Nagi 的叠加配置
│   ├── .env               成员级变量（权限 0600）
│   ├── shared.env         这个成员当前版本用的共享变量（部署时生成，权限 0600）
│   ├── env/<服务>.env     服务级环境变量（权限 0600）
│   ├── ssh/               从 git 拉取文件用的 deploy key
│   ├── data/              成员的运行文件（compose 里相对路径的根）
│   └── volumes/           命名 volume 的数据
└── backups/               kopia 快照仓库（整个项目一个）
```

顶替节点和备份节点上的项目目录在设置时单独指定。

**格式版本号**：项目目录会跟着项目在节点之间搬（顶替、迁移、备份节点），两边的节点版本可能不一样，所以 `config/format` 记着目录的格式版本：

- 节点打开项目时，格式比自己认识的旧，就先快照再就地升级（只往新升）；比自己认识的新，就不碰这个项目，提示先升级节点。
- 同步副本时带上格式版本号，接收方不认识就拒绝并告警（见 [control-plane.md](control-plane.md#接口设计)），不会用看不懂的格式恢复。

## 网络

### 项目内网

- 节点为每个项目建一个 Docker 网络 `nagi-<项目 ID>`，网段从节点本地的容器网段池分配（见 [mesh.md](mesh.md#容器网段只在节点内分配)）。
- **默认开启**，在项目设置里可以关闭。开启时，每个成员的容器都加入项目内网，可以用名字互相访问：
  - 单容器成员：用**成员名**，例如后端连 `db:5432`。
  - compose 成员里的服务：用**服务.成员**，例如 `db.umami`。两份 compose 里都有叫 `db` 的服务也不会冲突。
- compose 成员内部仍然有自己的默认网络，里面的服务照常用 compose 里的原名（如 `db`）互相访问，网上拿来的 compose 不用改。
- 单容器成员不单独建网络，只在项目内网里，省网段。
- **接入方式**：
  - 单容器成员由 override 加入项目内网。表单生成的 compose 里服务名就是成员名，compose 自动把它注册为别名。
  - compose 成员**不**在 override 里加项目内网，而是由节点在容器启动后用 `docker network connect --alias` 接入，只带"服务.成员"这个别名；容器重建后，节点根据 Docker 事件自动重新接入。原因：compose 会把服务原名也注册到它加入的每个网络上（实测），两份 compose 都有 `db` 时，项目内网里就会有两个 `db`。
- **名字不能撞**：单容器成员的名字不能和项目里任何 compose 成员的服务名相同，否则 compose 成员内部查 `db` 时，可能查到项目内网里的单容器成员 `db`。加成员、改 compose 时检查，撞了就拒绝并说明原因。
- 关闭内网时，成员之间互相访问不了：compose 成员断开项目内网，只留在自己的默认网络里（内部照常互通），不重建；单容器成员这时改成单独一个网络，需要重建容器（短暂重启），重新打开内网时同理。界面上提前提示。

### 共享网络

- 项目之间默认隔离。需要时，在节点上建一个命名的**共享网络**（例如 `db-shared`），让几个项目加入，例如多个应用共用一个数据库项目。
- 项目加入共享网络时要设一个**网络名**（小写字母、数字和 `-`，本节点唯一，默认由项目名生成）。它的成员在共享网络里的名字是**成员.网络名**（例如 `pg.base`；compose 成员里的服务是 `服务.成员.网络名`），不会和别的项目重名。项目名可以重名、可以改，所以不直接用项目名；改项目名不影响网络名，改网络名时提示连它的项目要跟着改。
- 共享网络一律由节点用 `docker network connect --alias` 接入，和 compose 成员接入项目内网一样。
- 共享网络的网段也从节点的容器网段池分配。
- 没连起来的共享网络只在本节点存在。设置顶替或迁移时，如果目标节点上没有项目加入的共享网络，界面上明确提示"搬到其他节点后会断开和哪些项目的连接"。搬过去以后，目标节点上有同名网络就留在里面（网络名被占用时退出并提示改名），没有就退出、需要时重新加入。共用一个数据库的东西，最好放进同一个项目，共享网络只用于例外情况。

### 跨节点连接共享网络

几个节点上的同名共享网络可以在面板上**连起来**（例如 n1、n2 上的 `db`）。连起来以后，加入它的项目不论在哪个节点，都用同样的名字互相访问，例如 n1 上的应用照常连 `pg.base:5432`，`base` 项目实际在 n2 上。

- **连接关系存在节点上**：每个节点记着"`db` 和哪些节点相连"，双方互相记着才算连通，换面板也不丢。在面板上连接时，面板给相关节点同时设置（节点上没有这个网络就先建）；两组已经连通的节点连在一起时合并成一组，组里每两个节点之间都相连。发起连接的面板必须管理组里的所有节点（所以它们都在同一个 mesh 里）。断开时，本节点和组里其他节点互相删掉对方。删除共享网络前要先断开连接。
- **代理容器**：对方节点上加入了这个网络的每个成员，本节点都在网络里放一个代理容器，它在网络里的名字就是对方成员的名字。本节点的容器访问这个名字时连到代理，代理把连接交给本节点的 Nagi（经挂进代理容器的 unix socket），Nagi 经 mesh 交给对方节点的 Nagi，再由它连到真正的容器。
  - 不建网卡、不改路由和 iptables，各节点的容器网段重叠也没关系，名字解析照常靠 Docker 自带的 DNS。
  - 代理容器用节点本地生成的空镜像（不用拉取），运行的是挂进去的 nagi 本身，内存占用很小。所以发布的 nagi 是静态编译的（`CGO_ENABLED=0`）。节点升级后代理容器自动重建。
  - **只转发 TCP**。端口：对方容器声明的端口（镜像的 `EXPOSE`、compose 的 `ports`、`expose`）自动带上；没声明的，在对方项目的设置里补"跨节点端口"，例如 `pg:5432`（compose 成员写 `服务.成员:端口`）。
  - 每个代理容器占网络里的一个地址：一个共享网络（/26）里，本地成员和代理加起来最多 62 个左右。
- **成员列表**：每个节点每 10 秒经 mesh 问一遍相连的节点"你这里的 `db` 里有哪些成员、开着哪些端口"，据此增删代理容器。对方暂时联系不上时保留现有的代理（连接会失败），恢复后照常。同一个名字本节点也有时以本节点的为准。
- **跟着顶替走**：代理在每次连接时才查这个名字现在在哪个节点。项目顶替或迁移到另一个也连着这个网络的节点后，十几秒内代理就指向新节点，名字不变，项目也不用退出再加入。
- **网络名在整组里唯一**：项目加入共享网络、连接两组节点时，检查整组里有没有别的项目用了同一个网络名，有就拒绝。加入时连不上组里的某个节点也拒绝（检查不了）；顶替、迁移过去时不检查连不上的节点，真撞了名，代理按"本节点优先、再按节点公钥顺序"选一个并告警。
- **授权**：只有组里的节点能查询这个网络的成员列表、能经 mesh 连进来；连进来以后只能连到这个网络里的成员。

## 创建方式

项目创建时可以是空的，之后往里加成员；也可以创建时就带上第一个成员。加成员有两种方式，底层都是 compose：

1. **单容器（镜像表单）**：填镜像（必填）、运行命令、端口、环境变量、持久化目录，以及可选的内存上限（MB）、CPU 上限（核数）、健康检查命令和间隔，Nagi 生成成员的 `compose.yml`（服务名就是成员名；资源限制写成 `mem_limit`、`cpus`，健康检查写成 `healthcheck`，用 `sh -c` 执行，连续失败 3 次算不健康）。
   - **不提供文件**：就是直接运行在线镜像，例如 `nginx`、`redis`。
   - **提供文件**：文件放进成员的 `data/`，并挂进容器作为工作目录，适合运行构建好的程序。
   - **持久化目录**：填容器内的路径（如 `/var/lib/redis`），数据落到成员的 `volumes/<名字>`，和命名 volume 的处理一致。
2. **compose**：用户直接粘贴或编辑 compose，整份作为一个 compose 成员，例如自带数据库的开源应用。
   - 暂不支持把一份多服务的 compose 拆成多个单容器成员：拆开要处理 `depends_on`、共用 volume、共用的 `.env`、自定义网络等，容易出错。自己的系统可以一个个成员地加；以后有真实需求再做拆分导入。

应用模板（一键安装 WordPress、Postgres 等）MVP 不做。模板本质上就是预填好的 compose 成员，以后加模板库不影响架构。

## 环境变量

分三层，与 compose 自身的语义一致：

| 层级 | 作用 | 存放 | 生效方式 |
| --- | --- | --- | --- |
| 项目共享变量 | 所有成员的 compose 里都能用 `${变量}` 引用，例如数据库密码 | `config/.env`；部署时复制到成员的 `shared.env` | 部署时先传 `shared.env` |
| 成员级变量 | 替换这个成员 compose 里的 `${变量}` | `members/<成员>/.env` | 再传成员的 `--env-file`，同名时以成员的为准 |
| 服务级环境变量 | 传进对应服务的容器 | `members/<成员>/env/<服务>.env` | override 里为该服务加 `env_file` |

- 共享变量改一处，所有引用它的成员都能用上，不用在后端和数据库里各填一遍。
- **共享变量也先存草稿**：改了先存为项目的草稿，不影响任何成员。部署这份草稿时，草稿写进 `config/.env`，并默认把引用了改动变量的成员一起部署（可以取消勾选），记一条部署记录。没跟着部署的成员标出"共享变量有更新"，下次部署它时用上。
- **每个成员的版本记下部署时用的共享变量**：部署时把 `config/.env` 复制成成员的 `shared.env` 再传给 compose。所以镜像更新、git webhook 这类自动部署只会用已经部署过的共享变量，不会悄悄带上没部署的改动；回滚时也回到版本里记的值。
- 服务级变量只进入对应的容器，数据库密码不会出现在不需要它的容器里。单容器成员只有一个服务，界面上只显示一层。

## 修改与部署

- **先存草稿，点部署才生效**。修改成员的 compose、变量等，都先保存为这个成员的草稿，存在 `config/project.db`。页面提示"有未部署的修改"，用户可以继续修改、放弃草稿，或者点部署一次性生效。
- **部署一个成员时生成这个成员的新版本**（见下文"版本与回滚"），只影响这个成员的容器。
- **一起部署**：可以一次选多个成员部署（例如有草稿的都部署）。按依赖顺序逐个部署：成员可以设置"先部署的成员"（例如后端依赖数据库），一起部署时排在它们后面，没设置的按成员创建顺序；依赖有循环时拒绝。某个成员失败就停下，已经部署的保留，在日志里说明哪些成功、哪些没动。一起部署记为一条部署记录。
- **修订号**：每个成员有自己的修订号，保存它的草稿或部署它时加一；项目设置（名称、共享变量、内网、共享网络）另有一个修订号。面板提交修改时带上它所基于的修订号，节点上的已经变了就拒绝，面板刷新后重新提交。两个面板同时改不同的成员不会冲突（见 [control-plane.md](control-plane.md#多面板同时修改)）。
- 项目设置（名称、内网开关、共享网络）不进版本，改了立即生效：内网开关和共享网络通过 `docker network connect/disconnect` 调整正在运行的容器；只有开关内网时单容器成员要重建（见"网络"）。共享变量是例外，走草稿（见"环境变量"）。

## 部署方式

```
docker compose -p nagi-<项目 ID>-<成员> \
  --project-directory /mnt/qmt/members/<成员>/data \
  -f /mnt/qmt/members/<成员>/compose.yml -f /mnt/qmt/members/<成员>/override.yml \
  --env-file /mnt/qmt/members/<成员>/shared.env --env-file /mnt/qmt/members/<成员>/.env \
  up -d --remove-orphans
```

- **相对路径以成员的 `data/` 为准**：compose 里的 `./uploads` 就是 `members/<成员>/data/uploads`，网上拿来的 compose 不用改路径。
- **命名 volume 落到成员的 `volumes/<名字>`**：由 override 把命名 volume 绑定到这个目录，用户的 compose 不用改。这样项目的所有数据都在项目目录里。声明为 `external` 或使用了自定义 driver 的 volume 保持原样，界面上提示"这个 volume 不在快照范围内"。
- **文件更新后重启服务**：只更新了 `data/` 里的文件、compose 本身没变时，`compose up` 不会重建容器，所以部署时对挂载了 `data/` 的服务强制重建，确保运行的是新文件。
- **`network_mode: host` 的服务**：允许使用，但它不经过 Caddy、不在项目内网里、端口直接对外。成员页面上醒目提示。

## 镜像

- **镜像更新**：节点每天检查一次各成员用到的镜像有没有新版本（只查询镜像摘要，不下载，也不消耗 Docker Hub 的拉取次数），在面板上标出来，不自动升级。用户点"更新"时拉取新镜像并重新部署这个成员，记为这个成员的新版本，出问题可以回滚。
- **版本记录镜像摘要**：成员的每个版本记录部署时每个镜像的实际摘要（digest）。回滚时用旧摘要，即使镜像标签是 `latest`，也能回到当时那一份镜像。
- **镜像加速**：可以在面板上按节点配置镜像加速地址，国内节点配置、海外节点不配。只有用户配置了，Nagi 才会写入 Docker 的配置（`/etc/docker/daemon.json`），并提示需要重启 Docker。重启 Docker 会让容器短暂中断，建议同时开启 Docker 的 `live-restore`。
- **私有仓库认证**：每个项目有自己的认证文件 `config/docker/config.json`（项目里所有成员共用），部署时通过 `DOCKER_CONFIG` 环境变量指向它，不碰全局的 `~/.docker`。两个项目用同一个仓库的不同账号也不会冲突。认证信息和密钥一样存储和备份。
  - 在项目上登录仓库时用 `docker login` 向仓库验证账号，登录信息写进项目的 `config/docker/`（接口只返回仓库地址，不返回密码）。项目登录过仓库才设置 `DOCKER_CONFIG`；没有时照旧用机器全局的配置，节点上全局 `docker login` 过的照常能用。登录信息随项目目录同步给备份节点和顶替节点，热备提前拉镜像时也用它。
- **镜像更新的实现**：节点启动 5 分钟后检查一次，之后每 24 小时一次，也可以在项目上手动检查。对每个正在运行的服务，用 Docker 的 distribution 接口（HEAD 请求清单）查询标签当前的摘要，和本地镜像的仓库摘要比较；私有仓库用项目自己的登录信息。回滚时固定了摘要的镜像、本地构建（没有仓库摘要）的镜像跳过。结果随项目状态上报给面板（`image_updates`）。"更新"就是带 `pull_images` 的成员部署：先 `docker compose pull` 再启动，记为这个成员的新版本，可以回滚。
- **镜像加速的实现**：面板上按节点设置加速地址，节点把 `registry-mirrors` 写进 `/etc/docker/daemon.json`，保留文件里的其他配置；接口同时返回 Docker 当前生效的地址，两者不一样说明还没有重启 Docker。

## 成员的文件怎么进入 `data/`

| 方式 | 说明 |
| --- | --- |
| 面板上传压缩包 | 上传 zip / tar.gz / tar，经 mesh 传到节点，替换文件后直接部署（见下） |
| 从 git 仓库拉取 | 每个成员自动生成一对 SSH deploy key，用户把公钥加到仓库的只读 deploy key。默认手动点"拉取并部署"，也可以开启 webhook（每个成员一个地址），push 后自动部署这个成员。节点需要能访问 git 服务器 |
| 用户自己放 | 用 scp / rsync 直接放进 `members/<成员>/data/` |

- **更新时整体替换，保留指定目录**：新文件先放到临时目录，再替换成员 `data/` 的内容。用户列出的保留路径（如 `uploads/`、`logs/`）不动。这样不会残留已删除的旧文件，也不会误删运行中产生的数据。
- **保留路径第一次出现时用新文件初始化**：保留路径在节点上还不存在时（例如第一次部署），照常用新文件里的内容创建；之后就以节点上的为准。
- **面板上传**：浏览器把压缩包 POST 到面板的 `/api/upload`（要带 `X-Nagi-Upload` 请求头，跨站页面发不出），面板经 mesh 调用节点的 `MeshService.Upload` 流式转发，节点只接受信任面板的 mesh 公钥。上传时指定成员，节点解压到 `members/<成员>/.upload/files` 暂存，界面随后用 `use_upload` 部署这个成员：在项目锁内替换它的 `data/`、生成它的新版本，和 git 拉取走同一条路（部署前快照、保留路径、版本文件快照、回滚都一样）。
  - 压缩包里只有一个顶层目录时自动去掉这一层（例如 `dist/`）。
  - 只解出普通文件和目录，跳过符号链接；路径一律限制在解压目录内（`..` 在根目录处截止）；跳过 `__MACOSX/` 和 `.DS_Store`；解压后总大小上限 10 GiB。
  - 解出的文件一律保证所有用户可读（至少 0644），保留可执行位：容器里的进程常以非 root 用户运行，而很多打包工具默认写 0600。
  - 新的上传会替换上一次还没部署的上传；部署时文件进了 `data/` 就删除暂存，部署失败要重新上传。
- **自动保护挂载目录**：compose 里挂载进容器的 `data/` 下的目录（如 `./pgdata:/var/lib/postgresql/data`）一律自动加入保留路径，防止更新文件时把数据库目录冲掉。如果新上传的文件里也包含某个保留路径，以现有内容为准，并在部署日志里提示"上传中的这部分被忽略"。
- **不在节点上构建**：MVP 只运行构建好的文件，构建交给用户本地或 CI。

## 有状态的判定

用了命名 volume 或者有保留路径的成员，自动视为有状态，其余视为无状态。界面上显示判定结果，用户可以手动覆盖。项目里只要有一个成员有状态，项目就算有状态。

- 成员是否有状态决定：部署这个成员前是否自动保存它的数据；快照时是否暂停它的容器（见 [snapshot.md](snapshot.md#一致性)）。
- 项目是否有状态决定：顶替是否需要人工确认（见 [failover.md](failover.md)）。

## 版本与回滚

- **版本按成员记**：每次部署一个成员都生成它的一个新版本（包括没有修改、只是重新部署或拉取了新文件）。最新版本还没成功部署过时（刚创建，或者上次部署失败）复用它的版本号。
- **一个版本 = 配置 + 文件 + 镜像摘要**。配置是成员的 compose、变量、密钥，以及部署时用的共享变量（端口映射和其他项目设置不在版本里，改了立即生效）；文件是部署那一刻成员 `data/` 里除保留路径以外的内容；镜像摘要是部署时每个镜像的实际 digest。不管文件是上传、git 拉取还是手动放进来的，都在点"部署"时记为新版本，三种来源只有一套逻辑。
- 版本记录存在 `config/project.db`，文件存在 `backups/` 的 kopia 仓库里，靠去重只占变化的部分。两者都随项目同步给顶替节点和备份节点，顶替、迁移以后版本记录和部署记录还在，可以接着回滚。每个成员保留最近 20 个版本。版本文件的快照单独打标签，只按版本数量清理，不受定时快照保留策略的影响。
- **回滚 = 用旧版本的配置、文件和镜像生成这个成员的一个新版本并部署**，回滚本身也是一个版本，可以再回滚。镜像固定到旧版本记录的摘要。只影响这个成员。
- 运行数据（`volumes/` 和保留路径）默认不动。有状态成员每次部署前自动保存一份它的数据，回滚到版本 N 时可以勾选"同时恢复数据"：先停止这个成员，恢复版本 N 被替换前的那份数据，再启动。
- 草稿不受回滚影响。
- **部署记录**：每次部署（一个或多个成员）在项目上记一条，内容是部署完成后**所有成员**各自的版本，以及这次动了哪些成员、来源（手动、git、镜像更新、回滚）。项目页显示的就是这个列表，保留最近 100 条。
- **回到某次部署时的状态**：选一条部署记录，版本和它不一样的成员都回滚到记录里的版本（各自生成新版本），作为一次一起部署执行，本身也记一条部署记录。之后才加的成员不动，界面上提示。前后端一起改出了问题，一次就能一起回滚。

## 删除

- **删除成员**：停止并删除它的容器，从项目里移除；它的目录默认保留，想一起删除需要确认。它的版本记录一并删除，部署记录里保留它的名字，对外映射里指向它的规则失效。
- **删除项目**：停止并删除所有成员的容器、项目网络，**项目目录默认保留**（含数据和快照）。想连目录一起删除，需要输入项目名确认。

## override 叠加配置

agent 为每个成员生成 `members/<成员>/override.yml`，部署时叠加在成员的 compose 之上。用户的 compose 不会被修改，导出时仍是原版。

生成 override 前，agent 先解析用户的 compose（用 compose 官方的 Go 解析库），只为用户没写的字段补默认值。因为 override 里写的值会覆盖用户的值，不能无差别地写入默认值。

**Nagi 必须加的**：

- compose 成员默认网络的网段（从节点本地的容器网段池分配的 /26，见 [mesh.md](mesh.md#容器网段只在节点内分配)）；单容器成员在内网开启时不建自己的网络
- 单容器成员：加入项目内网（`external`），内网关闭时改为自己的网络。compose 成员和共享网络不写在这里，由节点用 `docker network connect` 接入（见"网络"）
- 命名 volume 绑定到成员的 `volumes/<名字>`
- 服务级环境变量的 `env_file`
- 管理标签：`nagi.project`（项目 ID）、`nagi.member`（成员名）、`nagi.version`
- 去掉所有 `ports` 映射，对外访问统一由 Caddy 按 `config/routes/` 转发（见 [exposure.md](exposure.md)）

**默认值（用户在 compose 里写了就以用户的为准）**：

| 项目 | 默认值 | 理由 |
| --- | --- | --- |
| 日志 | json-file，每个容器最多 3 个 10MB 文件 | Docker 默认不轮转，日志会撑满磁盘 |
| 重启策略 | `unless-stopped` | 容器挂了或机器重启后自动拉起，手动停止的不拉起 |
| 资源限制 | 不限制，界面上可设 | 应用差异太大，默认值容易误杀；监控里显示用量，内存吃紧时告警 |

去掉 `ports` 依赖 compose 的 `!reset` 语法，要求 docker compose 2.24 或更新版本。
