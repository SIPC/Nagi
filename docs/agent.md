# 节点

节点由 `nagi agent` 启动（或作为 `nagi server` 的内嵌 agent），是自己项目的**数据主人**。只支持 Linux（amd64 / arm64），以 systemd 服务运行。

## 职责

- **保存自己项目的数据**：compose、环境变量、密钥、历史版本都以节点本地的为准
- 主动连接信任列表中的每一个面板，接收用户的修改，存到本地后执行，再把结果和最新数据上报给所有面板（见 [control-plane.md](control-plane.md)）
- 调用 `docker compose` 部署和更新项目
- 内嵌 Caddy（含 layer4 模块）：所有对外流量的统一出口，占用节点的 80/443（见 [exposure.md](exposure.md)）
- 版本、快照与回滚（见本文和 [snapshot.md](snapshot.md)）；手动迁移（见 [failover.md](failover.md)）
- 把快照同步给顶替节点或备份节点；作为顶替节点时，提前准备好要顶替的项目并参与租约投票（见 [failover.md](failover.md)）
- WireGuard 组网（见 [mesh.md](mesh.md)）
- 采集监控数据存在本地，在本地判断并发送告警（见 [monitoring.md](monitoring.md)）

## 节点目录 `/var/lib/nagi`

节点自身的数据，都很小：

- 身份信息：证书、WireGuard 私钥、信任的面板列表
- 节点 SQLite：本节点有哪些项目、各自的项目目录在哪、租约状态、监控数据

## 项目标识

- 每个项目创建时生成一个全局唯一的**项目 ID**，项目名只用于显示，可以重名、可以修改。
- compose 项目名使用 `nagi-<项目 ID>`。项目迁移或顶替到其他节点、多个面板同时管理时，都靠项目 ID 识别同一个项目，不会因为重名冲突。

## 项目目录

创建项目时由用户**手动填写**，没有默认值。目录不能位于另一个项目的目录内。例如 `/mnt/qmt`：

```
/mnt/qmt/
├── config/              agent 对这个项目的配置
│   ├── compose.yml      当前版本的 compose（用户写的，或由表单生成）
│   ├── override.yml     Nagi 的叠加配置
│   ├── .env             项目级变量（权限 0600）
│   ├── env/<服务>.env   服务级环境变量（权限 0600）
│   ├── docker/          本项目的镜像仓库认证（权限 0600）
│   ├── routes/          端口映射，每条一个文件，改了立即生效（见 exposure.md）
│   └── project.db       版本历史、草稿
├── data/                项目根目录，项目的实际运行文件
├── volumes/             compose 中命名 volume 的数据
└── backups/             kopia 快照仓库
```

顶替节点和备份节点上的项目目录在设置时单独指定。

## 创建方式

只有两种，底层都是 compose：

1. **写 compose**：用户直接粘贴或编辑 compose。
2. **镜像表单**：填镜像（必填）、运行命令、端口、环境变量、持久化目录，Nagi 生成 `config/compose.yml`。以后用户可以切换到直接编辑 compose。
   - **不提供文件**：就是直接运行在线镜像，例如 `nginx`、`redis`。
   - **提供文件**：文件放进 `data/`，并挂进容器作为工作目录，适合运行构建好的程序。
   - **持久化目录**：填容器内的路径（如 `/var/lib/redis`），数据落到 `volumes/<名字>`，和命名 volume 的处理一致。

应用模板（一键安装 WordPress、Postgres 等）MVP 不做。模板本质上就是预填好的 compose，以后加模板库不影响架构。

## 环境变量

分两层，与 compose 自身的语义一致：

| 层级 | 作用 | 存放 | 生效方式 |
| --- | --- | --- | --- |
| 项目级变量 | 替换 compose 里的 `${变量}` | `config/.env` | 部署时用 `--env-file` 传给 compose |
| 服务级环境变量 | 传进对应服务的容器 | `config/env/<服务>.env` | override 里为该服务加 `env_file` |

服务级变量只进入对应的容器，数据库密码不会出现在不需要它的容器里。镜像表单只有一个服务，界面上只显示一层。

## 修改与部署

- **先存草稿，点部署才生效**。修改 compose、变量、开放设置等，都先保存为草稿，存在 `config/project.db`。页面提示"有未部署的修改"，用户可以继续修改、放弃草稿，或者点部署一次性生效。
- **部署时生成一个新版本**（见下文"版本与回滚"）。
- **修订号**：项目有一个修订号，每次保存草稿或部署都加一。面板提交修改时带上它所基于的修订号，节点上的修订号已经变了就拒绝，面板刷新后重新提交。这就是多面板同时修改时的冲突处理（见 [control-plane.md](control-plane.md#多面板同时修改)）。

## 部署方式

```
docker compose -p nagi-<项目 ID> \
  --project-directory /mnt/qmt/data \
  -f /mnt/qmt/config/compose.yml -f /mnt/qmt/config/override.yml \
  --env-file /mnt/qmt/config/.env \
  up -d --remove-orphans
```

- **相对路径以 `data/` 为准**：compose 里的 `./uploads` 就是 `data/uploads`，网上拿来的 compose 不用改路径。
- **命名 volume 落到 `volumes/<名字>`**：由 override 把命名 volume 绑定到这个目录，用户的 compose 不用改。这样项目的所有数据都在项目目录里。声明为 `external` 或使用了自定义 driver 的 volume 保持原样，界面上提示"这个 volume 不在快照范围内"。
- **文件更新后重启服务**：只更新了 `data/` 里的文件、compose 本身没变时，`compose up` 不会重建容器，所以部署时对挂载了 `data/` 的服务强制重建，确保运行的是新文件。
- **`network_mode: host` 的服务**：允许使用，但它不经过 Caddy、没有网段隔离、端口直接对外。项目页面上醒目提示。

## 镜像

- **镜像更新**：节点每天检查一次项目用到的镜像有没有新版本（只查询镜像摘要，不下载，也不消耗 Docker Hub 的拉取次数），在面板上标出来，不自动升级。用户点"更新"时拉取新镜像并重新部署，记为一个新版本，出问题可以回滚。
- **版本记录镜像摘要**：每个版本记录部署时每个镜像的实际摘要（digest）。回滚时用旧摘要，即使镜像标签是 `latest`，也能回到当时那一份镜像。
- **镜像加速**：可以在面板上按节点配置镜像加速地址，国内节点配置、海外节点不配。只有用户配置了，Nagi 才会写入 Docker 的配置（`/etc/docker/daemon.json`），并提示需要重启 Docker。重启 Docker 会让容器短暂中断，建议同时开启 Docker 的 `live-restore`。
- **私有仓库认证**：每个项目有自己的认证文件 `config/docker/config.json`，部署时通过 `DOCKER_CONFIG` 环境变量指向它，不碰全局的 `~/.docker`。两个项目用同一个仓库的不同账号也不会冲突。认证信息和密钥一样存储和备份。

## 项目文件怎么进入 `data/`

| 方式 | 说明 |
| --- | --- |
| 面板上传压缩包 | 上传 zip / tar.gz，经 mesh 中转到节点 |
| 从 git 仓库拉取 | 每个项目自动生成一对 SSH deploy key，用户把公钥加到仓库的只读 deploy key。默认手动点"拉取并部署"，也可以开启 webhook，push 后自动部署。节点需要能访问 git 服务器 |
| 用户自己放 | 用 scp / rsync 直接放进 `data/` |

- **更新时整体替换，保留指定目录**：新文件先放到临时目录，再替换 `data/` 的内容。用户列出的保留路径（如 `uploads/`、`logs/`）不动。这样不会残留已删除的旧文件，也不会误删运行中产生的数据。
- **自动保护挂载目录**：compose 里挂载进容器的 `data/` 下的目录（如 `./pgdata:/var/lib/postgresql/data`）默认自动加入保留路径，防止更新文件时把数据库目录冲掉。用户可以手动移除。如果新上传的文件里也包含某个保留路径，以现有内容为准，并在部署日志里提示"上传中的这部分被忽略"。
- **不在节点上构建**：MVP 只运行构建好的文件，构建交给用户本地或 CI。

## 有状态项目的判定

用了命名 volume 或者有保留路径的项目，自动视为有状态，其余视为无状态。界面上显示判定结果，用户可以手动覆盖。这个判定决定：

- 顶替是否需要人工确认（见 [failover.md](failover.md)）
- 快照时是否暂停容器（见 [snapshot.md](snapshot.md#一致性)）
- 部署前是否自动快照

## 版本与回滚

- **每次部署都生成一个新版本**（包括没有修改、只是重新部署或拉取了新文件）。最新版本还没成功部署过时（刚创建，或者上次部署失败）复用它的版本号。
- **一个版本 = 配置 + 文件 + 镜像摘要**。配置是 compose、变量、密钥（端口映射不在版本里，改了立即生效）；文件是部署那一刻 `data/` 里除保留路径以外的内容；镜像摘要是部署时每个镜像的实际 digest。不管文件是上传、git 拉取还是手动放进来的，都在点"部署"时记为新版本，三种来源只有一套逻辑。
- 版本记录存在 `config/project.db`，文件存在 `backups/` 的 kopia 仓库里，靠去重只占变化的部分。默认保留最近 20 个版本，可调整。版本文件的快照单独打标签，只按版本数量清理，不受定时快照保留策略的影响。
- **回滚 = 用旧版本的配置、文件和镜像生成一个新版本并部署**，回滚本身也是一个版本，可以再回滚。镜像固定到旧版本记录的摘要。
- 运行数据（`volumes/` 和保留路径）默认不动。有状态项目每次部署前自动保存一份数据，回滚到版本 N 时可以勾选"同时恢复数据"：先停止服务，恢复版本 N 被替换前的那份数据，再启动。
- 草稿不受回滚影响。

## 删除项目

- 停止并删除容器，**项目目录默认保留**（含数据和快照）。
- 想连目录一起删除，需要输入项目名确认。

## override 叠加配置

agent 为每个项目生成 `config/override.yml`，部署时叠加在用户的 compose 之上。用户的 compose 不会被修改，导出时仍是原版。

生成 override 前，agent 先解析用户的 compose（用 compose 官方的 Go 解析库），只为用户没写的字段补默认值。因为 override 里写的值会覆盖用户的值，不能无差别地写入默认值。

**Nagi 必须加的**：

- 项目默认网络的网段（从节点本地的容器网段池分配的 /26，见 [mesh.md](mesh.md#容器网段只在节点内分配)）
- 命名 volume 绑定到 `volumes/<名字>`
- 服务级环境变量的 `env_file`
- 管理标签：`nagi.project`（项目 ID）、`nagi.version`
- 去掉所有 `ports` 映射，对外访问统一由 Caddy 按 `config/routes/` 转发（见 [exposure.md](exposure.md)）

**默认值（用户在 compose 里写了就以用户的为准）**：

| 项目 | 默认值 | 理由 |
| --- | --- | --- |
| 日志 | json-file，每个容器最多 3 个 10MB 文件 | Docker 默认不轮转，日志会撑满磁盘 |
| 重启策略 | `unless-stopped` | 容器挂了或机器重启后自动拉起，手动停止的不拉起 |
| 资源限制 | 不限制，界面上可设 | 应用差异太大，默认值容易误杀；监控里显示用量，内存吃紧时告警 |

去掉 `ports` 依赖 compose 的 `!reset` 语法，要求 docker compose 2.24 或更新版本。
