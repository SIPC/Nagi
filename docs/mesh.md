# WireGuard mesh

mesh 是节点和面板之间的数据通道。管理操作走控制面（见 [control-plane.md](control-plane.md)），不依赖 mesh。

## 组网

- 节点之间组成全连接（full mesh）网络。
- **面板也加入 mesh**。
- **范围**：一个面板和它管理的所有节点组成一个 mesh。一个节点同一时间只归一个面板管理，所以项目的容器、它们的顶替节点和备份节点一定在同一个 mesh 里。移交过程中节点短暂同时在两个面板的 mesh 里。
- **成员列表的传播**：节点每次上报（连上时、状态变化时、每 15 秒）都带上自己的 mesh 信息（公钥、UDP 端口、本机地址、别人看到的公网地址）；面板在响应里返回成员列表：面板自己加上它所有在线节点。
- **用途**：快照传输、租约投票、容器文件上传（面板 → 节点），项目内网和项目连接里跨节点的容器之间的连接（见 [agent.md](agent.md#网络)），以及跨节点入口的对外流量（见 [exposure.md](exposure.md#跨节点入口)）。
- **密钥**：每个 agent 和面板都在本地生成自己的 WireGuard 私钥，私钥不离开本机。

## 实现：全部使用用户态 wireguard-go

不使用内核 WireGuard，只有一套代码路径，也不需要内核模块。mesh 传快照、上传、投票和容器之间的 TCP 连接，用户态的性能够用。

**进程内网络栈**：mesh 用 wireguard-go 自带的用户态网络栈（gVisor netstack），不建网卡、不改路由、不需要 `/dev/net/tun`，在容器里也能跑。只有 Nagi 自己的流量走 mesh，机器上的其他程序看不到 mesh 地址。容器跨节点访问也不需要网卡：容器连的是本节点上的代理容器，代理把连接交给 Nagi，由 Nagi 经 mesh 转给对方节点（见 [agent.md](agent.md#网络)）。

**UDP 端口**：节点首次启动时随机选一个并记在 `identity/mesh-port`，可以用 `nagi agent --mesh-port` 指定；记住的端口被占用时重新随机选。面板的 UDP 用和面板端口相同的号码。端口不通时自动改走面板中转，不影响可用。

wireguard-go 的底层收发由 Nagi 自己实现（`internal/pkg/mesh`），按顺序尝试三种路径：

1. **UDP 直连**
2. **UDP 经面板中转**：直连不通时（例如双方都在 NAT 后面）
3. **套在 TLS 里经面板中转**：UDP 完全不通时，WireGuard 数据包经控制连接传输（`PanelService.MeshRelay` 双向流）

mesh 坏了只影响数据传输和投票，不影响管理。

### 路径选择

- WireGuard 眼里每个对端的"地址"就是对端本身（公钥），每个包走哪条路径由收发层决定，所以路径切换不会打断 WireGuard 会话。
- **探测包**：和 WireGuard 共用 UDP 端口，以 `NAGI` 开头（WireGuard 包的第一个字节是 1～4，不会混淆）。ping/pong 用双方 WireGuard 密钥协商出的共享密钥做 MAC，别人伪造不了；只有收到对自己 ping 的 pong（事务号对得上）才认为直连可用，重放旧包也没用。
- 直连不可用时，每 5 秒向对方所有候选地址（面板告诉的地址、从对方 ping 学到的地址）发 ping；可用时每 10 秒保活一次，25 秒没收到 pong 就认为断了。收到对方的 ping 会立刻反向 ping，加快 NAT 打洞。
- pong 里带着"我看到的你的地址"，节点由此知道自己经过 NAT 以后的公网地址，上报给面板，面板再告诉其他节点。
- 发送顺序：直连可用就直连；对方就是控制连接的另一端时走控制连接；否则经共同面板 UDP 中转（要求到这个面板的直连可用）；再不行经共同面板的控制连接中转。
- **面板中转**：面板只替自己的在线节点中转。UDP 中转按来源地址认出发送方（地址必须是 ping/pong 确认过的）；控制连接中转一律按连接所属的节点算发送方，不信任包里写的来源。WireGuard 本身还会再校验一次。
- 来源地址没确认过的 WireGuard 包直接丢弃。
- **成员列表里刚消失的成员先留 2 分钟**：节点重启时会和面板断开一下，面板下一次给的列表里就没有它了。要是立刻删掉，它回来后发起的握手会被丢掉，要等其他节点下一次上报（最多 15 秒）才重新加上。留着只是网络还通，每个操作仍单独校验调用方（见下文"mesh 连通不等于授权"）。
- **对端重启**：重启的一方加上成员时 WireGuard 就发起握手，这时往往还没有可用的路径。发不出去的握手发起包先暂存（5 秒），直连确认或控制连接登记后马上补发；加上成员时也立刻探测直连。否则另一方会一直用重启前的会话发包（全被丢掉），要等 WireGuard 自己超时重新握手，十几秒连不上。

### 抗丢包（FEC）

mesh 里的 TCP 跑在 gVisor 上，拥塞控制是 reno/cubic：跨境线路上只要有少量随机丢包就会频繁降速（往返 150 ms、丢包 0.2% 时只有约 0.4 MB/s）。所以直连时在收发层加前向纠错（`internal/pkg/mesh/fec.go`），丢的包在接收方算回来，上面的 TCP、UDP 转发、租约投票都察觉不到丢包：

- **分组**：发给一个对端的 WireGuard 包每 10 个一组，按需附带 m 个 Reed-Solomon 校验包，组里丢的包不超过 m 个都能算回来。组没凑满时最多等 5 ms 就按已有的包发校验，流量小的时候丢的包也等得到。
- **冗余随丢包率调整**：接收方按组统计对方发来的包丢了多少，攒够约 2000 个包就在下一个能力包里报给对方（见下文，2 秒一个）；发送方按报告选 m：丢包低于 0.05% 时为 0（只多 7 字节包头），0.5% 以下为 1，2% 以下为 2，再多为 3。增加立刻生效，减少要连续 3 次报告都偏低：丢包少时一次报告里可能正好没丢，一下就减，冗余会来回跳。新连接一开始 m 为 1，等报告来了再调：等测出丢包再加，TCP 早就降速了。
- **不加校验包的组不提前结束**：接收方只能从校验包里知道一组提前结束了，所以 m 为 0 时一组总是凑满 10 个。
- **按顺序交付**：有校验包的组里前面缺了包，后面先到的包先扣下，算回来以后按原来的顺序一起交给 WireGuard，最多扣 15 ms；否则 TCP 看到乱序就当成丢包降速，算回来也晚了。算不回来时到时间就放行，只多这 15 ms 延迟。
- **范围**：只用于 UDP 直连。经面板中转的包不加：UDP 中转会让面板多转发，控制连接中转本身不丢包。
- **能力包**：直连时双方每 2 秒互发一个能力包（和 ping 一样带 MAC），写明自己支持哪些能力，以及收到对方的包的丢包率。45 秒没收到就当对方不支持（例如换回了旧版本）；旧版本不认识能力包，直接忽略，所以只有双方都支持时才加 FEC 包头。
- **格式**：数据包和校验包的第一个字节是 0x10、0x11，和 WireGuard 包（1～4）、控制包（`NAGI`）都不重。

节点页「网络」标签的每个连接写着当前的纠错（例如「纠错 1/10」）和丢包率（见下文的丢包率），悬停可以看到已经恢复的包数。

线路拥堵时丢包是成串的（队列满了一次丢一批），校验包救不回来，还多占本来就不够的带宽。所以接收方同时统计丢的包里有多少是一组丢了 3 个以上的：超过一半时在能力包里告诉对方"校验包没用"，对方 1 分钟内不加校验包，之后再按丢包率试。随机丢包时一组丢 3 个以上很少见（丢包 2% 时约千分之一）。

### QUIC 快速通道

FEC 只能救回零散的丢包，mesh 里 TCP 的拥塞控制本身（reno/cubic）在长距离线路上仍然慢。所以两端都支持、并且直连时，mesh 上的 TCP 连接改走 QUIC，拥塞控制用 BBR（`internal/pkg/mesh/quic.go`，BBR 取自 Hysteria，MIT 许可，在 `internal/pkg/mesh/bbr`）：

- **不开新端口**：QUIC 包和 WireGuard 包共用 mesh 的 UDP 端口，按第一个字节区分（QUIC 包第二高位总是 1，WireGuard 包是 1～4，FEC 包是 0x10、0x11；控制包以 `NAGI` 开头，先按控制包解析，解析不了的才当 QUIC）。只收已经确认直连的地址发来的 QUIC 包，所以也沿用直连已经打通的 NAT。
- **身份**：QUIC 的 TLS 证书是每次启动临时生成的，不用来认人。握手后，发起方在第一个流上发自己的公钥和证明，接收方回自己的证明；证明是用双方 WireGuard 密钥协商出的共享密钥（和 ping 的 MAC 是同一个）对 TLS 导出的会话值算的 HMAC。会话值和这次 TLS 连接绑定，中间人转发也通不过；接收方还要求连接来自对方确认过的直连地址。连接上的调用方身份就是这个公钥，`KeyOf` 照常按 mesh 地址认人，权限检查不变。
- **连接**：每对成员之间一条 QUIC 连接，两个方向都可以开流；对方表示支持 QUIC 时由公钥小的一方提前建好，另一方需要时也会现建。每个 mesh TCP 连接是一个流，开头两个字节是目标端口，支持半关闭。
- **透明**：`Dial` 先试 QUIC，对方不支持（旧版本）、不是直连、2 秒内建不起来时走 WireGuard 里的 TCP，建不起来的 1 分钟内不再试；`Listen` 两种连接都收。容器跨节点访问、跨节点入口、快照同步、面板上传文件都自动受益，上层不用改。
- **重启**：无状态重置的密钥由私钥推出，成员重启后对方的旧连接马上收到重置，不用等 30 秒的空闲超时。
- **不走 QUIC 的**：跨节点的 UDP（数据报本来就不重传）、经面板中转的连接。
- **流量**：QUIC 包不经过 WireGuard，按对端单独计数，加进每个成员的收发字节，概览的流量图和节点的流量监控照常统计。
- **关闭**：节点设置里的「QUIC 快速通道」可以关掉（所在网络限制或降速 UDP 时），保存在节点的 `identity/mesh-quic-off`。关闭后马上断开已有的 QUIC 连接，并在能力包里不再声明支持，其他成员随即改走 WireGuard；重新打开后马上通知各成员并重建连接。面板自己的 mesh 不能关。

节点页「网络」标签里用着 QUIC 的连接写着「QUIC」。

### 测速

节点页「网络」标签里每个成员后面有「测速」（只有管理员能用）：节点经 mesh 连对方的 7002 端口，先上传 5 秒、再下载 5 秒（走 QUIC 时再经 WireGuard 隧道各测一次，共约 20 秒），显示两个方向的速率，悬停可以看到这次走的是 QUIC 还是 WireGuard。走的路和业务流量一样，测出来的就是容器跨节点访问、迁移、同步时能拿到的速度（`internal/pkg/mesh/speed.go`）。

- 速率在收的一端算，跳过开头 1 秒（慢启动），上传的结果由对方回传。
- 每个成员同一时间只接受一个测速，别人正在测时直接拒绝；单个方向最长 10 秒，调用方要求再长也按 10 秒算。
- 对方是旧版本（没有 7002 端口）时提示不支持。
- **对比和提示**：走 QUIC 时再经 WireGuard 隧道（隧道里 gVisor 的 TCP）测一次，悬停可以看到对比。QUIC 包不在 WireGuard 隧道里，两者共用 UDP 端口、并列存在，主要差别是拥塞控制（BBR 和 cubic）。有更快的走法时在第二行提示：
  - WireGuard 隧道比 QUIC 快 20% 以上：可以在节点设置关闭 QUIC（对这个节点的所有连接生效）。
  - 直连但有一端关了 QUIC：开启后通常更快。
  - 经面板中转：放行两端的 mesh UDP 端口后可以直连。
- 不会自动按测速结果切换：接入时照旧按规则选（能直连、两端都支持就走 QUIC）。

### 丢包率

「网络」标签里直连的成员在第二行显示两个方向最近的丢包率（`丢包 ↑ 0.93% ↓ 0.05%`）：

- **↑ 发给对方的包**：取下面两个里较新的。经 WireGuard 的由对方按 FEC 序号统计后在能力包里报告（见上文的抗丢包）；经 QUIC 的由这一端的 QUIC 统计，每发 1000 个包算一次。quic-go 换成 BBR 以后不再统计丢包，所以在拥塞控制外面包了一层自己数。
- **↓ 对方发来的包**：这一端按 FEC 序号统计，只有经 WireGuard 的流量；流量都走 QUIC 时测不到这个方向，看对方节点页里的 ↑。
- 流量太少（不够一个统计窗口）、5 分钟没有更新、不是直连、对方是旧版本时不显示。

### mesh 上的服务

每个节点和面板在自己 mesh 地址的 7000 端口提供 `MeshService`（gRPC）。流量已经由 WireGuard 加密和认证，gRPC 不再加 TLS；调用方身份就是来源 mesh 地址对应的公钥。方法有：

- `Ping`：连通测试。面板上可以查看每个节点的 mesh 状态（到 mesh 里每个节点和面板走哪条路径、握手时间、收发字节）并测试连通。
- `Upload`：面板把容器文件上传到节点（客户端流）。
- `VolumeDownload` / `VolumeUpload`：存储标签的文件下载和上传，面板转发浏览器的请求（见 [agent.md](agent.md#存储)）。
- `ReplicaManifest` / `ReplicaPut` / `ReplicaCommit`：把容器的快照仓库同步给顶替节点或备份节点（见 [snapshot.md](snapshot.md#备份节点的实现)）。
- `LeaseVotes`：顶替的租约投票，按容器，同一对成员之间的多个容器合并成一次请求（见 [failover.md](failover.md#实现)）。

7002 端口是测速（见上文）。7001 端口转发容器之间的 TCP 连接：调用方先发一行请求（项目 ID、容器、端口），节点检查调用方有权访问这个项目、容器确实在本节点上运行后，连到那个容器，回一行结果，然后双向转发；容器不在本节点上（例如已经被顶替）时回"不在这里"，代理再试顶替节点。跨节点入口也走这个端口，入口节点只能访问映射指向的那个端口（见 [exposure.md](exposure.md#权限)）。

容器之间的 UDP 也在 7001 端口握手，数据报走 mesh 上的 UDP：

- 请求行以 `udp` 开头，多带调用方在 mesh 上的 UDP 端口；检查和 TCP 一样（端口要是容器声明的或内部端口里补的 UDP 端口），通过后对方开一个只收调用方这个端口的 UDP 端口，回 `OK <端口>`。mesh 上的来源地址已经由 WireGuard 认证，数据报不再单独校验。
- **多路复用**：一个代理的一个 UDP 端口只握手一次，所有客户端的数据报都走这条通道，前面加 4 字节的流 ID（代理容器按客户端地址分配，不重复使用）。目标节点按流 ID 为每个客户端开一个连到容器的 UDP socket；只发过一个数据报的流（例如 DNS 查询）30 秒没动静就关掉，其余的 2 分钟；一条通道最多 1024 个流，满了关掉最久没动的。
- 握手的 TCP 连接留着做控制连接：两边每 10 秒发一个空行，30 秒没收到就算断了；目标节点发现容器不在了或者换了地址时主动断开。调用方有数据要发时还在控制连接上发 `?`（最多每秒一次），对方立刻回一个空行，3 秒没回就拆掉通道：对方节点重启、断网时不用等 30 秒的心跳超时。断了以后调用方重新按顺序握手（第一次立刻重试，连续刚建好就断才等 3 秒），容器被顶替以后就连到顶替节点；重新握手期间的数据报丢掉。
- 单个数据报最大 16 KiB，更长的丢掉。超过 mesh MTU（1280）的靠 IPv6 分片，丢一片整个数据报就丢了。
- 旧版节点不认识 `udp` 请求，回"请求格式不对"，调用方当作连不上。

## 地址

### mesh 地址：由公钥推导的 IPv6

- 每个节点和面板的 mesh 地址由它的 WireGuard 公钥计算得出：固定前缀 `fd4e:6167::/32`（"Nagi" 的 ASCII），后 96 位取公钥的哈希。
- **不需要分配**：加入时不用分配地址，多个面板各自加节点、两个 mesh 合并，都不会冲突（重复概率可以忽略）。
- **不能冒用**：成员列表里只有公钥，mesh 地址总是由公钥算出来，WireGuard 又按公钥认证对方，所以别人无法冒用他人的地址。
- IPv6 只在隧道内部使用，节点之间的外层网络照常走 IPv4。

### 容器网段：只在节点内分配

- 每个节点有一个本地的容器网段池，默认 `10.200.0.0/16`：本节点上有容器的每个项目，项目内网占一个 /24（放本节点的容器和代理）；每个容器组的默认网络占一个 /26；单个容器只在项目内网里，不另占。
- 只在节点内保证不重复，不需要全局协调。分配时跳过和 Docker 现有网络重叠的网段。如果和节点所在的局域网冲突，可以按节点修改。
- 只有容器组的默认网络和项目内网使用这个网段；compose 里用户自定义的其他网络仍由 Docker 分配。
- 容器迁移或顶替到其他节点时，在新节点上重新分配。
- 跨节点访问不用容器的 IP，而是经代理容器按名字访问，所以各节点的网段重叠也没关系。

## mesh 连通不等于授权

在同一个 mesh 里，只说明网络能通。每个操作都要单独校验调用方身份（调用方公钥对应的是哪个面板或节点）：

- 容器文件上传：只接受该节点信任列表里的面板。
- 租约投票和快照同步：只接受该容器顶替设置里的 A、B（或备份节点）和见证人。
- 容器之间的连接：只接受面板告诉本节点"有权访问这个项目"的节点（同一项目、或已连接项目的容器所在的节点，以及它们的顶替节点），只能连到这个项目里的容器。

这样一个节点上的容器不能借 mesh 访问和它没有关系的项目。
