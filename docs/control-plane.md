# 控制面

控制面是面板与节点之间的管理通道。

## 连接

- agent 通过 **mTLS** 连接信任列表中每个面板的**面板端口**，这是唯一的控制通道，方向永远是 agent → 面板，节点无需为控制面暴露任何入站端口。
- 面板不占用 80/443，这两个端口留给 Caddy。单机模式下面板和内嵌 agent 因此不会冲突。
- 面板首次启动时生成自签 CA。agent 用面板的公钥指纹校验面板身份，不需要域名，也不需要外部 CA。
- **面板必须能被所有节点访问**。面板有一个"对外地址"设置（自动检测，可修改），安装命令和节点连接都使用这个地址。面板在 NAT 后面时，需要用户做端口转发。
- 控制面**不依赖** WireGuard mesh：国内与海外之间跨境时，原生 WireGuard（UDP）不可靠，而普通的 TCP + TLS 连接通常可用。如果跨境环境下高位端口受限，可以在用 `--no-agent` 启动、因而没有 Caddy 的面板机器上，用 `--port 443` 把面板端口指定为 443。

## 信任的面板列表

每个节点维护一份**信任的面板列表**，记录每个面板的地址和公钥指纹。节点会主动连接列表里的每一个面板。

**修改列表只有两条路：**

1. **由已信任的面板发指令**：已经被信任的面板可以让节点加入或移除某个面板。新面板先生成一次性令牌，旧面板把新面板的地址、指纹和令牌发给节点，节点连上新面板，用令牌完成登记，流程和节点首次加入一样。
2. **在节点上用 root 执行本地命令**：用于旧面板已经挂掉、无法再发指令的情况。能登录节点 root 的人本来就拥有这台机器，这条路不会降低安全性。

没有其他方式能让节点信任一个新面板，别人无法冒充面板接管节点。

**常见操作都由这个机制组合而成：**

| 操作 | 做法 |
| --- | --- |
| 换面板 | 旧面板把新面板加进列表，再把自己移除 |
| 增加面板 | 把新面板加进列表，不移除旧的 |
| 旧面板已挂，换面板 | 在节点上执行本地命令，把新面板加进列表、把旧面板移除 |

## 多面板同时修改

- **面板之间不需要互相通信或同步。** 每个面板各自连接节点，节点把数据报给每个面板，所以每个面板手里都有一份完整的配置备份。
- **冲突在节点上解决。** 每个项目带一个修订号，保存草稿或部署都会加一（见 [agent.md](agent.md#修改与部署)）。面板提交修改时注明"基于第 N 号修订"，如果节点上的项目已经不是第 N 号，节点拒绝这次修改，面板刷新后重新提交。不需要加锁，也不需要选主。

## 节点加入流程

1. **面板生成一次性令牌**，1 小时内有效，用一次就作废。面板给出一行安装命令，大致形如：

   ```
   curl --pinnedpubkey "sha256//<面板公钥指纹>" -k https://<地址:端口>/install.sh \
     | sh -s -- --token <令牌>
   ```

   面板是自签证书，所以用 `-k` 跳过 CA 校验，真正的校验靠 `--pinnedpubkey` 钉住面板公钥，中间人无法冒充。
2. **安装脚本检查环境并下载 nagi**：检查是否为 Linux、是否已安装 Docker 和 compose 插件（2.24 或更新版本），不满足就提示用户先安装，不自动安装 Docker。然后从面板下载 nagi 二进制（同样钉住公钥），安装为 systemd 服务。不依赖 GitHub，国内节点也能快速下载。
3. **agent 在本地生成两对密钥**：身份密钥和 WireGuard 密钥。私钥都不离开节点。mesh 地址由 WireGuard 公钥直接算出，不需要分配（见 [mesh.md](mesh.md#地址)）。
4. **agent 调用面板的 Enroll 接口**，提交令牌、身份公钥（CSR）和 WireGuard 公钥。
5. **面板校验令牌后立即作废**，签发证书，返回证书、CA 和 peer 列表。持有令牌即视为已授权，不需要再在面板上确认。
6. **agent 写入信任列表**，启动 WireGuard，与面板建立长连接。面板把新节点推送给其他节点，加入 mesh。

**证书有效期**：节点的客户端证书有效期 1 年，每次连上面板时自动续期，只要一年内连上过面板就不会过期。面板另外维护一份已移除节点的名单，名单上的节点即使证书未过期也立即拒绝连接。

**移除节点**：面板忘记这个节点并把它加入已移除名单。节点上的项目照常运行，数据仍在节点上；节点若还信任其他面板，仍可被那些面板管理。

**单机模式**：`nagi server` 内嵌的 agent 在本机自动完成以上流程，不需要令牌和安装命令。

## 接口设计

**连接结构**：

```
浏览器 ──HTTPS──┐
               ├─► 面板端口 ──按 TLS ALPN 分流──┬─ 浏览器：Web UI + Connect-RPC + WebSocket
agent ──TLS────┘                               └─ agent：yamux 多路复用
                                                     ├─ agent 调面板：PanelService
                                                     └─ 面板调 agent：AgentService（反向 gRPC）
```

agent 主动连上面板后，在同一条 TLS 连接上用 yamux 复用出多条通道。agent 照常调用面板的接口；同时 agent 在这条连接上反过来充当 gRPC 服务端，面板像调用普通接口一样调用 agent。这样每个操作都是独立的强类型接口，日志和终端就是普通的流式接口，以后加功能只需加一个方法。

**服务划分**：

| 服务 | 调用方向 | 主要方法 |
| --- | --- | --- |
| EnrollService | agent → 面板（尚无证书时） | `Enroll`：用令牌换证书和 peer 列表 |
| PanelService | agent → 面板 | 上报最新状态（供总览页）；项目版本变化时上报配置备份；上报事件 |
| AgentService | 面板 → agent（反向 gRPC） | 项目：部署、更新、回滚、启停、删除；观察：日志（服务端流）、终端（双向流）、查询历史指标；节点：更新 peer 列表、修改信任列表、升级 |
| MeshService | agent ↔ agent / 面板，经 WireGuard，直接连对方的 mesh 地址 | 租约投票；快照同步给顶替节点或备份节点；项目文件上传（面板 → 节点，客户端流） |

文件上传走 mesh，大文件不占用控制连接，管理操作不会被上传卡住。mesh 直连不通时，WireGuard 流量会自动套在 TLS 里经面板中转。mesh 上的 gRPC 同样使用 mTLS，证书与控制面相同。由于一个 mesh 里可能有多个面板签发的证书，每个调用都要校验调用方是否有权限（见 [mesh.md](mesh.md)）。

**浏览器与面板**：用 Connect-RPC，和节点共用同一套 proto 定义，自动生成 TypeScript 类型；也支持普通 JSON，可以用 curl 调用。终端这类双向交互用 WebSocket，由面板桥接到 `AgentService` 的终端接口。

**版本兼容**：

- proto 只加字段，不修改、不删除已有字段。
- 面板兼容比自己旧一个大版本的节点，升级面板时节点不用同时停。
- 面板上可以一键把节点升级到同一版本，二进制从面板下载。
