# 控制面

控制面是面板与节点之间的管理通道。

## 连接

- agent 通过 **mTLS** 连接信任列表中面板的**面板端口**，这是唯一的控制通道，方向永远是 agent → 面板，节点无需为控制面暴露任何入站端口。
- 面板不占用 80/443，这两个端口留给 Caddy。单机模式下面板和内嵌 agent 因此不会冲突。
- 面板首次启动时生成自签 CA。agent 用面板的公钥指纹校验面板身份，不需要域名，也不需要外部 CA。
- **面板必须能被所有节点访问**。面板有一个"对外地址"设置（自动检测，可修改），安装命令和节点连接都使用这个地址。面板在 NAT 后面时，需要用户做端口转发。
- 控制面**不依赖** WireGuard mesh：国内与海外之间跨境时，原生 WireGuard（UDP）不可靠，而普通的 TCP + TLS 连接通常可用。如果跨境环境下高位端口受限，可以在用 `--no-agent` 启动、因而没有 Caddy 的面板机器上，用 `--port 443` 把面板端口指定为 443。

## 信任的面板列表

每个节点维护一份**信任的面板列表**，记录面板的地址和公钥指纹。节点会主动连接列表里的面板。

**一个节点同一时间只归一个面板管理**：项目配置以面板为准，两个面板同时管理同一个节点就会有两份配置。列表里只在移交的过程中短暂出现两个面板（新面板登记完成、旧面板移除自己之前），这期间新面板只能查看。

**修改列表只有两条路：**

1. **由已信任的面板发指令**：已经被信任的面板可以让节点加入或移除某个面板。新面板先生成一次性令牌，旧面板把新面板的地址、指纹和令牌发给节点，节点连上新面板，用令牌完成登记，流程和节点首次加入一样。
2. **在节点上用 root 执行本地命令**：用于旧面板已经挂掉、无法再发指令的情况。能登录节点 root 的人本来就拥有这台机器，这条路不会降低安全性。

没有其他方式能让节点信任一个新面板，别人无法冒充面板接管节点。

**常见操作都由这个机制组合而成：**

| 操作 | 做法 |
| --- | --- |
| 移交给另一个面板 | 旧面板把新面板加进列表，再把自己移除 |
| 旧面板已挂，换面板 | 在节点上执行本地命令，把新面板加进列表、把旧面板移除 |

新面板接管节点后，按节点上报的配置缓存把项目拼回来（见 [panel.md](panel.md#项目数据)），旧面板不用导出什么。

### 接入码

换面板时通常要把很多节点一起搬过去，所以新面板生成的是**接入码**：把新面板的对外地址、公钥指纹和一个加入令牌打包成一段文本（`nagi-invite:...`）。令牌 1 小时内可以给多个节点用，面板上能看到每个接入码已经用了几次，也可以提前作废。普通的"添加节点"安装命令仍然用一次性令牌。

接入码可以多次使用，还要经过旧面板（可能是另一个人管理的）转交，泄露了别人也能拿它加入自己的节点。所以**用接入码加入的节点要在新面板上批准**：节点页显示"待批准"，批准之前它不进 mesh、拿不到告警配置、不采用它上报的配置缓存，也不能对它做任何操作。已经批准过的节点重新加入不用再批准。

**在旧面板上操作（移交）**：粘贴接入码，勾选节点。节点加入新面板后，旧面板把自己从节点的信任列表移除，并忘记这些节点和只在这些节点上的项目（拒绝再连接）。

- **按整个项目移交**：项目的容器分布在几个节点上，所以勾选的节点必须包含所选项目的全部容器所在的节点（以及它们的顶替节点、备份节点、作为见证人的节点）。有项目只有一部分在勾选的节点上时拒绝，并列出缺了哪些节点。界面上可以按项目勾选，自动带上相关的节点。
- **见证人**：见证人是旧面板的顶替，移交前先把见证人换成新面板（见 [failover.md](failover.md#实现)）。

旧面板对每个节点依次调用 `AddPanel`（节点用令牌向新面板登记，和首次加入一样），再调用 `RemovePanel` 移除自己。节点已经信任这个面板时只更新地址，不消耗令牌；而且只能由这个面板自己更新，一个面板不能改另一个面板的地址（否则能把它改成连不上的地址，悄悄锁在外面）。

### 在节点上操作

旧面板已经挂了时：

```
nagi panel list
nagi panel add <接入码>            # 也可以用 --server、--fingerprint、--token
nagi panel remove <地址或指纹>      # 移除最后一个面板需要 --force
```

面板自带的节点数据在 `<面板数据目录>/agent`，执行时加 `--data-dir /var/lib/nagi/agent`。

### 节点怎么应用修改

- 两条路都只修改 `identity/panels.json`。修改时先读文件里的最新内容再写回，节点进程和本地命令不会互相覆盖。
- 运行中的节点每 10 秒重新读一次信任列表（面板发指令时立即读），按列表增减连接：新面板开始连接，被移除的面板断开连接，并删除它下发的告警配置。
- 面板移除的是它自己时，节点先返回响应，1 秒后再断开。
- 一个面板移除另一个面板时，节点发一条告警（被移除的面板之后连不上这个节点，自己不会知道）。
- **信任的面板之间没有隔离**：被信任的面板能对节点做任何事（包括升级节点的程序），所以只信任自己管理的面板。
- **不能通过面板移除最后一个面板**，避免节点失去管理；本地命令加 `--force` 可以。一个面板都不信任的节点照常运行容器，等用 `nagi panel add` 加入面板后自动连接，新面板从它的缓存拼回项目。
- 每次重连都读取信任列表里的最新条目，所以证书续期、地址修改在下次重连时生效。
- 断开后按 1、2、4、8、10 秒的间隔重连（最长 10 秒，加最多 20% 的随机等待）。上限不能太长：面板重启以后，节点要等下一次重连才回来，这期间界面上的项目都显示节点离线。
- 面板自带的节点只在第一次启动（还没有信任任何面板）时自动加入本面板。移交给别的面板之后，面板重启也不会把它加回来。

## 节点加入流程

1. **面板生成一次性令牌**，1 小时内有效，用一次就作废。面板给出一行安装命令，大致形如：

   ```
   curl --pinnedpubkey "sha256//<面板公钥指纹>" -k https://<地址:端口>/install.sh \
     | sh -s -- --token <令牌>
   ```

   面板是自签证书，所以用 `-k` 跳过 CA 校验，真正的校验靠 `--pinnedpubkey` 钉住面板公钥，中间人无法冒充。
2. **安装脚本检查环境并下载 nagi**：`/install.sh` 由面板动态生成，写好了面板地址和公钥指纹。脚本检查是否为 Linux、root、是否已安装 Docker 和 compose 插件（2.24 或更新版本），不满足就提示用户先安装，不自动安装 Docker。然后从面板的 `/download/nagi-linux-<架构>` 下载 nagi 二进制（同样钉住公钥），执行 `nagi enroll` 完成加入，再安装为 systemd 服务（`nagi agent`）。令牌只用于加入，不写进服务配置。没有 systemd 时提示用户自行运行。不依赖 GitHub，国内节点也能快速下载。
   - 面板提供的二进制：优先用面板数据目录 `binaries/nagi-linux-<架构>`；没有时，如果面板自己就是这个架构的 Linux 版本，直接提供面板自身。面板和节点架构不同时，需要把对应架构的 nagi 放到 `binaries/` 下。
3. **agent 在本地生成两对密钥**：身份密钥和 WireGuard 密钥。私钥都不离开节点。mesh 地址由 WireGuard 公钥直接算出，不需要分配（见 [mesh.md](mesh.md#地址)）。
4. **agent 调用面板的 Enroll 接口**，提交令牌、身份公钥（CSR）和 WireGuard 公钥。
5. **面板先校验请求**（证书签名请求的签名、WireGuard 公钥没有被别的节点用过），**再校验令牌并作废**，然后签发证书，返回节点 ID、证书和 CA。用安装命令（一次性令牌）加入的节点直接可用；用接入码加入的要批准（见[接入码](#接入码)）。
   - 面板记下节点的 WireGuard 公钥。节点之后上报的 mesh 信息里公钥不一致就不采用：一个节点不能冒用别的节点的公钥，抢走它经面板的中转。
6. **agent 写入信任列表**，启动 WireGuard，与面板建立长连接。之后每次上报时面板在响应里返回 mesh 成员列表，其他节点下次上报（最多 15 秒）就知道新节点了。

**证书有效期**：节点的客户端证书有效期 1 年。节点连上面板时，如果证书 30 天内到期就自动续期（私钥不变，面板校验证书签名请求里的公钥属于这个节点），新证书下次连接时生效。面板另外维护一份已移除节点的名单，名单上的节点即使证书未过期也立即拒绝连接。

**移除节点**：节点上还有容器时不能移除，先把容器迁移走或删除。面板忘记这个节点并把它加入已移除名单。

**单机模式**：`nagi server` 内嵌的 agent 在本机自动完成以上流程，不需要令牌和安装命令。

## 接口设计

**连接结构**：

```
浏览器 ──HTTPS──┐
               ├─► 面板端口 ──按 TLS ALPN 分流──┬─ 浏览器：Web UI + Connect-RPC + WebSocket
agent ──TLS────┘                               └─ agent：yamux 多路复用
                                                     ├─ agent 调面板：PanelService
                                                     └─ 面板调 agent：AgentService（反向 gRPC）
```

agent 主动连上面板后，在同一条 TLS 连接上用 yamux 复用出多条通道。agent 照常调用面板的接口；同时 agent 在这条连接上反过来充当 gRPC 服务端，面板像调用普通接口一样调用 agent。这样每个操作都是独立的强类型接口，日志和终端就是普通的流式接口，以后加功能只需加一个方法。

**服务划分**：

| 服务 | 调用方向 | 主要方法 |
| --- | --- | --- |
| EnrollService | agent → 面板（尚无证书时） | `Enroll`：用令牌换证书 |
| PanelService | agent → 面板 | `Report`：上报节点和容器的最新状态和 mesh 信息（刚连上新面板时也带上配置缓存），响应里带 mesh 成员列表（连上时、有变化时、每 15 秒）；`RenewCertificate`：续期证书；`RelayAlert`：请面板代发告警；`MeshRelay`：mesh 的 TLS 中转通道 |
| AgentService | 面板 → agent（反向 gRPC） | 容器：同步配置缓存、部署、回滚、快照、迁移、顶替设置、删除；项目内网：代理名单；观察：日志（服务端流）、终端（双向流）、查询历史指标；节点：修改信任列表、项目根目录、镜像加速、告警配置、升级 |
| MeshService | agent ↔ agent / 面板，经 WireGuard，直接连对方的 mesh 地址 | 连通测试；租约投票；快照同步给顶替节点或备份节点；容器文件上传（面板 → 节点，客户端流）；容器之间的连接另走 7001 端口（见 [mesh.md](mesh.md#mesh-上的服务)） |

文件上传走 mesh，大文件不占用控制连接，管理操作不会被上传卡住。mesh 直连不通时，WireGuard 流量会自动经面板中转（UDP 或控制连接）。mesh 上的 gRPC 不再加 TLS：WireGuard 已经加密并认证了对方的公钥，调用方身份由来源 mesh 地址确定，每个调用都要校验调用方是否有权限（见 [mesh.md](mesh.md)）。

**浏览器与面板**：用 Connect-RPC，和节点共用同一套 proto 定义，自动生成 TypeScript 类型；也支持普通 JSON，可以用 curl 调用。终端这类双向交互用 WebSocket，由面板桥接到 `AgentService` 的终端接口。

**版本兼容**：

- proto 只加字段，不修改、不删除已有字段。
- 面板兼容比自己旧一个大版本的节点，升级面板时节点不用同时停。
- 节点之间（顶替、备份节点、迁移）同步容器时带上容器目录的格式版本号，对方不认识就拒绝并告警（见 [agent.md](agent.md#容器目录)）。所以升级时先升级热备和备份节点，再升级容器所在的节点。
- 面板上可以一键把节点升级到同一版本，二进制从面板下载。节点版本和面板不一样时界面上提示可以升级（面板在设置里返回自己的版本）。面板按节点的架构找到要提供的二进制（数据目录 `binaries/nagi-linux-<架构>`，没有时用面板自身），把 SHA-256 发给节点；节点钉住面板公钥从 `/download/` 下载、核对 SHA-256、试运行一次 `version` 确认能在本机运行，再替换自己的可执行文件，然后原地重启（`exec`，进程号不变，systemd 和容器里都适用）。项目容器由 Docker 运行，不受影响；内嵌的 Caddy 会中断一两秒。面板自带的节点和面板是同一个二进制，随面板一起升级，不能单独升级。
