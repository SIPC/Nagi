# 控制面

控制面是面板与节点之间的管理通道。

## 连接

- agent 通过 **mTLS** 连接信任列表中面板的**面板端口**，这是唯一的控制通道，方向永远是 agent → 面板，节点无需为控制面暴露任何入站端口。
- 面板不占用 80/443，这两个端口留给 Caddy。单机模式下面板和内嵌 agent 因此不会冲突。
- 面板首次启动时生成自签 CA。agent 用面板的公钥指纹校验面板身份，不需要域名，也不需要外部 CA。
- **面板必须能被所有节点访问**。面板有一个"对外地址"设置（自动检测，可在设置页的「面板访问」里修改），安装命令和节点连接都使用这个地址。修改以后面板把新地址告诉在线的节点（`AddPanel`，节点只接受面板改它自己的地址，不需要令牌），节点下次重连时使用；当时离线的节点要在节点上用 `nagi panel add` 更新。面板在 NAT 后面时，需要用户做端口转发。
- 控制面**不依赖** WireGuard mesh：国内与海外之间跨境时，原生 WireGuard（UDP）不可靠，而普通的 TCP + TLS 连接通常可用。如果跨境环境下高位端口受限，可以在用 `--no-agent` 启动、因而没有 Caddy 的面板机器上，用 `--port 443` 把面板端口指定为 443。

## 信任的面板列表

每个节点维护一份**信任的面板列表**，记录面板的地址和公钥指纹。节点会主动连接列表里的面板。

**一个节点同一时间只归一个面板管理**：项目配置以面板为准，两个面板同时管理同一个节点就会有两份配置。例外是同一个面板的主备面板（见 [standby.md](standby.md)）：它们共用一份数据，节点只执行当前主面板（任期最大的）发来的修改，备用面板只能查询。除此之外，列表里只在移交的过程中短暂出现两个面板（新面板登记完成、旧面板移除自己之前），这期间新面板只能查看。

**修改列表只有两条路：**

1. **由已信任的面板发指令**：已经被信任的面板可以让节点加入或移除某个面板。新面板先生成一次性令牌，旧面板把新面板的地址、指纹和令牌发给节点，节点连上新面板，用令牌完成登记，流程和节点首次加入一样。
2. **在节点上用 root 执行本地命令**：用于旧面板已经挂掉、无法再发指令的情况。能登录节点 root 的人本来就拥有这台机器，这条路不会降低安全性。

没有其他方式能让节点信任一个新面板，别人无法冒充面板接管节点。

**常见操作都由这个机制组合而成：**

| 操作 | 做法 |
| --- | --- |
| 移交给另一个面板 | 旧面板把新面板加进列表，再把自己移除 |
| 旧面板已挂，换面板 | 在节点上执行本地命令，把新面板加进列表、把旧面板移除 |

新面板接管节点后，按节点上报的配置缓存把项目拼回来（见 [panel.md](panel.md#项目数据)），旧面板不用导出什么。

### 接入码

换面板时通常要把很多节点一起搬过去，所以新面板生成的是**接入码**：把新面板的对外地址、公钥指纹和一个加入令牌打包成一段文本（`nagi-invite:...`）。令牌 1 小时内可以给多个节点用，最多加入 20 次（`inviteMaxUses`，达到上限后加入被拒绝，提示令牌已失效），面板上能看到每个接入码已经用了几次，也可以提前作废。普通的"添加节点"安装命令仍然用一次性令牌。

接入码可以多次使用，还要经过旧面板（可能是另一个人管理的）转交，泄露了别人也能拿它加入自己的节点。所以**用接入码加入的节点要在新面板上批准**：节点页显示"待批准"，批准之前它不进 mesh、拿不到告警配置、面板不代发它的本地审计、不采用它上报的配置缓存，也不能对它做任何操作。已经批准过的节点重新加入不用再批准。
- 节点名称用节点提交的主机名，按改名的规则处理：去掉控制字符和不可见字符（零宽空格、双向控制符、变体选择符、还没分配的码位、非字符等），各种空格换成普通空格，连续的空格合成一个，最多 64 个字符（截断后再去掉末尾的空格），空的用节点 ID；和别的节点重名时自动加后缀（`-2`、`-3`……），不拒绝，免得正常加入失败。拿到接入码的人因此没法让列表里出现两个同名的「待批准」，诱使管理员批准他的那台。重名按「骨架」比较，只用于判断、不改显示的名称：先做 NFKD（全角字母数字、数学字母、组合方式不同的带附加符号的字母都变成一样的写法），再把西里尔、希腊字母里和拉丁字母、数字长得一样的（例如西里尔字母的 а 和拉丁字母的 a）以及几个和连字符形近的标点换成拉丁字母和 `-`（表在 `api/node_skeleton.go`，注释里写了覆盖范围）。表里没有的形近字（例如拉丁字母的 l 和数字 1、切罗基字母）仍不算重名，批准前以节点 ID 和来源地址为准。移除过的节点重新加入时沿用原来的名称，同样按这些规则处理，移除期间有别的节点用了同样的名称时加后缀。待批准节点的详情里显示节点 ID 和来源地址；来源地址是面板看到的连接地址，不采用节点上报的内容（从本机连来的显示面板的对外地址）。
- 加入通知：同一个接入码第一次加入立即通知，之后 10 分钟内的加入合成一条（还有几个节点、前 10 个的名称和来源地址），审计里每次加入照样各记一条。

待批准的节点同时在线的控制连接全局最多 16 条、同一来源（IPv4 地址，IPv6 按 /64）最多 4 条，超出的新连接直接拒绝，节点按退避重连；已批准的节点不受限制。一次搬很多节点时，没连上的在节点页显示为离线，照样可以批准，批准以后马上连上。

**在旧面板上操作（移交）**：粘贴接入码，勾选节点（一次最多 20 个，和接入码的加入次数上限一致，多了分批、每批用新的接入码）。节点加入新面板后，旧面板把自己从节点的信任列表移除，并忘记这些节点和只在这些节点上的项目（拒绝再连接）。

- **按整个项目移交**：项目的容器分布在几个节点上，所以勾选的节点必须包含所选项目的全部容器所在的节点（以及它们的顶替节点、备份节点、作为见证人的节点）。有项目只有一部分在勾选的节点上时拒绝，并列出缺了哪些节点。界面上可以按项目勾选，自动带上相关的节点。
- **见证人**：见证人是旧面板的顶替，旧面板没法替新面板登记见证人，所以由新面板在拼回项目以后自动把见证人换成自己（见 [failover.md](failover.md#实现)）。这期间 A、B 两票照常构成多数。
- **mesh 不断**：新面板批准节点之前不给它 mesh 成员列表，节点先留着旧面板给的列表；新面板给了列表以后，旧面板的成员再留 2 分钟（新面板刚接管时，其他节点可能还没上报地址）。所以移交过程中节点之间照常联系，顶替续约、项目内网不受影响。

旧面板对每个节点依次调用 `AddPanel`（节点用令牌向新面板登记，和首次加入一样），再调用 `RemovePanel` 移除自己。节点已经信任这个面板时只更新地址，不消耗令牌；而且只能由这个面板自己更新，一个面板不能改另一个面板的地址（否则能把它改成连不上的地址，悄悄锁在外面）。

### 在节点上操作

旧面板已经挂了时：

```
nagi panel list
nagi panel add <接入码>            # 也可以用 --server、--fingerprint、--token
nagi panel remove <地址或指纹>      # 移除最后一个面板需要 --force
```

面板自带的节点数据在 `<面板数据目录>/agent`，执行时加 `--data-dir /var/lib/nagi/agent`。

### 节点怎么应用修改

- 两条路都只修改 `identity/panels.json`。修改时先读文件里的最新内容再写回，节点进程和本地命令不会互相覆盖。
- 运行中的节点每 10 秒重新读一次信任列表（面板发指令时立即读），按列表增减连接：新面板开始连接，被移除的面板断开连接，并删除它下发的告警配置。
- 面板移除的是它自己时，节点先返回响应，1 秒后再断开。节点处理每个请求前都查一次信任列表，断开之前的这段时间里，被移除的面板查询也会被拒绝。
- 一个面板移除另一个面板时，节点发一条告警（被移除的面板之后连不上这个节点，自己不会知道）。
- **信任的面板之间没有隔离**：被信任的面板能对节点做任何事（包括升级节点的程序），所以只信任自己管理的面板。
- **不能通过面板移除最后一个面板**，避免节点失去管理；本地命令加 `--force` 可以。一个面板都不信任的节点照常运行容器，等用 `nagi panel add` 加入面板后自动连接，新面板从它的缓存拼回项目。
- 每次重连都读取信任列表里的最新条目，所以证书续期、地址修改在下次重连时生效。
- 断开后按 1、2、4、8、10 秒的间隔重连（最长 10 秒，加最多 20% 的随机等待）。上限不能太长：面板重启以后，节点要等下一次重连才回来，这期间界面上的项目都显示节点离线。
- 面板自带的节点只在第一次启动（还没有信任任何面板）时自动加入本面板。移交给别的面板之后，面板重启也不会把它加回来。

## 节点加入流程

1. **面板生成一次性令牌**，1 小时内有效，用一次就作废。面板给出一行安装命令，大致形如：

   ```
   curl --pinnedpubkey "sha256//<面板公钥指纹>" -k "https://<地址:端口>/install.sh?k=<钥匙>" \
     | NAGI_TOKEN=<令牌> sh -s --
   ```

   面板是自签证书，所以用 `-k` 跳过 CA 校验，真正的校验靠 `--pinnedpubkey` 钉住面板公钥，中间人无法冒充。
   安装脚本里写着面板的地址和指纹，所以只给带着钥匙的请求：钥匙由这个令牌的哈希再算一次哈希得出（`installKey`），令牌用掉或过期以后脚本就取不到了，不带钥匙、钥匙不对一律 404。钥匙算不回令牌，出现在 curl 的参数里也不能拿来加入节点。接入码不经过安装脚本，只有接入码可用时不提供。
   令牌用环境变量 `NAGI_TOKEN` 传给脚本，脚本再用环境变量传给 `nagi enroll`，不出现在进程参数里：安装要几分钟，同一台机器上的任何用户都能读别的进程的参数（`/proc/<pid>/cmdline`），抢先用令牌加入自己的机器；环境变量只有 root 能读。脚本读完就清掉这个变量，不传给 Docker 安装脚本等子进程。旧面板生成的 `sh -s -- --token <令牌>` 和 `nagi enroll --token` 仍然能用。命令要以 root 执行，不能写成 `… | NAGI_TOKEN=<令牌> sudo sh -s --`：sudo 默认不传环境变量，脚本拿不到令牌（提示里会说明，先 `sudo -i` 再粘贴）；root 的 shell 是 csh 这类不支持 `变量=值 命令` 写法的，先执行 `sh` 再粘贴。末尾的 `-s --` 让用户能接着追加 `--download-url` 等选项。
2. **安装脚本检查环境并下载 nagi**：`/install.sh` 由面板动态生成，写好了面板地址和公钥指纹。脚本检查是否为 Linux、root。没有 Docker 时用官方脚本 get.docker.com 自动安装（`--docker-mirror Aliyun` 等传给它的 `--mirror`），compose 插件缺失或低于 2.24 时单独安装（先用包管理器的 `docker-compose-plugin`，不行再从 GitHub 下载到 `/usr/local/lib/docker/cli-plugins`）；这部分与面板安装脚本 `scripts/install.sh` 共用（`install.go` 的 `sharedScript`，有测试检查两边一致）。然后从和面板同一版本的 GitHub Release 下载 `nagi-linux-<架构>`，按同一处的 `SHA256SUMS` 校验（下载和校验也在共用代码里，`download_nagi`），安装到 `/usr/local/bin/nagi` 并在 `/usr/bin` 下建链接、安装 bash 补全，执行 `nagi enroll`（令牌在环境变量里）完成加入，再安装为 systemd 服务（`nagi agent`）。令牌只用于加入，不写进服务配置。没有 systemd 时提示用户自行运行。
   - **面板不提供二进制**：节点安装和一键升级都从 GitHub Release（或镜像）下载。面板不是正式版本（本地编译的 `dev`）时从最新发布的版本下载，脚本提示版本不一致。v0.1.0 的节点一键升级要从面板下载，v0.28.0 起面板不再提供，这样的节点要在节点上重新执行安装脚本升级。
   - **镜像**：无法访问 GitHub 时在安装命令末尾加 `--download-url <地址>`（或环境变量 `NAGI_DOWNLOAD_URL`），该地址下要有 `nagi-linux-<架构>` 和 `SHA256SUMS`。脚本把它记在 `<节点目录>/identity/download-url`，之后一键升级也只从这里下载。镜像里的 nagi 低于 v0.35.0 时不读环境变量里的令牌，脚本下载后发现版本过旧就停下，提示更新镜像。
   - **加速代理**：检测到中国大陆网络时经 GitHub 加速代理下载，用上的代理记在 `<节点目录>/identity/github-proxy`。一键升级先经它下载，不行再直接连 GitHub、依次换内置的代理，成功的记下来；能连上 GitHub 时代理的文件都要和 GitHub 上的 `SHA256SUMS` 一致（见 [panel.md](panel.md#更新面板)）。
3. **agent 在本地生成两对密钥**：身份密钥和 WireGuard 密钥。私钥都不离开节点。mesh 地址由 WireGuard 公钥直接算出，不需要分配（见 [mesh.md](mesh.md#地址)）。
4. **agent 调用面板的 Enroll 接口**，提交令牌、身份公钥（CSR）和 WireGuard 公钥。
5. **面板先校验请求**（证书签名请求的签名、WireGuard 公钥没有被别的节点用过），**再校验令牌并作废**，然后签发证书，返回节点 ID、证书和 CA。节点 ID 由节点的身份公钥算出，写在证书里；节点连上来时面板核对证书里的 ID 和证书的公钥对得上，拿着 CA 私钥（例如被移除的备用面板）也冒充不了已有的节点。用安装命令（一次性令牌）加入的节点直接可用；用接入码加入的要批准（见[接入码](#接入码)）。节点加入的通知在标题里写来源地址，正文写节点 ID：令牌被别人抢先用掉时，管理员能看出加入的不是自己的机器。
   - 面板记下节点的 WireGuard 公钥。节点之后上报的 mesh 信息里公钥不一致就不采用：一个节点不能冒用别的节点的公钥，抢走它经面板的中转。
6. **agent 写入信任列表**，启动 WireGuard，与面板建立长连接。之后每次上报时面板在响应里返回 mesh 成员列表，其他节点下次上报（最多 15 秒）就知道新节点了。

**证书有效期**：节点的客户端证书有效期 1 年。节点连上面板时，如果证书 30 天内到期就自动续期（私钥不变，面板校验证书签名请求里的公钥属于这个节点），新证书下次连接时生效。面板另外维护一份已移除节点的名单，名单上的节点即使证书未过期也立即拒绝连接。

**节点名称**：加入时用节点的主机名（去掉控制字符和不可见字符，最多 64 个字符，重名时加后缀，见[接入码](#接入码)），之后可以在节点页重命名（`RenameNode`）。名称只存在面板上，不改节点本机的主机名；连续的空格合成一个，不能包含控制字符、不可见字符和还没分配的码位，不能和别的节点重名（按骨架比较，和看得到的节点形近也算重名，报「名称与节点 X 过于相似」，见[接入码](#接入码)）。升级前存下的、不合现在规则的名称，主面板启动时整理一次（去掉不可见字符、合并空格、截短，整理后重名的加后缀，已经合规的名称优先保留），改了的节点各记一条操作者是系统的「重命名节点」审计。在线的节点改名后，mesh 成员列表里的名字随下一次上报更新。顶替设置、副本里记的是设置时的名字，界面按节点 ID 显示当前的名字。面板下发告警配置时带上节点的名称（`AlertConfig.node_name`，改名后立即重发，离线的节点连上时发），节点自己发出的告警用它，和界面一致；没有时（旧版本的面板）用主机名。

**移除节点**：节点上还有容器时不能移除，先把容器迁移走或删除。面板忘记这个节点并把它加入已移除名单。

**单机模式**：`nagi server` 内嵌的 agent 在本机自动完成以上流程，不需要令牌和安装命令。

## 接口设计

**连接结构**：

```
浏览器 ──HTTPS──┐
               ├─► 面板端口 ──按 TLS ALPN 分流──┬─ 浏览器：Web UI + Connect-RPC + WebSocket
agent ──TLS────┘                               └─ agent：yamux 多路复用
                                                     ├─ agent 调面板：PanelService
                                                     └─ 面板调 agent：AgentService（反向 gRPC）
```

agent 主动连上面板后，在同一条 TLS 连接上用 yamux 复用出多条通道。agent 照常调用面板的接口；同时 agent 在这条连接上反过来充当 gRPC 服务端，面板像调用普通接口一样调用 agent。这样每个操作都是独立的强类型接口，日志和终端就是普通的流式接口，以后加功能只需加一个方法。

**服务划分**：

| 服务 | 调用方向 | 主要方法 |
| --- | --- | --- |
| EnrollService | agent → 面板（尚无证书时） | `Enroll`：用令牌换证书 |
| PanelService | agent → 面板 | `Report`：上报节点和容器的最新状态和 mesh 信息（刚连上新面板时也带上配置缓存），响应里带 mesh 成员列表（连上时、有变化时、每 15 秒）；`RenewCertificate`：续期证书；`RelayAlert`：请面板代发告警；`MeshRelay`：mesh 的 TLS 中转通道 |
| AgentService | 面板 → agent（反向 gRPC） | 容器：同步配置缓存、部署、回滚、快照、迁移、顶替设置、删除；项目内网：代理名单；观察：日志（服务端流）、终端（双向流）、查询历史指标；节点访问：节点终端（双向流）、节点文件（见 [node-access.md](node-access.md)）；节点：修改信任列表、项目根目录、镜像加速、告警配置、升级 |
| MeshService | agent ↔ agent / 面板，经 WireGuard，直接连对方的 mesh 地址 | 连通测试；租约投票；快照同步给顶替节点或备份节点；容器文件上传（面板 → 节点，客户端流）；容器之间的连接另走 7001 端口（见 [mesh.md](mesh.md#mesh-上的服务)） |

文件上传和存储标签的文件下载、上传都走 mesh，大文件不占用控制连接，管理操作不会被上传卡住。mesh 直连不通时，WireGuard 流量会自动经面板中转（UDP 或控制连接）。mesh 上的 gRPC 不再加 TLS：WireGuard 已经加密并认证了对方的公钥，调用方身份由来源 mesh 地址确定，每个调用都要校验调用方是否有权限（见 [mesh.md](mesh.md)）。

**浏览器与面板**：用 Connect-RPC，和节点共用同一套 proto 定义，自动生成 TypeScript 类型；也支持普通 JSON，可以用 curl 调用。终端这类双向交互用 WebSocket，由面板桥接到 `AgentService` 的终端接口。

**版本兼容**：

- proto 只加字段，不修改、不删除已有字段。
- 面板兼容比自己旧一个大版本的节点，升级面板时节点不用同时停。预发布版的面板（`vX.Y.0-pre.N`）同样要能管理上一个正式版的节点，正式版渠道的节点不会被升级到预发布版（见 [development.md](development.md#预发布版本)）。
- 节点之间（顶替、备份节点、迁移）同步容器时带上容器目录的格式版本号，对方不认识就拒绝并告警（见 [agent.md](agent.md#容器目录)）。所以升级时先升级热备和备份节点，再升级容器所在的节点。
- 面板上可以一键把节点升级到和面板同一版本，也可以在节点页逐个升级全部节点（见 [panel.md](panel.md#更新状态)）。每个节点有自己的更新渠道，面板是预发布版时只有预发布渠道的节点能升级到它（见 [development.md](development.md#预发布版本)）。节点版本和面板不一样时界面上提示可以升级（面板在设置里返回自己的版本）。面板把自己的版本号发给节点（`UpgradeRequest.version`；面板不是正式版本时拒绝）；节点从这个版本的 GitHub Release（安装时指定了镜像就只从镜像；GitHub 连不上或太慢时经加速代理，地址的顺序、换地址和校验的规则见 [panel.md](panel.md#更新面板)：能连上 GitHub 时先取 GitHub 上的 `SHA256SUMS`，代理的文件必须和它一致，GitHub 上没有这个版本时不升级）下载，按 `SHA256SUMS` 核对、试运行一次 `version` 确认能在本机运行且版本对得上（镜像地址不分版本，里面放的可能不是要求的版本），再替换自己的可执行文件，然后原地重启（`exec`，进程号不变，systemd 和容器里都适用）。项目容器由 Docker 运行，不受影响；内嵌的 Caddy 会中断一两秒。下载、核对、试运行期间节点记下最新的进度（阶段、下载地址、已下载和总大小），面板通过 `UpgradeProgress` 每秒问一次，显示在界面上（见 [panel.md](panel.md#更新状态)）；没有在升级、已经开始替换时返回空的。面板自带的节点和面板是同一个二进制，随面板一起[更新](panel.md#更新面板)，不能单独升级。
- **升级后自检，起不来就换回**：试运行 `version` 只能说明新版本在这台机器上跑得起来，正式启动时仍可能出错（迁移节点数据失败、启动时崩溃、连不上面板）。所以替换前把当前版本留成 `<可执行文件>.old`（同一个文件系统上用硬链接，不行时复制），并在 `identity/upgrade-pending.json` 里记下从哪个版本升到哪个版本（`agent/upgrade_guard.go`）。新版本启动时最先检查这条记录，连上面板才算升级完成并删掉它；连续启动 3 次都在 2 分钟内退出、没有连上（反复崩溃，systemd 一直在拉起），就把 `.old` 换回来原地重启。只是连不上面板不换回，只记日志、继续重试：能挡住节点和面板之间连接的人（网络中间人、对面板的拒绝服务），不能借此让节点退回有漏洞的旧版本。启动后撑过 2 分钟就不算崩溃，启动次数清零，之后连上面板时照常算升级完成。节点上报进程的启动时间（`NodeInfo.started_at`），面板看到节点在替换之后又起来了、版本却还是旧的，马上记为升级失败（「新版本没能在节点上正常运行，节点已自动回到 …」），不再等 3 分钟；一键升级全部节点时随之停下。`.old` 留到下一次升级，需要时也可以手动换回。这一套要两边都支持：做替换的旧版本负责留下 `.old` 和记录，新版本负责自检，所以从 v0.29.1 往后的升级才有。在 Docker 的 Debian 容器里实测过两种情况：每次启动 3 秒后被杀掉，第 4 次启动时换回；一直连不上面板，不换回，连上后升级完成。
