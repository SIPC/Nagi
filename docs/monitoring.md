# 监控与告警

## 指标

| 来源 | 指标 |
| --- | --- |
| 节点 | CPU、内存、磁盘、网络 |
| 容器 | CPU、内存、网络、重启次数 |
| 健康检查 | compose 中 healthcheck 的结果 |
| Caddy | 请求数、错误率、延迟（所有对外流量都经过 Caddy，采集很容易） |

## 存储

- **存在节点本地**（节点 SQLite），面板按需查询。面板挂了历史数据也不丢，面板机器不会因为节点多而变重。面板只缓存最新状态，用于总览页面。
- **保留时长**：最近 24 小时每 10 秒一个点，用来排查故障；30 天内每 5 分钟一个点，用来看趋势。每个节点大约占几十 MB。
- **表**：节点数据库里的 `metrics_raw`（10 秒）和 `metrics_m5`（5 分钟平均）。采集器每 10 秒写一次，把已经过去的 5 分钟窗口降采样，并删除过期数据。
- **查询**：面板调用节点的 `QueryMetrics`，按序列名前缀和时间范围查。范围在 24 小时以内用 10 秒精度，更长用 5 分钟精度。可以带聚合步长 `step`（秒）：节点把每条序列按步长合并，时间取窗口起点（各节点对齐，可以直接相加），`:p95`、`:p99` 取窗口内的最大值，其余取平均值。界面可选 1 小时、6 小时、24 小时、7 天、30 天，步长分别为 20 秒、2 分钟、10 分钟、1 小时、4 小时，每条序列不超过约 180 个点。

### 序列名

| 序列 | 含义 |
| --- | --- |
| `node:cpu`、`node:mem`、`node:disk` | 使用率（%）。磁盘是节点数据目录所在的文件系统 |
| `node:disk@<挂载点>` | 使用率（%）。容器目录所在、和节点数据目录不是同一块的磁盘（例如项目根目录 `/srv` 挂在数据盘上），按挂载点去重 |
| `node:mem_used`、`node:disk_free` | 字节 |
| `node:net_rx`、`node:net_tx` | 物理网卡收发速率（字节/秒），不算回环、Docker 网桥、veth、WireGuard |
| `c:<项目 ID>/<容器>/<服务>:cpu` | 容器 CPU（%，单核 100%）。同一服务的多个副本相加 |
| `c:<项目 ID>/<容器>/<服务>:mem` | 容器内存（字节） |
| `c:<项目 ID>/<容器>/<服务>:net_rx`、`:net_tx` | 容器网络（字节/秒） |
| `c:<项目 ID>/<容器>/<服务>:restarts` | 累计重启次数 |
| `l:<项目 ID>/<容器>:cpu`、`:mem` | 运行中的容器最多能用多少：CPU（%，单核 100%）、内存（字节）。设了限制（compose 的 `cpus`、`mem_limit`、`deploy.resources.limits`）按限制，没设按主机；容器组把各服务的限制加起来，有一个服务没设或加起来超过主机就按主机。界面上占用指示的满格 |
| `r:<项目 ID>/<规则名>:req`、`:2xx`、`:3xx`、`:4xx`、`:5xx` | http 规则的请求数及各类状态码的响应数（每秒）。1xx（如 WebSocket 升级）只计入 `req`。有过请求的规则之后没请求时记 0，一天没请求就不再记 |
| `r:<项目 ID>/<规则名>:in`、`:out` | 请求体、响应体的流量（字节/秒），不含头部 |
| `r:<项目 ID>/<规则名>:lat`、`:p50`、`:p95`、`:p99` | 平均耗时和耗时分位数（毫秒），只在有请求的采样点记录。分位数按每个采样间隔内的请求计算，请求超过 2048 个时等概率抽样 2048 个 |
| `m:<成员公钥的十六进制>:rx`、`:tx` | 和这个 mesh 成员（其他节点或面板）之间的收发速率（字节/秒），由 WireGuard 累计字节换算。计数器变小（对端重启）的那一轮不记 |
| `m:<成员公钥的十六进制>:rtt` | 到这个成员的延迟（毫秒），取直连保活 ping（每 10 秒一次）最近一次的往返时间。只在直连时记录，经面板中转时没有 |

### 节点上报的磁盘

节点每次上报时带上各磁盘的容量和用量（`NodeUsage.disks`），节点卡片显示它们的合计，悬停可以看到每块盘。统计本地块设备和 ZFS，同一块盘的多个挂载点只算一次（ZFS 按存储池算）；不算 loop、只读镜像、网络存储，以及启动分区、系统目录和容器运行时目录下的挂载。节点目录和项目目录所在的盘一定算在内。这份数据只用于显示，不保存历史；磁盘告警仍只看上面的 `node:disk` 和 `node:disk@<挂载点>`。

### Caddy 请求统计

只统计 http 规则（tcp/udp 没有状态码）。每条 http 规则先经过 `log_append`，在访问日志里加上 `nagi_route = <项目 ID>/<规则名>`。访问日志不输出到终端，只交给节点注册的 Caddy 日志输出模块 `nagi_metrics`，在进程内按规则累计请求数、各类状态码、请求体和响应体字节数（访问日志的 `bytes_read`、`size`）以及耗时样本，采集器每 10 秒取一次并算出分位数。容器没运行时返回的 502 也算 5xx。HTTP 跳转 HTTPS 的 308 和未匹配域名的 404 不算在任何规则里。统计记在收到请求的节点上：映射有其他入口节点时，界面也查询这些节点并汇总（见 [exposure.md](exposure.md#跨节点入口)）。

### 全局概览

面板的「概览」页（界面见 [ui.md](ui.md#布局)）汇总所有节点和容器的状态，并显示对外流量和节点之间的流量。所有流量数字和趋势都来自节点存的序列，刷新页面不丢，浏览器里不累积任何数据。

| 内容 | 来源 | 现状 |
| --- | --- | --- |
| 节点在线数、容器运行数、项目数 | 面板已有的节点和项目状态 | 已有，只需汇总 |
| 节点 CPU、内存、磁盘、网卡流量 | `node:*` | 已有，只需汇总 |
| 流量最大的端口映射 | `r:*`，只有 http 规则 | 已有，只需汇总排行 |
| 节点之间的流量 | `m:*` | 节点算好存下，按公钥对应到节点 |
| 对外流量 | `node:net_*` 减 `m:*` | 查询时按时刻相减 |

**节点之间**：节点把每个成员的累计字节换算成速率，存成 `m:<成员公钥>:rx`、`:tx`，沿用现有的保留策略。序列名用 mesh 公钥，因为节点只知道成员的公钥，不知道面板上的节点 ID；页面用 `GetNodeMesh` 返回的公钥对应到节点。两端都有记录，只取发送方的数，避免重复计算。面板也是 mesh 成员（经面板下载、上传节点上的文件走 mesh），但面板不存指标：节点发给面板的取节点的发送量，面板发给节点的取节点的接收量。面板的 mesh 公钥由 `GetPanelMesh` 得知；有本面板自带的节点（`Node.own_embedded`）时算到那台机器上，同时从它的对外流量里扣掉，否则单独显示为「面板」。

**对外流量**：`node:net_rx`、`node:net_tx` 统计物理网卡，已经不算回环、Docker 网桥、veth 和 WireGuard 网卡，但 WireGuard 封装后的 UDP 包仍走物理网卡，所以要减掉：

```
对外入站 = node:net_rx − 所有对端接收速率之和
对外出站 = node:net_tx − 所有对端发送速率之和
```

结果小于 0 时按 0 处理。这是估算值，界面上要注明：

- WireGuard 计数和网卡上看到的字节不完全一致（封装开销），有少量误差。
- 拉镜像、备份、节点和面板之间的控制连接也算在对外里。

**查询**：页面每 10 秒经面板查询各节点（`QueryNodeMetrics`），和节点页、项目页一样。延迟约 10 秒（采样间隔），不是逐秒。

**升级**：节点要升级后才有节点之间的数据和对外流量；旧节点在页面上标注需要升级，只显示已有的网卡流量。

## 告警

- **谁来判断和发送**：节点在本地判断，并直接发送告警，面板挂了告警照常能发出。"节点失联"由面板负责，因为节点自己挂了没法报告。
- **渠道**：通用 webhook 和 Telegram。在面板上配置，下发到节点。
- **发送失败时经面板转发**：有些节点访问不了告警渠道（例如国内节点访问不了 Telegram）。节点直接发送失败时，改为通过控制连接交给面板代发（面板填上节点名，节点给的文字限制长度、去掉控制字符，按纯文本发送）；面板也不可达时，先存在本地，恢复后补发。
- **默认规则**（阈值都可以修改）：
  - 节点失联
  - 磁盘使用超过 90%（节点数据目录和各容器目录所在的每一块盘分别判断）
  - 内存使用超过 90% 并持续 5 分钟
  - 容器 10 分钟内重启 3 次
  - 健康检查失败
  - 5xx 错误率超过 5%（最近 5 分钟，至少 20 个请求）
  - 证书申请失败，或证书 7 天内过期
  - 快照失败，或因暂停超过 30 秒而放弃
  - 同步到备份节点或热备失败
  - 顶替：续不上租约而停止容器、无法顶替（热备还没收到过同步）、有状态容器等待确认、顶替失败；已顶替、已被顶替是一次性通知
- **重复告警**：问题出现时发一次，恢复时发"已恢复"；一直没恢复就每 4 小时提醒一次。

### 实现

- **配置**：面板把渠道和规则存在 settings 表（键 `alert_config`），用主密钥加密，因为里面有 Telegram 令牌。节点连上时、配置修改时，面板调用节点的 `SetAlertConfig` 下发。节点按面板指纹分别保存在 `identity/alerts.json`（0600），面板挂了也能照常发。
- **判断**：节点每 30 秒判断一次。磁盘、内存看最新的采样；重启看时间窗口内累计重启次数的增量；健康检查看容器的 `unhealthy` 状态；证书读 Caddy 存储里已经拿到的证书的过期时间，只看还在用的域名（项目映射和面板域名；解绑以后留下的旧证书不算），跳过 Caddy 本地 CA 给 `.localhost` 等内部域名签的证书（有效期本来就只有几小时，自动续）；5xx 比例按最近 5 分钟的 `r:*:req`、`r:*:5xx` 计算，至少 20 个请求才判断（默认超过 5% 告警）。
- **事件类告警**：快照失败由定时快照报告，下一次成功时恢复；证书申请失败来自 Caddy 的 `cert_failed` 事件（节点注册了事件处理模块 `events.handlers.nagi`），拿到证书的 `cert_obtained` 事件时恢复。Caddy 会自己重试申请，重复的失败在 4 小时内只提醒一次。
- **渠道密钥在节点上**：面板挂了告警照常发，节点就必须自己拿着渠道的配置，包括 Telegram 机器人令牌和 webhook 地址。任何一个节点被攻破，这些就会泄露，所以告警最好用专门的机器人，不要和别的用途共用。
- **代发限流**：面板给每个节点代发告警，10 分钟内最多 30 条，防止被攻破的节点借面板的渠道刷屏。
- **代发与补发**：直接发送失败时，调用配置这个渠道的面板的 `RelayAlert` 代发；面板也不可达时存进 `identity/alerts-queue.json`（最多 200 条），每 30 秒重试。
- **节点失联**：面板每 15 秒检查一次。离线时间从"最后在线"和"面板启动"中较晚的那个算起，避免面板重启后节点还没来得及重连就报失联。
- **状态在内存里**：节点或面板重启后，还没恢复的问题会再提醒一次。
- **测试**：面板设置里可以给某个渠道发一条测试消息（由面板发送）。

### 消息格式

webhook 收到 POST JSON：

```json
{
  "status": "firing",
  "key": "disk",
  "title": "磁盘使用 93%，超过 90%",
  "message": "",
  "node": "node1",
  "project": "",
  "time": "2026-10-17T09:04:03Z",
  "text": "🔴 磁盘使用 93%，超过 90%
节点：node1
时间：..."
}
```

`status` 是 `firing`、`resolved`，或者一次性通知 `info`（例如"已顶替项目"，没有对应的恢复）；`key` 标识同一个问题，例如 `disk`、`mem`、`restart:c:<项目 ID>/<容器>/<服务>`、`health:<项目 ID>/<容器>/<服务>`、`cert:<域名>`、`errors:<项目 ID>/<规则名>`、`event:snapshot:<项目 ID>/<容器>`、`event:cert_failed:<域名>`、`event:backup:<项目 ID>/<容器>`、`event:standby:<项目 ID>/<容器>`、`event:lease:<项目 ID>/<容器>`、`event:takeover:<项目 ID>/<容器>`、`offline`。Telegram 收到的是 `text` 的内容。
