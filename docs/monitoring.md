# 监控与告警

## 指标

| 来源 | 指标 |
| --- | --- |
| 节点 | CPU、内存、磁盘、网络 |
| 容器 | CPU、内存、网络、重启次数 |
| 健康检查 | compose 中 healthcheck 的结果 |
| Caddy | 请求数、错误率、延迟（所有对外流量都经过 Caddy，采集很容易） |

## 存储

- **存在节点本地**（节点 SQLite），面板按需查询。和"数据在节点"一致：多面板不用同步，面板挂了历史数据也不丢，面板机器不会因为节点多而变重。面板只缓存最新状态，用于总览页面。
- **保留时长**：最近 24 小时每 10 秒一个点，用来排查故障；30 天内每 5 分钟一个点，用来看趋势。每个节点大约占几十 MB。
- **表**：节点数据库里的 `metrics_raw`（10 秒）和 `metrics_m5`（5 分钟平均）。采集器每 10 秒写一次，把已经过去的 5 分钟窗口降采样，并删除过期数据。
- **查询**：面板调用节点的 `QueryMetrics`，按序列名前缀和时间范围查。范围在 24 小时以内用 10 秒精度，更长用 5 分钟精度。

### 序列名

| 序列 | 含义 |
| --- | --- |
| `node:cpu`、`node:mem`、`node:disk` | 使用率（%）。磁盘是节点数据目录所在的文件系统 |
| `node:mem_used`、`node:disk_free` | 字节 |
| `node:net_rx`、`node:net_tx` | 物理网卡收发速率（字节/秒），不算回环、Docker 网桥、veth、WireGuard |
| `c:<项目 ID>/<成员>/<服务>:cpu` | 容器 CPU（%，单核 100%）。同一服务的多个副本相加 |
| `c:<项目 ID>/<成员>/<服务>:mem` | 容器内存（字节） |
| `c:<项目 ID>/<成员>/<服务>:net_rx`、`:net_tx` | 容器网络（字节/秒） |
| `c:<项目 ID>/<成员>/<服务>:restarts` | 累计重启次数 |
| `r:<项目 ID>/<规则名>:req`、`:5xx` | http 规则的请求数、5xx 响应数（每秒）。有过请求的规则之后没请求时记 0，一天没请求就不再记 |
| `r:<项目 ID>/<规则名>:lat` | 平均耗时（毫秒），只在有请求的采样点记录 |

### Caddy 请求统计

只统计 http 规则（tcp/udp 没有状态码）。每条 http 规则先经过 `log_append`，在访问日志里加上 `nagi_route = <项目 ID>/<规则名>`。访问日志不输出到终端，只交给节点注册的 Caddy 日志输出模块 `nagi_metrics`，在进程内按规则累计请求数、5xx 数和耗时，采集器每 10 秒取一次。容器没运行时返回的 502 也算 5xx。HTTP 跳转 HTTPS 的 308 和未匹配域名的 404 不算在任何规则里。

## 告警

- **谁来判断和发送**：节点在本地判断，并直接发送告警，面板挂了告警照常能发出。"节点失联"由面板负责，因为节点自己挂了没法报告。
- **渠道**：通用 webhook 和 Telegram。在面板上配置，下发到节点。多面板时，节点向所有信任面板配置的渠道发送，同一个渠道只发一次。
- **发送失败时经面板转发**：有些节点访问不了告警渠道（例如国内节点访问不了 Telegram）。节点直接发送失败时，改为通过控制连接交给面板代发；面板也不可达时，先存在本地，恢复后补发。
- **"节点失联"的重复**：多面板时每个面板都会各自发现节点失联并发送，可能收到重复的失联告警。面板之间不通信，这一点暂时接受。
- **默认规则**（阈值都可以修改）：
  - 节点失联
  - 磁盘使用超过 90%
  - 内存使用超过 90% 并持续 5 分钟
  - 容器 10 分钟内重启 3 次
  - 健康检查失败
  - 5xx 错误率超过 5%（最近 5 分钟，至少 20 个请求）
  - 证书申请失败，或证书 7 天内过期
  - 快照失败，或因暂停超过 30 秒而放弃
  - 发生顶替
- **重复告警**：问题出现时发一次，恢复时发"已恢复"；一直没恢复就每 4 小时提醒一次。

### 实现

- **配置**：面板把渠道和规则存在 settings 表（键 `alert_config`），用主密钥加密，因为里面有 Telegram 令牌。节点连上时、配置修改时，面板调用节点的 `SetAlertConfig` 下发。节点按面板指纹分别保存在 `identity/alerts.json`（0600），面板挂了也能照常发。
- **多面板合并**：渠道按目的地去重（同一个 webhook 地址、同一个 Telegram 机器人和聊天只发一次）；阈值取所有面板里最严格的。
- **判断**：节点每 30 秒判断一次。磁盘、内存看最新的采样；重启看时间窗口内累计重启次数的增量；健康检查看容器的 `unhealthy` 状态；证书读 Caddy 存储里已经拿到的证书的过期时间；5xx 比例按最近 5 分钟的 `r:*:req`、`r:*:5xx` 计算，至少 20 个请求才判断（默认超过 5% 告警）。
- **事件类告警**：快照失败由定时快照报告，下一次成功时恢复；证书申请失败来自 Caddy 的 `cert_failed` 事件（节点注册了事件处理模块 `events.handlers.nagi`），拿到证书的 `cert_obtained` 事件时恢复。Caddy 会自己重试申请，重复的失败在 4 小时内只提醒一次。
- **代发与补发**：直接发送失败时，调用配置这个渠道的面板的 `RelayAlert` 代发；面板也不可达时存进 `identity/alerts-queue.json`（最多 200 条），每 30 秒重试。
- **节点失联**：面板每 15 秒检查一次。离线时间从"最后在线"和"面板启动"中较晚的那个算起，避免面板重启后节点还没来得及重连就报失联。
- **状态在内存里**：节点或面板重启后，还没恢复的问题会再提醒一次。
- **测试**：面板设置里可以给某个渠道发一条测试消息（由面板发送）。

### 消息格式

webhook 收到 POST JSON：

```json
{
  "status": "firing",
  "key": "disk",
  "title": "磁盘使用 93%，超过 90%",
  "message": "",
  "node": "node1",
  "project": "",
  "time": "2026-10-17T09:04:03Z",
  "text": "🔴 磁盘使用 93%，超过 90%
节点：node1
时间：..."
}
```

`status` 是 `firing`、`resolved`，或者一次性通知 `info`（例如"已顶替项目"，没有对应的恢复）；`key` 标识同一个问题，例如 `disk`、`mem`、`restart:c:<项目 ID>/<成员>/<服务>`、`health:<项目 ID>/<成员>/<服务>`、`cert:<域名>`、`errors:<项目 ID>/<规则名>`、`event:snapshot:<项目 ID>`、`event:cert_failed:<域名>`、`offline`。Telegram 收到的是 `text` 的内容。
