# 对外访问：Caddy 统一出口

所有对外流量都从节点上的内嵌 Caddy 进入，默认是容器所在的节点，也可以从别的节点进（见[跨节点入口](#跨节点入口)）；容器自身不映射任何端口。Caddy 占用节点的 80/443，面板使用自己的随机端口，两者不冲突。

## 端口映射

- 映射属于容器，存在面板上，随容器的配置缓存下发给容器所在的节点（以及它的顶替节点、备份节点）。节点汇总本节点上所有容器的映射生成 Caddy 配置，所以对外端口和域名默认开在容器所在的节点上；容器迁移或顶替到别的节点，映射跟着过去。
- **改了立即生效，不需要重新部署**：映射只影响 Caddy，不动容器，所以不走草稿和版本。
- 只在面板上修改，节点上的是缓存。
- 在容器页的「网络」标签里管理，那里还有内部访问地址；项目页的「网络」只有全部映射的总览。每条映射的请求和流量在项目页的「概览」里看。
- 映射指向"容器（容器组还要指明组里的哪个容器）+ 容器端口"。有些镜像没在 compose 里写端口，需要手动添加映射才能访问。手动添加的映射和从 compose 导入的映射完全一样。容器被删除后，指向它的映射标为无效。
- 字段：容器、组里的哪个容器（compose 服务名，单个容器不用填）、容器内端口、协议（http、tcp 或 udp）、节点上对外的端口（tcp/udp 必填；http 没绑域名时必填）、绑定的域名（只用于 http）、只开 HTTP 不申请证书、入口节点（见[跨节点入口](#跨节点入口)）。

- **访问地址**：界面上每条映射旁给出打开它的地址：绑了域名的用域名；没绑的 http 映射用"容器所在节点的地址:端口"。节点地址是面板看到的节点来源 IP，面板自带的节点用面板的对外地址；节点在 NAT 后面时这个地址不一定能从外面访问。

## HTTP 服务

- **没绑域名**：Caddy 开一个端口（用户填写或自动分配），用 `IP:端口` 访问。
- **绑了域名**：先开 HTTP。拿到证书以后（自动申请；用户上传证书还没做），同时开启 HTTPS，并自动把 HTTP 跳转到 HTTPS。
  - 实现：关闭 Caddy 自带的自动跳转。域名始终放在 443 上，让 Caddy 去申请证书；80 端口上，还没拿到证书的域名直接转发，已经拿到证书的域名跳转到 HTTPS。节点每 15 秒检查一次证书状态。
  - 这样证书申请失败时（例如域名还没解析到节点），网站仍然能用 HTTP 访问，不会被跳转到打不开的 HTTPS。
- **只开 HTTP**：可以为域名关闭 HTTPS（例如前面还有 CDN 终结 HTTPS），这时不申请证书、不跳转。
- 80 端口上没匹配到任何域名的请求返回 404。

## 域名检查

绑定域名时，表单不再显示节点端口（经 80/443 访问）；tcp/udp 映射不显示域名。检查结果只用来提示，不拦着保存：前面有 CDN 时解析到的本来就不是节点，DNS 也可能之后才改。

- **解析**：面板查域名解析到的地址，和每个入口节点的地址比较，编辑时和映射列表上都显示。结果有四种：解析正确；解析到了别的地址（前面有 CDN 时可以忽略）；解析不到；无法比对（节点离线，或者节点地址是内网地址、节点可能在 NAT 后面）。结果缓存 30 秒。查的是面板看到的 DNS，分地区解析时可能和外面看到的不一样。
- **证书**：节点随上报带上开放的每个域名的证书状态（已签发和到期时间、申请中、申请失败和原因），申请成功或失败时立即上报。按入口节点分别显示；只开 HTTP 的域名不显示。申请失败时 Caddy 会自动重试，原因（ACME 的原始错误）可以展开查看。失败原因只在内存里，节点重启后 Caddy 重新申请，期间显示申请中。旧版本节点不报，显示状态未知。
- **手动重试**：申请失败时可以点“立即重试”，不用等 Caddy 的下一次自动重试（间隔逐渐拉长，最长几小时）。节点强制重载 Caddy 配置：旧的申请任务取消，所有还没拿到证书的域名立刻重新申请，退避从头算；已有证书的域名不受影响。Let's Encrypt 对同一个域名每小时只允许 5 次失败的验证，所以同一个节点 1 分钟最多重试一次；改好 DNS 或防火墙再点。
- 不单独探测 80/443 从外面通不通：面板连得上不代表外面连得上。端口不通时证书申请会失败，原因里能看到。

## TCP / UDP 服务

数据库、游戏服、MQTT 等，同样经 Caddy 转发，使用内嵌的 layer4 模块。

**已知限制**：经 Caddy 转发后，容器看到的来源 IP 是 Caddy 的地址，不是真实客户端。HTTP 服务不受影响（Caddy 会在请求头里带上真实 IP）。需要按客户端 IP 做限制的 TCP/UDP 服务，需要应用支持 PROXY protocol；以后可以考虑提供"该端口直接映射"的例外选项。

## compose 里写的 `ports`

每次部署时，把 compose 里**新出现的** ports 导入成映射文件，之后可以在界面上修改协议或绑定域名。协议：compose 里写了 `app_protocol: http` 就按 http；否则容器端口是常见的网站端口（80、8000、8080、8081、8888、3000、3001、4000、5000、5173、8096）时按 http 开放（能统计请求、能绑域名），部署日志里注明是猜的；其余按 tcp/udp 原样开放。9000（php-fpm 等）和 443（容器内一般是 HTTPS）不算网站端口。运行时由 override 去掉容器的端口映射（见 [agent.md](agent.md#override-叠加配置)）。

- 导入过哪些端口（容器 + 服务 + 容器端口 + 协议）记在面板上。已经导入过的端口不会再导入：用户改过的映射不会被覆盖，删掉的映射也不会被加回来。所以之后改 compose 或镜像表单里已有端口的节点端口不会生效，对外端口一律在映射里改；界面上修改容器时不再显示镜像表单的端口一栏，compose 编辑框旁也有说明。
- 和同一节点上的其他映射冲突、或者没写对外端口的 compose 端口不导入，只在部署日志里提示，可以之后手动添加。

`network_mode: host` 的服务例外：它直接使用宿主机网络，不经过 Caddy，端口直接对外，项目页面上醒目提示（见 [agent.md](agent.md#部署方式)）。

## 端口冲突

保存映射时由面板检查（从 compose 导入时也检查，冲突的不导入）：

- 80 和 443 留给域名访问，不能作为其他开放方式的端口。
- 端口不能和同一节点上的其他映射重复；域名在整个面板上不能重复。设了顶替或备份节点的容器，在那个节点上也要不冲突。
- 还没在用的端口，让节点尝试监听一下，确认没有被节点上的其他程序（包括面板端口、sshd 等）占用。
- 绑定域名时，在容器所在节点和入口节点上同样检查 80 和 443：它们被其他程序（例如机器上另外装的 Caddy、Nginx）占着时，节点的 Caddy 配置整个加载失败，这个节点上的所有映射都不生效。只在保存映射时查；部署和补推配置时不查，免得连容器也部署不了。只有 Caddy 配置加载成功时，这两个端口才算它自己占着。

冲突时拒绝保存并提示。

## 跨节点入口

容器在节点 A 上，外部请求可以访问节点 B 的地址，由 Nagi 转发到 A 上的容器。容器不用动，也不用给它换地址。

### 怎么设置

- 入口是端口映射的属性，不是单独的功能页。映射多一个字段“入口节点”，可以多选，默认只勾容器所在的节点。改了立即生效，不需要重新部署。
- **容器所在的节点**这个选项跟着容器走：容器迁移或顶替到别的节点，入口也跟过去。其他入口节点是固定的节点，不随容器移动。可以取消容器所在的节点，只从别的节点进；至少要留一个入口。
- 一条映射在所有入口上用相同的协议、端口和域名。要用不同的端口，就再加一条映射。
- 访问地址：界面上列出每个入口节点的“地址:端口”，节点地址的来源和局限见[端口映射](#端口映射)。

### 流量路径

```
外部请求 → B 的 Caddy → B 上的本地转发口 → mesh → A 的 7001 端口 → A 上的容器
```

- 面板在代理计划（`LinkPlan`）里告诉 B 要开哪些入口，节点缓存这份计划，面板不在时入口照常工作。
- B 为每条入口在 `127.0.0.1` 上开一个随机端口作为 Caddy 的上游，TCP、HTTP 和 UDP 都这样。收到连接后沿用项目内网的转发（见 [mesh.md](mesh.md)）：按顺序试容器所在节点和顶替节点，对方回“不在这里”就试下一个，所以顶替以后不用改入口。
- 证书和 HTTPS 在 B 上处理，流量到 A 以后直接连容器，不再经过 A 的 Caddy。
- 目标都连不上时：HTTP 返回 502，TCP 断开连接，UDP 丢包。

### 权限

- 入口节点只需要访问映射指向的那个端口，不应该因此能访问项目里的其他容器和端口。所以不复用 `LinkAllow`（它放行整个项目开放的端口），而是单独下发 `LinkEntryAllow`：哪些节点可以访问哪个容器的哪个端口和协议。容器所在节点和顶替节点都下发这份名单。
- 这也解决了手动添加的映射：它指向的端口可能没有在 compose 里声明，现有检查会拒绝，按这份名单放行就可以了。
- 放行被撤销（映射删了、节点被移除）时，目标节点 5 秒内断开只靠入口放行建立的连接。只在建立时检查不够：Caddy 会复用到上游的连接。
- 本地转发口只监听 `127.0.0.1`，转发的就是对外开放的那个端口，所以入口节点上的本机程序能连到它也没有多开放什么。

### 冲突检查

- [端口冲突](#端口冲突)的规则扩展到每个入口节点：一条映射占用它所有入口节点上的端口。迁移、设置顶替或备份时，也要和目标节点上其他映射的入口比较。
- 新加入口节点、或者改了端口时，这些入口节点必须在线，节点确认端口没有被其他程序占用（`CheckPorts`）；不在线就拒绝保存。入口和端口都没变的节点不用再查，它不在线时也能改映射的其他部分。删除入口时节点不在线的，等它上线后补推。
- 节点上报自己是否支持跨节点入口，旧版本节点不能选作入口，容器所在节点和顶替节点是旧版本的也拒绝，并提示先升级。`--no-proxy` 的节点没有 Caddy，不能选作入口。
- 顶替后容器到了 B，而 B 本来就是这条映射的入口：同一条映射只开一次，容器所在节点的规则优先；取消了容器所在节点时，走入口的规则，转发时发现目标就在本节点上，直接连容器。这些都在节点上判断，面板不在时也一样。

### 其他功能的处理

- **入口节点挂了**：只影响从它进来的流量，其他入口和容器不受影响。不会自动切走，外部要靠 DNS 或客户端切到别的入口。
- **容器所在节点挂了**：有顶替时自动跟随；没有顶替时入口连不上容器，等容器恢复或重新部署。
- **面板不在**：入口节点按缓存的计划（`links.pb`）照常工作，节点重启后也能恢复；要改入口等面板恢复。
- **节点被移除**：从映射的入口里去掉；没有入口了就把映射标为无效，不会悄悄改回从容器所在节点开放，用户重新选择入口节点后恢复。移交项目时入口节点算作相关节点，一起带上。
- **面板丢失后拼回**：入口节点随映射保存在容器缓存里。节点 ID 由节点的身份公钥算出，换面板不变，所以拼回时照原样保留；入口节点还没接入新面板时先跳过，接入后自动恢复。
- **监控**：HTTP 请求统计记在收到请求的入口节点上（见 [monitoring.md](monitoring.md#caddy-请求统计)）。界面查询所有入口节点并汇总：请求数和流量相加，耗时取最慢的那个入口。告警按节点判断，不汇总。

### 限制

- **性能**：多绕一跳，而且走用户态 WireGuard，带宽和延迟都比直连差。B、A 之间打不通、改走面板中转时，这部分流量还要经过面板。设置入口节点时界面上有说明；实际走直连还是中转在节点页的 Mesh 标签里看。
- **流量费用**：同一份流量在入口节点和容器所在节点上都要收发，两边都计费。
- **入口不是高可用**：入口节点是单点，跨节点入口本身不负责健康检查和切换。
- **来源 IP**：HTTP 由入口节点的 Caddy 在请求头里带上真实 IP；TCP/UDP 看不到真实客户端，和[现有限制](#tcp--udp-服务)一样。
- **绑定域名**：每个入口节点都会尝试申请证书。域名只解析到其中一部分入口时，其他入口申请失败并产生证书告警；解析到多个入口时，验证请求可能落到另一台节点上而失败。所以绑定域名时界面提示：只勾域名实际解析到的节点；需要多个入口时，建议由前面的 CDN 终结 HTTPS，并打开“只开 HTTP”。

## Caddy 如何找到容器

Caddy 运行在 agent 进程里，直接通过容器的 IP（容器组优先用它默认网络里的地址，单个容器用项目内网或它自己网络里的地址）转发流量，不经过端口映射。容器重建后 IP 会变，agent 监听 Docker 事件，容器变化时立即更新 Caddy 的转发目标。

## 为什么统一出口

- 出口只有一套，不会出现 Docker 端口映射绕过 ufw 防火墙的问题。
- 以后做顶替后的流量切换，也只需要改 Caddy；[跨节点入口](#跨节点入口)能让对外地址固定在入口节点上，不随顶替变化。
