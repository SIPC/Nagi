# 高可用

## 面板故障

- **业务不受影响**：项目数据本来就在节点上。面板不可达时，节点照常运行容器、续签 HTTPS 证书、执行定时快照、发送告警，只是暂时不能通过 UI 修改。
- **数据不丢**：面板手里只有配置备份。面板恢复，或者换一个新面板接入后，节点把各自的项目上报上来，面板的数据就回来了。换面板的方式见 [control-plane.md](control-plane.md#信任的面板列表)。
- **面板也是最后一道备份**：如果某个项目的所在节点和顶替节点都坏了，还可以用面板上的配置备份在别的节点上重建这个项目（见下文）。面板只备份配置，项目文件需要重新上传或从 git 拉取，运行数据无法恢复。
- **面板高可用**：同时运行两个面板管理同一批节点，一个挂了另一个照常可用。面板之间不需要 Raft 之类的集群同步。

### 用配置备份重建项目

所在节点坏了、又没有顶替节点或备份节点上的副本可以恢复时的最后手段。

- **前提**：原节点离线（在线时用"迁移"）。原节点要还在面板的节点列表里：移除节点会删掉它的配置备份。
- **操作**：项目列表里，离线节点的项目显示的是配置备份；在它上面点"用配置备份重建"，选目标节点和目录。
- **重建出来的是一个新项目**：新的项目 ID，项目名不变。原节点修好回来时，它手里有真正的数据，两个项目互不干扰，由用户决定留哪个。
- **带过去的**：
  - 每个容器最新版本的配置：compose 或镜像表单、变量、密钥、文件来源、保留路径、依赖顺序；
  - 没部署的草稿，包括容器的草稿和共享变量的草稿；
  - 项目设置：共享变量、内网、网络名、跨节点端口、快照间隔；
  - 端口映射和域名：在目标节点上冲突的跳过并提示。
- **不带过去的**：
  - 项目文件、运行数据和历史版本，版本从 1 开始；
  - 顶替和备份节点的设置。
  - 共享网络：目标节点上有同名网络就留在里面，没有就退出。
- **重新生成的**：每个容器的 deploy key 和 webhook 令牌都是新的。私有 git 仓库要加上新的 deploy key，webhook 地址也要在仓库里更新。
- **自动部署**：按依赖顺序部署能直接部署的容器，也就是从 git 拉文件的，或者不用 `data/` 里文件的。
  - 要用 `data/` 里的文件、又没有文件来源的容器（镜像表单设了工作目录，或者 compose 挂载了 `data/` 下的路径）不部署，提示先上传文件再部署。
  - 部署失败的容器（例如私有仓库还没加新的 deploy key）照常提示，修好后手动部署。

## 节点故障：指定顶替节点

**谁来顶替由用户事先指定。** 在面板上创建或编辑项目时，可以为它指定一个顶替节点。没有指定的项目，所在节点挂了就原地等待，Nagi 不做任何动作。这同时取代了自动调度：MVP 阶段项目放在哪里、由谁顶替，都由用户决定。

### 租约与三方多数票

每个设置了顶替的项目有三个参与者：

| 角色 | 说明 |
| --- | --- |
| A | 项目当前所在的节点 |
| B | 用户指定的顶替节点 |
| 见证人 | 每个项目**只指定一个**：某一个面板，或者另一台节点。默认是发起设置顶替的那个面板。只投票，不运行项目 |

规则只有一条：**只有拿到 3 票中的 2 票的一方才能运行项目。**

- 投票的方式是租约：持有者定期续约，租约到期就自动作废。见证人同一时间只把票投给一方，也就是当前的持有者。
- 租约默认 30 秒，每 10 秒续约一次，可按项目调整。A 挂掉后大约 40 秒内 B 顶上。
- A 续不上租约时，必须在租约到期前 5 秒**已经停完**项目；B 在租约到期后再等 5 秒才启动。中间留 10 秒空档，双方都只看自己测量的时长，不依赖两台机器的时钟一致。
- 停止容器需要时间（compose 默认给容器 10 秒优雅退出）。所以 A 在"到期前 5 秒 + 停止超时"的时刻就开始停止；到了到期前 5 秒还没停完，直接强制结束容器。
- 所有投票消息都走 WireGuard mesh，不论见证人是面板还是节点，用的都是同一套代码。
- 见证人必须唯一。多面板时，如果两个面板都以为自己是见证人、各自投票，多数票就失效了。
- **三方必须一直能互相联系**：投票走 mesh，而 mesh 只连通同一个面板下的节点和面板。所以节点拒绝移除这样的面板：移除后本节点和顶替设置里的其他参与方之间，经剩下的面板联系不上了（例如这个面板就是见证人，或者它是 A 和 B 唯一共同的面板）。面板移交节点、忘记节点之前也先检查。要先更换见证人，或者让相关节点都加入另一个面板（共同管理）后再移除，或者取消顶替。节点本地命令可以加 `--force` 强制移除（旧面板已经挂了时只能这样），并提示哪些项目暂时没法顶替。
- 设置顶替时，A 和 B 都必须信任发起设置的那个面板（见 [mesh.md](mesh.md)）。
- 设置顶替时就检查 B：项目目录是否可用、项目经 Caddy 对外开放的端口在 B 上是否已被占用。有问题当场提示，而不是等到顶替时才失败。
- 已知的极端情况：面板挂了，同时 A 和 B 之间的 UDP 也不通，A 联系不上任何一方，会主动停掉项目。这需要两处同时出问题，而且结果只是停机，不会出现两份同时运行。

各种故障下的结果：

| 情况 | 结果 |
| --- | --- |
| A 挂了，或者 A 自己断网 | B 和见证人构成多数，B 顶上；A 的租约过期，自己停掉 |
| B 挂了 | A 和见证人构成多数，A 照常运行 |
| 见证人（面板）挂了 | A 和 B 构成多数，A 照常运行 |
| A 和 B 之间断网，但都能连上见证人 | 见证人的票只给当前持有者 A，A 继续运行，B 不动 |
| A 和见证人之间断网，但 A 和 B 之间通 | A 和 B 构成多数，A 照常运行 |
| 同时坏两方 | 不顶替，原地等待 |

### 数据主人与热备

- **谁持有租约，谁就是数据主人**：平时 A 持有租约，项目数据以 A 为准，A 定时把配置、版本文件和快照同步给 B（默认每 15 分钟，见 [snapshot.md](snapshot.md)）。B 顶替以后，B 成为新的数据主人。
- **热备**：B 平时就按版本记录的镜像摘要拉好镜像、准备好配置，顶替时只需要启动容器。B 上的项目目录在设置顶替时单独指定，项目网段在 B 上重新分配；B 上有同名的共享网络时项目留在里面（网络连起来的话照常和原来的项目互通），没有就退出。
- **A 恢复后不抢回来**：A 回来后发现租约已经归 B，就保持停止状态，并从 B 同步最新数据，不会用自己手里的旧数据覆盖。要不要切回 A，由用户在面板上决定。

### 实现

- **设置**：在项目页选顶替节点 B、B 上的项目目录、见证人（默认本面板，也可以选另一台节点）。项目加入的共享网络在 B 上没有时提示：顶替到 B 后会断开和哪些项目的连接。迁移时同样提示。设置时检查 B：目录可用、B 上还没有这个项目；A 上的项目没有设备份节点。面板按"见证人 → B → A"的顺序下发设置，任何一方失败就撤销已下发的。三方各存一份（节点在 `<节点目录>/failover/`，面板在 `<面板数据目录>/witness/`），初始租约归 A、第 1 轮。
- **投票**（`internal/pkg/lease`，面板和节点共用）：经 mesh 调用 `MeshService.LeaseVote`，调用方身份就是 mesh 公钥，只接受设置里的 A、B。同一方同一轮是续约；更高的轮次只有在当前的票已经作废（超过租约时长没续约）时才同意。投给谁、第几轮写在磁盘上；投票者重启后按"刚刚续过约"处理，一个租约时长内只给原持有者续约，不投给别人，所以投票者重启不会造成两边同时运行。
- **持有者**：每 1/3 个租约时长向另一个节点和见证人续约（加上自己的一票）。租约从发出请求的时刻算起。续不上时在"到期前 5 秒 + 10 秒停止超时"开始 `compose stop`，到期前 5 秒还没停完就强制结束容器；之后又续上了就重新启动。节点刚启动时第一次续约失败也会立即停止项目（不知道上次续约是什么时候）。
- **热备**：持有者每 15 分钟（设了顶替的项目定时快照也改为每 15 分钟）以及每次定时快照后，把副本同步给热备（复用备份节点的同步）；同步失败 1 分钟后重试并告警。热备收到同步后按副本里的配置提前拉镜像（最多每 30 分钟一次）。
- **顶替**：热备投给持有者的票作废后，先向见证人和原持有者要第 `轮次 + 1` 轮的票，拿到一票再投自己——避免要不到票时自己白白占着这一票。凑够 2 票就成为新的持有者，等 5 秒，用副本恢复项目（项目 ID 不变，恢复到设置里的目录）并启动；恢复期间照常续约。
- **原持有者回来**：续约被拒绝，响应里看到更高的轮次，就停止并删除容器、把项目移出本节点、目录改名为 `<目录>.replaced-<时间>` 保留，然后接受新持有者的同步，成为它的热备。之后新持有者挂了，它又能顶回来（恢复到原目录）。要不要把项目切回原节点，由用户用"迁移"决定。
- **告警**：续不上租约、有状态项目等待确认、无法顶替（热备还没收到过同步）、同步给热备失败会告警并在恢复时通知；已顶替、已被顶替是一次性通知。
- **实测**（两个节点各自独立的 Docker，见证人是面板，租约 30 秒）：切断 A 的网络后，A 在最后一次续约后约 15 秒停止项目；无状态项目在 A 开始停止约 25 秒后在 B 上启动（A 的租约到期后 4 秒 B 拿到多数票，再等 5 秒）；有状态项目停在"等待确认"，确认后用最后一次同步的数据启动。恢复 A 的网络后，A 自动退位并在 1 分钟内开始接收 B 的同步。

- **节点代管重启**：设置了顶替的项目，容器的重启策略一律是 `no`（设置或取消顶替时直接改正在运行的容器，不用重新部署）。实测 Docker 在非正常关机后会把 `always`、`unless-stopped` 甚至 `on-failure` 的容器都拉起来，所以只能不让 Docker 管。持有租约的节点每 2 秒检查一次，按用户在 compose 里写的（或默认的 `unless-stopped`）策略重启退出的容器：`on-failure` 只在退出码非 0 时重启并遵守次数上限，`no` 不重启；连续重启时退避（2 秒起翻倍，最多 60 秒）。节点代为重启的次数计入监控的重启次数，"反复重启"告警照常有效。机器重启后，Docker 不会启动这些容器，节点拿到租约后由这里把它们启动起来。代价是节点进程不在时，崩溃的容器不会自己起来。
- **节点重启**：mesh 成员列表写在 `identity/mesh-peers.json`，节点重启后面板不在也能直接联系另一个节点和见证人节点。刚启动的 10 秒内续不上租约先不停（等 WireGuard 握手；这时项目本来就没在运行）；续不上时 2 秒后就重试。
- **设置顶替和迁移时检查端口**：B 上有其他项目的映射占用了相同的端口或域名，或者端口被其他程序占用，当场提示。
- **实测**（两个节点各自独立的 Docker）：B 上端口冲突时设置被拒绝；`on-failure:2` 的崩溃服务被节点重启恰好 2 次，监控里的重启次数是 2；A 断电重启后 Docker 没有拉起任何项目容器，节点 8 秒后拿到租约并启动，B 没有接管；面板也停掉时 A 断电重启，用保存的容器列表和 B 续约，9 秒后恢复运行。

- **更换见证人**：在项目页选新的见证人（本面板或另一台节点），顶替照常进行，不用先取消。面板先问 A、B 当前的持有者和轮次（取轮次大的），让新见证人从这个持有者开始投票（相当于"刚刚续过约"，一个租约时长内不会投给别人），再按 B → A 的顺序更新设置，最后清掉旧见证人；任何一步失败都撤销。旧见证人是另一个面板时清不掉它那边的设置，但 A、B 不会再找它投票，留下的设置不影响。
- **实测**（三个节点、两个面板）：面板 A 担任见证人时，A 不能把自己从节点上移除，面板 B 也不能移除 A，A 不能移交或忘记顶替节点，本地命令不加 `--force` 拒绝；把见证人换成 n3 以后，A 仍是 n1 和 n2、n3 唯一共同的面板，还是不能移除；n2、n3 也加入面板 B 以后才能移除。之后切断 n1，n2 靠 n3 的票顶上；n1 恢复后经面板 B 联系上 n2 并退位；再在面板 B 上把见证人换成面板 B，n2 照常续约。

**已知的限制**：

- 更换见证人可以直接做（见上）；修改其他设置（顶替节点、租约时长等）需要先取消再重新设置。

### 有状态项目

项目里只要有一个容器有状态（用了命名 volume 或有保留路径），项目就算有状态。顶替和迁移都按整个项目，所有容器一起搬。

- 顶替时 B 用最近一次数据快照（`volumes/` 和保留路径）启动，最后一次快照之后写入的数据会丢失。
- 项目刚设置顶替、还没有定时快照时，B 用各容器部署的版本文件恢复 `data/`，没有运行数据。
- 因此有状态项目默认只告警，由用户手动确认后才顶替。用户可以明确选择"自动顶替，接受丢失最近一段时间的数据"。
- 要做到零丢失，只能靠数据库自身的主从复制，这不在面板的通用能力范围内。

**暂不处理**：顶替之后流量怎么切换到 B（例如域名解析），由用户自行处理。

### 只备份不顶替：备份节点

没设顶替的项目，可以指定一个备份节点，只接收快照同步，不参与租约、不会自动顶替。顶替和备份节点二选一：设了备份节点的项目要先取消才能设顶替，设了顶替的项目不能再设备份节点（顶替节点本身就有一份副本）。节点坏了以后，由用户手动从备份节点恢复，或者把项目迁移过去。见 [snapshot.md](snapshot.md#异地副本)。

## 手动迁移

用户主动把项目从 A 搬到 C。复用备份节点的同步和恢复（见 [snapshot.md](snapshot.md#备份节点的实现)），由面板按顺序指挥两个节点：

1. **检查目标节点**：目录可用、目标节点上还没有这个项目、端口和域名不冲突。有问题当场失败，项目不用停。项目加入的共享网络在目标节点上没有时，提示搬过去以后会断开哪些连接。
2. 目标节点登记接收副本（只接受源节点的 mesh 公钥）。
3. 源节点在项目运行时先同步一次；然后停止并移除所有容器（`compose down -v`：命名卷都绑定在项目目录里，删除卷对象不会删数据），保存最后一次快照，再增量同步一次。停止以后项目标记为"迁移中"，期间不能部署或修改。
4. 目标节点恢复：项目 ID 不变，用最后一次快照恢复各容器的 `data/` 和 `volumes/`，按各自部署过的版本和镜像启动所有容器（不生成新版本）。
5. 成功：源节点把项目移出项目列表，**项目目录保留在磁盘上**，确认没问题后由用户自己删除。

- 停机时间只有第 3、4 步，也就是最后一次增量同步加启动的时间，不丢数据。
- 任何一步失败都撤销：目标节点上删掉恢复了一半的项目和副本，源节点取消"迁移中"并重新启动项目。迁移一旦开始，浏览器断开也会走完撤销。
- 版本记录和部署记录随 `project.db` 一起过去，可以接着回滚；webhook 地址不变。容器网段在新节点上重新分配，新节点上没有的共享网络会退出，备份节点设置需要重新选择。
- 设了顶替的项目要先取消顶替再迁移，迁移完成后在新节点上重新设置。迁移和顶替各管一件事，不互相改对方的设置。
