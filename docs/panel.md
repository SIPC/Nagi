# 面板

面板由 `nagi server` 启动，是项目配置的主人：保存所有项目和容器的配置、版本记录和部署记录，把容器分配到节点上运行，并负责 UI 和见证人投票。容器的运行文件、数据和快照在节点上，见 [agent.md](agent.md)。

## 职责

- 监听一个**面板端口**：首次启动时随机选一个高位端口并持久化，之后重启不变，也可以用 `--port` 指定。Web UI 和 agent 的控制通道共用这个端口
- Web UI（前端构建产物通过 `embed` 打包进二进制）与 Connect-RPC 接口（见 [control-plane.md](control-plane.md#接口设计)）
- SQLite 存储（modernc 纯 Go 实现，无需 CGO）：保存节点信息、面板自身的设置，以及所有项目的数据（见下文，密钥用面板主密钥加密）
- 把容器的配置下发给它所在的节点执行，更新节点上的配置缓存和代理名单；一起部署、迁移、回到某次部署这类涉及多个节点的操作由面板指挥
- 汇总各节点上报的容器状态，供 UI 显示
- 自签 CA：为 agent 签发客户端证书
- 加入 WireGuard mesh：把上传的项目文件传给节点，直连不通时替节点中转 mesh 流量（见 [mesh.md](mesh.md)）
- 可以担任顶替机制中的见证人（见 [failover.md](failover.md)）
- 发现节点失联时发送告警（见 [monitoring.md](monitoring.md)）
- 一键更新自己（见[更新面板](#更新面板)）

## 项目数据

面板数据库里存着：

- 项目：名称、网络名、共享变量（含草稿）、镜像仓库认证、项目连接、内部端口、快照间隔、部署记录、修订号；
- 容器：所在节点和容器目录、配置和草稿、版本记录（配置、镜像摘要、提交、部署时间）、端口映射、deploy key 和 webhook 令牌、快照仓库密码、顶替和备份节点设置、修订号。

容器的运行文件、数据、快照和版本文件不在面板上，在容器所在的节点（和它的热备、备份节点）上。

**节点缓存**：每次修改或部署，面板把容器的完整记录和所属项目的信息推给容器所在的节点（见 [agent.md](agent.md#节点目录-varlibnagi)），顶替节点和备份节点也各推一份。节点离线时，等它连上后补推。所以：

- **面板挂了**：容器照常运行、重启、快照、顶替，只是不能修改和部署。面板回来后照常。
- **面板彻底丢失**（机器坏了、没有备份）：装一个新面板，在各节点上用 `nagi panel add` 加入它（见 [control-plane.md](control-plane.md#在节点上操作)）。新面板按项目 ID 收集各节点上报的缓存，把项目拼回来：节点上报了面板不知道的容器时，面板向它要全部缓存（`AgentService.GetCache`），容器取当前部署的版本（配置、共享变量、镜像摘要）、端口映射、deploy key、快照仓库密码，备份节点和顶替设置拼回后等管理员确认才生效（见下面的「不轻信节点」），项目信息取项目修订号最大的那份，内部端口和项目连接取节点的代理计划。拼回来以后照常使用，不用重新部署。拼不回来的：草稿、旧版本和部署记录（旧版本的文件还在节点的快照仓库里，但面板上没有记录，不能选它回滚）、项目的创建时间；webhook 令牌只在面板上，会重新生成，git 那边的 webhook 地址要更新。顶替的见证人原来是旧面板的，管理员确认顶替设置以后，新面板自动换成自己（换之前 A、B 两票照常构成多数）。
- **旧面板回来**（面板离开期间节点归别的面板管过、改过东西）：面板下发的配置里带着自己的指纹（`ContainerSpec.panel`），节点上报时带回来。面板看到节点上的配置是别的面板写的，就知道自己的记录可能旧了：不把旧配置推下去，在节点页列出这些项目（"项目记录可能已过期"），管理员确认后以节点为准，删掉自己关于这个项目的记录（草稿、版本历史、部署记录、路由、成员范围；保留 webhook 令牌），按节点缓存重新拼回来。节点可能被攻破，所以不自动重建：否则一个节点随便报一个面板指纹，就能让面板清空项目、改用它缓存里的共享变量；拼回以后把配置重新推一次，节点缓存里记上本面板（否则面板每次重启都会再拼一遍）。节点刚连上、第一次上报处理完之前，面板也不给它推代理计划。
- **不轻信节点**（节点可能被攻破）：
  - 只有面板记录里本来就在这个节点上（或者这个节点是它的顶替参与方）的容器，节点说"配置是别的面板写的"才算数，节点不能借此让面板删掉别的节点上的项目；
  - 面板上本来就有的项目，节点缓存里多出来的容器不自动加进去（否则一个节点能把自己的容器塞进别的项目，拿到它的共享变量、连进它的内网）；只有从节点缓存拼回的项目，拼回后 24 小时内接受别的节点缓存里的容器（项目记着 `rebuilt_at`）；其余的列在节点页上（"节点上有面板不认识的容器"），管理员确认是自己的以后点"加入项目"，按节点缓存加入；
  - 节点同时信任着写它缓存的那个面板时（两个面板同时管着这个节点，例如面板丢了以后让节点加入了新面板，旧面板又回来了），本面板不以节点为准删记录，也不把自己的配置推过去覆盖，只记警告，等用户在节点上移除不用的那个面板（节点上报时带着它信任的面板列表）；
  - 拼回的备份节点和顶替设置不直接生效，在容器的「高可用」标签上列为待确认，管理员（要先做高权限确认）确认后才恢复，也可以放弃。它们会让另一个节点接收这个容器的副本、在顶替时以缓存里的配置运行它；自动生效的话，被攻破的节点可以伪造一个带特权 compose 和顶替设置的新项目，停止续约后让另一个节点顶替，在那里以 root 运行它。拼回时先核对：节点都是登记过的，顶替的一方就是上报的节点，两方的公钥和登记的 mesh 公钥一致，对不上的直接丢掉；确认时再核对一次。缓存里的配置有特权内容时，界面上醒目提示，确认时要输入容器名。没确认之前，容器只在上报的节点上运行，不会影响别的节点，节点上已有的顶替设置也留着（不让节点删掉），确认后照常运行，放弃后才删；
  - 拼回的端口映射只取这个容器自己的、名字没被占用、和别的映射不冲突的；
  - 项目连接只在两边都是拼回后 24 小时内的项目、代理所属的项目在面板记录里就在这个节点上时才连回去（节点的代理计划只给它上面的项目放代理），否则一个节点只要知道两个项目的 ID，就能让面板把它们连起来；
  - 同一个容器在两个节点上都有一份时（例如在备份节点上恢复过，原节点后来又回来了），按先报上来的拼回，记下那份的修订号；拼回后 10 分钟内另一个节点报上来更新的一份，改用那一份，旧的那份等它的节点下次上报时停掉、目录改名保留；
  - 项目刚拼回的 10 分钟内，面板不让节点删掉顶替设置（容器可能还没从持有者那里拼回来，先从热备拼回时会看不到）。
- 建议定期备份面板的数据目录（数据库和主密钥文件），恢复更完整（含草稿）。

**面板主密钥**：数据库里的密钥（容器的变量和密钥、镜像仓库认证、deploy key 私钥、快照仓库密码、告警配置里的 Telegram 令牌、两步验证密钥）用主密钥加密。主密钥单独存成一个文件，数据库文件泄露也读不出密钥，面板仍能自动重启、查看和编辑密钥。需要提醒用户单独备份主密钥文件。节点缓存里的密钥由节点保存在本机（权限 0600），和容器目录里的 `.env` 一样。

**主密钥文件不见了**（例如只恢复了数据库、忘了放回密钥）：数据库里有加密数据时面板**拒绝启动**，提示把备份的密钥放回原处。不悄悄生成新密钥，否则这些数据就再也解不开了。确实丢了，用 `nagi server --new-master-key` 启动：

- 生成新的主密钥；
- 关闭所有用户的两步验证（登录后可以重新开启）；
- 清掉数据库里加密的项目密钥，由在线节点从缓存重新上报（和面板丢失时拼回项目一样），离线节点的要等它回来；
- 清掉告警配置，设置页提示重新填写。在那之前面板不给节点下发告警配置，节点继续按原来的配置发告警，只是面板负责的"节点失联"告警发不出去。

## 访问

- **默认**：用 `https://IP:面板端口` 访问，使用自签证书。带内嵌 agent 和用 `--no-agent` 的纯面板都一样。
- **对外地址**：面板有一个"对外地址"设置（自动检测，可修改），安装命令和节点连接都使用它，必须能被所有节点访问（见 [control-plane.md](control-plane.md#连接)）。
- **绑定域名**：之后在面板设置里绑定，自动申请正式证书。
  - 带内嵌 agent 时：由本机 Caddy 反代到面板端口，证书由 Caddy 申请。Caddy 到面板这一段用面板的公钥指纹校验，不需要信任自签证书。
  - 纯面板（`--no-agent`）时：本机没有 Caddy，由面板自己申请证书并提供服务。
- **绑定域名的实现**：在设置页的「面板访问」里填域名（填空取消）。域名删掉以后，节点上这个域名"申请证书失败"的告警自动恢复。
  - 带内嵌节点（有 Caddy）时，面板把域名告诉自带节点（节点上报里带 `embedded`、从本机 127.0.0.1 连上来的那个；主备面板时别的面板自带的节点也连着本面板，不推给它。连上时和修改时都会推送），节点的 Caddy 加一条规则把这个域名反代到 `https://127.0.0.1:<面板端口>`，用面板的 CA 校验面板证书（证书里有 `localhost`）。证书由 Caddy 申请，和项目域名一样，拿到证书以后 HTTP 跳转到 HTTPS。项目的映射不能再用这个域名。
  - 纯面板（`--no-agent`，或者内嵌节点用 `--no-proxy` 不启动 Caddy）时，面板用 certmagic（Caddy 的证书库）自己申请 Let's Encrypt 证书，在 443 上提供服务；80 用于 HTTP 验证，其余请求跳转到 HTTPS。证书存在面板数据目录的 `certificates/`。
  - 节点的控制连接和安装命令仍然用"对外地址:面板端口 + 公钥指纹"，不经过域名。
  - 经本机 Caddy 转发的请求，来源都是本机；登录限速对这些请求改用 `X-Forwarded-For` 里的第一个地址。只看来源是不是本机不够（本机上的其他程序，例如 host 网络的容器，可以随便填 `X-Forwarded-For` 绕过限速）：面板随推送域名给自带节点一个随机值，Caddy 转发时带上请求头 `X-Nagi-Proxy`（覆盖客户端带的同名请求头），面板核对对上了才采用 `X-Forwarded-For`。Caddy 反代的是本机的面板（自带节点信任列表里地址是 127.0.0.1 的那个）。
  - 实测：带内嵌节点时用 `nagi.localhost`（Caddy 对 .localhost 用本地 CA 签发）能通过域名访问和登录；纯面板时 80 正确跳转、443 在监听并开始申请证书（没有公网域名，无法实测签发）。

## 登录

- **初始化**：首次启动时在日志里打印一个带一次性令牌的初始化链接，打开后设置管理员账号和密码。没有令牌的人无法抢先初始化。
- **登录**：密码登录，可在设置里开启 TOTP 两步验证（首页提醒开启）。绑定域名后可以添加通行密钥（Passkey），用它代替密码和验证码登录（见[通行密钥](#通行密钥)）。MVP 只有一个管理员账号。
- **防护**：
  - 登录失败限速和锁定：同一 IP 连续失败 10 次以后，每次失败等待时间翻倍，最长 15 分钟；最后一次失败一小时后清零。登录成功不清零按 IP 的计数，否则同一 IP 上的人用自己的账号登录一次，就能清掉猜别人密码的失败次数；密码对了、还没填验证码的那一次不算失败也不算成功。登录时密码对了、验证码猜错，另外记在账号上；高权限确认、改密码、关闭两步验证也按账号计数（四者共用一份，账号失败 5 次以后开始等待，成功后清零）。这样知道密码的人换 IP 也不能一直猜验证码，拿到别人会话的人也不能借这些接口无限次地猜；不知道密码的人只能碰到按 IP 的计数，锁不住别人的账号。
  - 安全入口：可选开启，开启后必须在地址后加上一段随机路径才能打开登录页。
- **找回**：忘记密码、丢了两步验证设备或者忘了安全入口时，在面板所在机器上用 root 执行本地命令重置。和节点一样，能登录机器 root 的人本来就拥有这台机器。

### 实现

- **修改密码**：需要当前密码，新密码至少 8 位；改完后其他地方的登录全部失效，当前会话保留。
- **两步验证**：标准 TOTP（RFC 6238：30 秒一步、6 位、HMAC-SHA1），和常见的验证器 App 兼容。开启时先生成密钥（10 分钟内有效），用验证器显示的验证码确认才生效。密钥用面板主密钥加密后存在数据库里。登录时允许前后各 30 秒的时间误差，同一个验证码只能用一次。关闭需要验证码或密码。开启后登录不带验证码时接口返回 `failed_precondition`，界面据此显示验证码输入框。
- **安全入口**：开启时生成一段随机路径。开启后，没登录的访问者必须先打开一次 `https://<面板>/<路径>`（设置一个 30 天的 cookie，然后跳到登录页），否则面板的页面和接口一律返回 404，看起来就像这个地址上没有面板。已登录的会话、项目 webhook（`/hooks/`）、节点安装脚本（`/install.sh`）、备用面板配对和状态不受影响，节点的控制连接按 ALPN 分流，也不经过它。这些例外的地址对不认识的请求也返回 404（webhook 先认令牌再检查请求方法，备用面板上没有配对接口，状态接口只回答出示了本组面板 CA 签发的证书的面板，见 [standby.md](standby.md#谁是主面板任期)），扫描的人从这里看不出是面板；`/install.sh` 只在有可用的加入令牌时提供。面板启动日志里会打印带入口的地址。
- **本地命令**（直接改面板数据库，面板运行中也能用）：

  ```
  nagi reset password [--user 用户名]   # 生成一个新的随机密码并打印，所有登录失效
  nagi reset 2fa                        # 关闭两步验证
  nagi reset entrance                   # 关闭安全入口（会打印原来的路径）
  nagi reset admin-networks             # 清除管理员登录地址（会打印原来的列表）
  ```

  默认数据目录 `/var/lib/nagi`，和 `nagi server` 一样用 `--data-dir` 指定。

## 通行密钥

钓鱼代理能同时截获密码和验证码，通行密钥（WebAuthn 的可发现凭据）不能被转发：浏览器只在添加时的域名下使用它，签名里带着页面的来源，面板核对来源和域名。

- **添加**：在「设置 → 账号安全 → 通行密钥」里添加，要先做高权限确认（`BeginPasskeyRegistration` 登记在 `elevationRequired`，理由和开启两步验证相同：拿到会话的人不能借它给自己留一个登录凭据）。只有绑定了域名、并且从这个域名打开面板时才能添加；没绑定时界面说明要先绑定，从别的地址打开时说明要在哪个地址打开。要求验证器验证用户（指纹、面容、PIN），证明（attestation）请求 none、不校验，不限制验证器的品牌。每个成员最多 20 个，名称默认是浏览器和系统（例如「Chrome · Windows」）。添加和删除都发通知（见 [audit.md](audit.md#安全告警)）。
- **登录**：登录页只在从绑定的域名打开时显示「使用通行密钥登录」。不填用户名，浏览器列出这个域名下的通行密钥。登录成功等同于密码加两步验证，不再要验证码。失败和密码登录一样按 IP 计入限速；不认识的凭据按 IP 每小时汇总记进审计，认识的凭据验证失败逐条记（`passkey_failed`，带原因）。
- **校验**（`auth/webauthn.go`，`auth/passkey.go`）：挑战 32 字节随机数，5 分钟内有效、只能用一次。登录的挑战没登录的人也能要，所以不在面板上占名额：编号里带随机数和过期时间，用面板进程内存里的密钥做 HMAC，挑战本身也由它们算出，提交登录时核对；凭据确实存在以后才记下用过的编号，不认识的凭据不占表。用过的编号按过期时间每分钟一桶，过期的整桶丢弃，没有总数上限，没登录的人填不满它。按名额或按网段限数量的话，攻击者和别人共用一个出口（CDN 节点、公司或运营商的 NAT）就能占满名额，让后面的人开始不了通行密钥登录。面板重启后，还没提交的登录要重新开始。添加的挑战只有登录了的成员能要，同时最多 1000 个，每个成员最多 5 个。核对 clientDataJSON 的类型、挑战和来源（来源的主机名就是绑定的域名，用 https；`localhost` 和 `*.localhost` 允许 http；端口不限），验证器数据里的域名哈希、用户在场和用户已验证标志，签名（ES256、EdDSA、RS256）。签名计数没有变大时拒绝（通行密钥可能被复制了；计数一直为 0 的验证器不比较）。
- **存储**：`passkeys` 表存凭据 ID、COSE 公钥、签名计数、名称和添加时的域名。换了域名以后旧的通行密钥用不了，列表里标明「域名已更换，无法使用」，可以删掉重新添加。删除成员时一起删除。
- **找回**：通行密钥不影响密码登录，丢了设备照常用密码登录后删掉它。高权限确认和重新验证仍用密码或验证码。
- **管理员处置**：通行密钥登录不要密码和验证码，账号被盗时只重置密码不够。所以别人重置这个成员的密码、清除两步验证，以及在面板机器上执行 `nagi reset password` 时，这个成员的通行密钥一并删除，重置密码的对话框和确认里写明。管理员在「设置 → 成员」能看到每个成员有几个通行密钥，菜单里的「清除通行密钥」列出名称、确认后全部删除（`UpdateUserRequest.clear_passkeys`），并发通知。`nagi reset 2fa`（关闭所有人的两步验证）不删通行密钥。

## 管理员登录地址

可选，默认不限制。在「设置 → 安全 → 会话」的「管理员登录地址」里填写允许的 IP 或网段（每行一个，最多 50 项，存在 settings 表的 `admin_networks`），之后管理员只能从这些地址登录和使用面板，操作员和只读成员不受影响。

- **登录**：密码（和验证码）或通行密钥都对了以后才判断地址，不在范围内时拒绝，计一次登录失败，记入审计（`admin_network_denied`）并告警「管理员 `<名称>` 从允许范围以外的地址登录，已拒绝」：凭据很可能已经泄露。没开两步验证的管理员，从范围以外的地址能据此知道密码对了；开了两步验证时还要验证码也对。
- **使用**：每次请求检查会话时判断（`auth.authenticate`）。离开允许的地址时请求被拒绝，会话不退出，回到允许的地址后照常。地址按请求来源算（经本机 Caddy 转发时用核对过的 `X-Forwarded-For`）。
- **访问令牌**：管理员的访问令牌（个人令牌和 OAuth 授权的）同样只能从这些地址使用。从范围以外的地址使用时当作令牌无效，和令牌自己的「允许的地址」一样记入审计（`token_network_denied`，参数 `rule` 是 `admin`）并告警（见 [mcp.md](mcp.md#网段)）。
- **修改**：只有管理员能改，要先做高权限确认（`SetAdminNetworks` 登记在 `elevationRequired`）；保存时当前地址必须在列表里，否则拒绝，免得保存后自己就用不了。修改发通知（见 [audit.md](audit.md#安全告警)）。
- **找回**：填错把自己锁在外面时，在面板机器上执行 `nagi reset admin-networks`。设置被手动改坏、一项也解析不出来时按不限制处理。

## 会话

会话 cookie 是 `__Host-nagi_session`（`HttpOnly`、`Secure`、`SameSite=Strict`），安全入口的 cookie 是 `__Host-nagi_entrance`：浏览器保证带这个前缀的 cookie 只能由面板自己的域名、通过 HTTPS 设置，同一主域名下兄弟子域名上的网站覆盖不了。v0.29.0 以前的会话 cookie `nagi_session` 从 v0.29.1 起不再接受（收到时只让浏览器删掉）：它没有前缀，同一主域名下的其他子域名可以给它种一个自己的会话，受害者打开面板就进了别人的账号（登录 CSRF）；只有这个旧 cookie 的人要重新登录一次。安全入口的旧 cookie `nagi_entrance` 仍然接受、收到时换发新名字：它的值由入口路径算出，别的网站种不了，忘了入口路径的人也不会因此被挡在外面。数据库里只存令牌的哈希。

本节讲网页的会话。安卓 App 不用 cookie，用硬件密钥换取短期令牌，见 [android.md](android.md)。

每个会话有一个固定的 ID（`sessions.id`），令牌只用来找到会话。终端和日志流每 30 秒按会话 ID 重查，审计记录的 `session` 字段是会话 ID 的哈希前 12 位。

**处置分两级**：信号明确时直接退出会话；信号可能来自正常使用时，要求重新验证。要求重新验证时，这个会话的所有请求返回 `unauthenticated`，响应头 `Nagi-Reverify` 写原因、`Nagi-Reverify-Method` 写验证方式，界面弹出「验证身份」（开了两步验证的输验证码，没开的输密码，`AuthService.Reverify`）。验证成功后会话继续；失败计入账号的失败次数，连续 3 次失败退出这个会话。

| 信号 | 处置 | 告警 |
| --- | --- | --- |
| 已经换掉的令牌在作废 60 秒后又被使用 | 退出 | 是 |
| 轮换时拿不出会话密钥的签名（签名不对，或连续两个挑战都在 2 分钟内没有签名） | 重新验证 | 是 |
| 浏览器标识是浏览器，TLS 握手却来自脚本工具 | 退出 | 是 |
| 浏览器标识没变，TLS 指纹里不随连接变化的部分变了 | 重新验证 | 否，只记入审计 |
| 浏览器类型或操作系统变了（手机切换「桌面版网站」不算） | 退出 | 是 |
| 5 分钟内在两个网段之间来回切换 | 不处置，只记入审计 | 达到 6 次时告警 |
| 管理员换到最近 5 个验证过的网段以外 | 重新验证 | 否，只记入审计 |
| 高权限确认之后 IP 变了 | 重新做高权限确认 | 否 |
| 空闲超过 24 小时，或从登录起超过 7 天 | 退出 | 否 |

这些事件记为审计的 `security` 类（`session_reuse`、`session_key_missing`、`session_signature_invalid`、`session_tls_tool`、`session_tls_changed`、`session_device_changed`、`session_network_flip`、`session_network_changed`），告警由面板发出（`Service.Alert` → 告警渠道），备用面板不发。

- **令牌轮换**：每 15 分钟换一次。到时间后的请求，面板在响应头 `Nagi-Session-Challenge` 里给一个随机挑战；页面用会话私钥签名后调用 `AuthService.RotateSession`（带上签的是哪个挑战），面板核对签名，设置新令牌的 cookie。签名期间挑战已经换了（过期再发、别的标签页先换了）时只是不换发，不算签名不符，页面用之后响应里的新挑战再签。新令牌处于待确认状态（`session_tokens` 里的 `pending`），浏览器带着它来请求以后才转正，旧令牌记为 `retired`；转正之前旧令牌照常可用，响应在网络上丢失时不会误判。同一个挑战只能换一次令牌（比较、清除挑战和记下新令牌在一个事务里）：几个标签页同时轮换时只有一个成功，其余的接着用现在的令牌，不会出现先发出去的令牌被后一个作废、浏览器被要求重新登录。主人和盗用者都在用这个会话时，最迟 15 分钟被发现。换下来的令牌保留一周用来发现重用。
- **会话密钥**：登录（和初始化）成功后，页面用 WebCrypto 生成 ECDSA P-256 密钥（私钥不可导出），存进 IndexedDB，公钥用 `AuthService.RegisterSessionKey` 记在会话上（`lib/session.ts`）。同一个浏览器的多个标签页、多次登录共用一份密钥。只能在登录或重新验证后的 2 分钟内、会话还没有公钥时登记，盗用者不能换上自己的密钥。拿不出签名时只要求重新验证，不退出：无痕窗口、清除过网站数据的浏览器验证后重新登记。挑战发出 2 分钟内没有签名时先再发一次（挑战前加 `r.`），这次也没有签名才要求重新验证：手机常把标签页放到后台，页面来不及签名；只偷到 cookie 的人最多多用一个挑战的时长。几个标签页同时生成密钥时用 Web Locks 排队，存进 IndexedDB 用 `add` 不覆盖已有的，免得后到的标签页换掉已经登记的那份（会表现为签名不对）。私钥没有绑定硬件，复制整个浏览器用户目录的木马能连私钥一起偷走。
- **TLS 指纹**：面板在 `GetConfigForClient` 里按 JA4 的规则算出 ClientHello 的指纹（`tlsutil.JA4`），握手结束后不管成败马上从指纹表里取走，交给 HTTP 服务的连接经 `http.Server.ConnContext` 放进请求：握手失败、中途断开的连接不会留在表里，没登录的人反复中止握手撑不大面板的内存。节点 Caddy 那边的表最多记 5 万个连接，满了先删一分钟以前的，还满就清空（之后这些连接的请求不带指纹，面板不做这项检查）。经本机 Caddy 转发时，由 Caddy 里 Nagi 自己的模块（握手匹配器和处理器 `nagi_ja4`，见 `agent/proxy/ja4.go`）算好放在请求头 `X-Nagi-Ja4`，和 `X-Forwarded-For` 一样凭 `X-Nagi-Proxy` 核对后才采用。浏览器的 ClientHello 都声明 h2、扩展在 14 个以上；Go、Python、curl 的 HTTP 客户端扩展少，Python 和 curl（Windows 的 Schannel）不声明 h2。实测：Chromium `t13d1516h2_…`，curl `t13d2012h1_…`，Python `t13d181100_…`。判断「指纹变了」时不比较完整的指纹，只比较同一个浏览器每次连接都不变的部分：TLS 版本、SNI、密码套件个数、ALPN 和密码套件的哈希（`sameClient`）。扩展的个数和哈希不比较：会话恢复时 ClientHello 多出 pre_shared_key（有时还有 early_data），有的握手带 padding，同一个浏览器两次连接也不同（实测同一部手机 `t13d1516h2` 和 `t13d1517h2` 交替出现），手机网络下重连频繁，按完整指纹比较会反复要求重新验证。声明 h3 的握手（HTTP/3）也算浏览器。请求带着 CDN 的请求头（`Cf-Ray`、`Cdn-Loop` 等）时，看到的是 CDN 回源的指纹，可能像脚本工具，所以不判断「是不是脚本工具」；但这些请求头谁都能带，指纹照样记下、比较，变了照样要求重新验证：偷到 cookie 的人带上 `Cf-Ray` 用脚本工具来，指纹和本人的不同，仍然要重新验证。平时 UA 变了（浏览器更新）会直接采用新指纹，但带 CDN 请求头时不这样：指纹是 CDN 回源的，浏览器更新不会让它变，UA 和指纹一起变了就要求重新验证并记 `session_tls_changed`，改一下 UA 的版本号也绕不过去。不按 CDN 的网段判断这些请求头是否可信：各家 CDN 的网段不同、会变，配错了经 CDN 访问的人会被当成脚本工具退出。CDN 回源的指纹不固定时，经 CDN 访问的人偶尔会被要求重新验证。从本机直接连面板（开发时的本地代理）时不做这项检查。
- **浏览器标识**：会话记下 `User-Agent`，只比较浏览器类型和操作系统，不比较版本号；手机浏览器切换「桌面版网站」时 Android 会报成 Linux、iPhone 和 iPad 会报成 macOS，这两组各算同一种系统（`Agent.SameDevice`）。浏览器自动更新时版本号和 TLS 指纹一起变，不受影响。窃密木马可以伪造这个标识，所以它只是辅助手段。不用页面采集的浏览器指纹（canvas、字体等）：能和 cookie 一起被偷走、误报多。
- **网络**：网段按 IPv4 /24、IPv6 /48 计算，只有同一种地址的网段之间来回切换才算，浏览器在 IPv4 和 IPv6 之间切换不算。管理员的网络绑定默认是「网段变化时」，可以改为「IP 变化时」或关闭，也可以用于所有成员；登录时的网段记为已验证的；另一种地址（登录用 IPv4，之后来了 IPv6，或者反过来）第一次出现时也要验证一次，否则偷到 cookie 的人换一种地址来就绕过了绑定。重新验证后记下当前的网段，每种地址记住最近 5 个（`nets.Known`），在它们之间切换（例如家里的 Wi-Fi 和移动数据）不用再验证。5 分钟内在两个网段之间来回切换记入审计（`session_network_flip`），不要求重新验证：手机在 Wi-Fi 和移动数据之间来回切换很常见。从第一次切换起 5 分钟内达到 6 次时告警：正常的手机 5 分钟里一般只有一两次，两处同时用一个登录时两边的请求交替到达，几乎每个请求都算一次，不用等令牌轮换的重用检测（最长约 16 分钟）。之后的 5 分钟重新计数。高权限确认只对做确认时的 IP 有效（`sessions.elevated_ip`）。
- **有效期**：空闲超过 24 小时退出，从登录起最长 7 天，两个时长可以在「设置 → 安全 → 会话」中改短。最近活动时间和 IP 最多每分钟写一次，「已登录的设备」里显示浏览器和系统、最近的 IP、最近活动时间。
- **下载**：经面板的下载不靠 cookie。下载工具（IDM 等）截下浏览器的下载后，用自己的 HTTP 客户端带着浏览器的 cookie 重新请求，TLS 指纹和 User-Agent 都和浏览器不同，按 cookie 检查会被当成会话被盗、退出登录。所以界面下载前先在 `/api/volume-file`、`/api/node-file` 上带 `check=1&sign=1` 请求（照常带 cookie，做和下载一样的会话和权限检查），面板确认文件能下载后签一个 5 分钟有效的链接 `/api/download/<token>`，浏览器再去下载它（`internal/server/api/downloadlink.go`）。token 是 AES-256-GCM 加密的链接内容（种类、项目、容器、卷、快照、路径或节点、用户 ID、会话 ID、签发的 IP、链接编号、到期时间），防篡改，路径和会话 ID 也不出现在下载工具或代理的日志里；密钥每个进程随机生成，面板重启后之前的链接失效。链接只凭 token 和有效期，不看 cookie，不做设备、指纹和网络的检查，也不改会话，所以不会让人退出登录；有效期内可以多次使用（续传、多线程下载工具），已经开始的传输过期后照常传完。每次使用都重查：会话还在（没有退出、撤销、过期，不用重新验证）、属于链接里的用户，角色和访问范围仍然允许（卷文件要能操作容器、项目在访问范围内；节点文件要是管理员，高权限确认只在签发时检查），管理员还要从允许的地址来。无效、过期的链接 404，会话或权限不再允许时 403，都不说明原因。响应带 `Referrer-Policy: no-referrer`、`Cache-Control: private, no-store`。签发时记一次下载（操作名和以前一样，参数里带链接编号 `download_link`，不记 token）；从签发以外的地址使用时多记一条（`other_ip`、`issued_ip`），每个链接每个地址一次，不算错误。备用面板上节点文件的链接和以前一样不能用。以前直接带 cookie 的 `GET /api/volume-file`、`/api/node-file` 仍然能用（缓存的旧页面），新的界面总是用签名链接。
- **请求来源**：修改类请求带 `Sec-Fetch-Site` 时必须是 `same-origin`，没有时核对 `Origin` 和 `Host`（经本机 Caddy 时用 `X-Forwarded-Host`），对不上的返回 403 并记一条安全事件。都没带的（命令行工具）放行，它们不会自动带上浏览器的 cookie。项目 webhook、`/mcp`、OAuth、节点安装脚本、备用面板的地址不检查。
- **以后再做**：浏览器的设备绑定会话（Device Bound Session Credentials），等主流浏览器普遍支持后接入。页面被注入脚本（XSS）时攻击者直接在主人的浏览器里操作，上面的绑定都不起作用，只能靠 CSP 和代码本身防。

## 成员和角色

面板可以有多个账号，在「设置 → 成员」管理。角色由面板按接口方法判断（`internal/server/auth/roles.go`），界面隐藏入口只是为了好用：

| 角色 | 能做什么 |
| --- | --- |
| 管理员 | 全部，包括成员、节点和面板设置、节点的终端和文件（[node-access.md](node-access.md)）、节点的镜像（[agent.md](agent.md#节点镜像)） |
| 操作员 | 管理项目和容器（部署、终端、数据），不能保存带特权的 compose，也不能进入管理员部署的特权容器（[说明](node-access.md#操作员不能借-compose-拿到节点-root)），节点只能查看，看不到面板设置 |
| 只读 | 只能查看项目和节点；回复里去掉容器配置、共享变量、deploy key 和 webhook 令牌，不能打开终端，不能浏览和下载卷里的文件 |

- 没有写明的修改接口只有管理员能调用。终端和上传不走 Connect，单独检查角色。
- 打开着的容器终端和日志每 30 秒重查一次会话、角色和项目范围，被踢出、降权或者移出范围就断开。
- 所有角色都能改自己的密码、两步验证，查看自己已登录的设备并让其他设备退出，也能改自己的显示名称和头像（点导航底部的用户卡片）。登录和审计日志仍然用用户名。头像在浏览器里裁成 128×128 后存进面板数据库，面板只接受不超过 256 KB 的 PNG、JPEG、WebP。没有上传头像时显示一个渐变色圆形，颜色按用户名算出，改显示名称不变。
- 至少保留一个管理员，不能删除当前登录的账号。管理员重置别人的密码后，那个账号已有的登录和访问令牌（[mcp.md](mcp.md#登录)）全部失效。
- 升级前已有的账号都是管理员。

### 访问范围

操作员和只读成员可以限定只能访问哪些项目、哪些节点。管理员始终能访问全部。

**设置**：在「设置 → 成员」添加成员时，或者从成员的 ⋯ 菜单打开「访问范围」，项目和节点各选「全部 / 指定」，选指定时勾选具体的项目或节点，也可以勾选项目分组、节点标签（见[分组和标签](#分组和标签)）：分组里的项目、带其中任一标签的节点都在范围内，以后放进分组、打上标签的也算，勾了分组的项目显示为「已包含」。默认都是全部，升级前已有的成员不受影响。成员列表显示每个人的范围（全部，或者分组、标签和几个项目、几个节点）。

**规则**：

- **项目范围**决定能看到和管理哪些项目。项目里的所有容器都可以按角色操作，不论容器在哪个节点上；容器在范围外的节点上时，也能把它迁移到范围内的节点。
- **节点范围**决定能看到哪些节点（节点页、监控、mesh），以及添加、迁移容器，设置顶替、备份节点和映射的入口节点时能选哪些节点。操作员和只读成员都一样。操作员对节点本来就只能查看，节点范围不额外放开任何修改。
- **两者交叉**：
  - 项目里的容器在范围外的节点上时，项目页照常显示这个容器和它的状态、占用，节点只显示名称，不能点进节点页。
  - 范围内的节点上有范围外项目的容器时，节点页不显示这些容器，容器数也只算范围内的；节点整体的占用照常显示。
- **新建项目**：指定了项目范围的成员新建的项目，自动加进他的范围。容器只能放在他范围内的节点上。
- **项目连接**：两个项目都在范围内才能连接或断开。已连接的项目不在范围内时，只显示「另一个项目」和它的网络名（配置里要用网络名访问对方的容器），不能断开。
- **全局概览**：只显示范围内的数据：范围内的节点、项目、端口映射，节点之间的流量只画范围内节点之间的。到范围外节点的流量不显示是哪个节点，只用来从网卡流量里减掉，所以「对外流量」仍然是真正对外的部分。
- **搜索、需要处理的提示**：只出现范围内的项目和节点。
- 删除项目、移除节点时，从所有成员的范围里去掉。重命名分组、标签时，成员范围里的名称一起改；删除分组、标签时，从成员的范围里去掉，借它访问的项目、节点随之不在范围内（单独勾选的不受影响）。

**实现**（`internal/server/api/scope.go`）：

- 数据库：`users` 的 `all_projects`、`all_nodes`（默认 1），表 `user_projects`、`user_nodes`，分组和标签在 `user_project_groups`、`user_node_tags`；删除成员、项目时级联删除，移除节点时另外删除（节点只是标记为已移除）。备用面板复制数据库时一起带过去。每次请求按当时的分组和标签算出范围内的项目和节点，所以分组、标签的变化立即生效。
- 检查是 Connect 的一个拦截器，放在角色检查之后，处理函数不用管：
  - 请求最外层的 `project_id`、`other_project_id` 核对项目范围，`node_id`、`node_ids`、`standby_node_id`、`witness_node_id` 核对节点范围。范围外的项目一律返回"项目不存在"，不暴露项目是否存在；节点返回"节点不存在"。
  - 另外处理的：`SaveRoute`、`CheckDomains` 核对映射里的入口节点（`route.entry_nodes` 不在最外层），这个映射原来就有的入口节点可以留着，管理员设的入口节点不妨碍操作员改别的设置；`RestoreFromBackup` 核对容器的备份节点，`PingNodeMesh` 核对对方公钥所属的节点。`QueryNodeMetrics` 的前缀限定在一个范围内的项目（如 `c:<项目 ID>/`）时，范围外的节点也放行，项目页才能显示容器的占用。
  - 回复里去掉范围外的内容：项目列表、节点列表（范围内项目用到的范围外节点放在 `other_nodes`，只有名称和是否在线；不认识的容器不给）、mesh 成员、副本、监控序列（容器、端口映射等以项目 ID 开头的序列只留范围内的项目，形式不认识的序列也去掉），已连接项目的名称。
  - 新建项目成功后加进成员的范围。
- 终端 `/ws/exec`、上传 `/api/upload`、卷文件 `/api/volume-file` 不走 Connect，单独核对项目范围。
- `scope_test.go` 列出 `ProjectService`、`NodeService` 里操作员、只读成员能调用的方法，每个都必须在请求里带项目或节点，或者登记为靠过滤回复，新增接口忘了处理时测试失败。
- 节点文件、节点终端仍然只有管理员能用，不受范围影响。

### 分组和标签

项目可以放进一个**分组**，节点可以打多个**标签**，用来整理列表和划分成员的[访问范围](#访问范围)。它们只在面板上，不下发给节点，不影响容器的运行。

- **分组**：在项目「设置 → 基本设置」选择或新建，新建项目时也可以直接选（已有分组时）。每个项目最多一个分组，名称不超过 32 个字符。项目页按分组分段显示，可以收起（记在浏览器里，展开和收起有高度过渡），未分组的放最后；没有任何分组时和以前一样。排序可选最近创建、按名称、自定义。点筛选行的「调整顺序」进入拖动（排序随之换成自定义，分组标题前出现拖动标记，卡片边框变成虚线，点击卡片不打开项目），点「完成」退出：按住分组标题上下拖动调整分组的顺序，按住卡片拖动调整项目的顺序（键盘用空格拿起和放下、方向键移动）。排序方式和顺序存在面板上（表 `user_project_order`，`AuthService.GetProjectOrder`、`SetProjectOrder`，不记审计），每个成员各自一份，换浏览器、换设备都一样；以前记在浏览器里的顺序（`nagi.projects.order`）在面板上还没有时搬过去，然后删掉。没排过的项目（例如新建的）排在最前面，没排过的分组排在排过的后面，未分组固定在最后。代码在 `web/src/pages/project-order.tsx`。筛选行可以只看一个分组或未分组的项目，搜索也匹配分组名。
- **标签**：在节点页的 ⋯ 菜单「编辑标签」，每个节点最多 10 个，每个不超过 32 个字符。节点列表在地址后面显示标签，上方可以按标签筛选，选多个时显示带其中任一标签的节点。
- 分组和标签没有单独的列表：有项目、节点（或成员的访问范围）用着就存在。项目页、节点页的 ⋯ 菜单「管理分组」「管理标签」可以重命名（名称已存在时合并）和删除：删除分组时项目变为未分组，删除标签时从节点上去掉。用到它的成员会列出来。
- **权限**：只有管理员能修改分组和标签，因为它们决定成员能访问什么。操作员能修改的项目设置不包括分组（`SetProjectGroup`、`RenameProjectGroup` 只给管理员，见 `internal/server/auth/roles.go` 的 `adminWrites`）。
- **实现**：表 `project_groups`（项目 → 分组）、`node_tags`（节点 → 标签），查询在 `internal/server/store/groups.go`，接口在 `internal/server/api/labels.go`。删除项目时级联删除，移除节点时另外删除。不放进下发给节点的配置：节点可能被攻破，从节点缓存拼回项目时不能让它决定项目在哪个分组、谁能访问。

## 审计日志

面板的操作、敏感查询、登录、终端和告警都记进审计日志，见 [audit.md](audit.md)。节点发出告警时通过 `PanelService.ReportAlert` 告诉面板，面板自己发的告警（节点失联）也记录；上报有频率限制，长度有上限。

## 更新面板

在设置页"关于"里一键更新本面板（只有管理员能检查和更新，其他角色只看到版本和状态），内嵌的节点在同一个进程里，一起更新。其他节点之后在节点页单独升级（[control-plane.md](control-plane.md)）。

- **检查**：跟随 `github.com/SIPC/Nagi/releases/latest` 的重定向得到最新版本号（不含预发布版），不用 GitHub API，不占它的限额。结果缓存 1 小时，界面显示查询的时间（"刚刚检查"）；有新版本时侧栏和二级菜单的"关于"上显示小圆点；点"检查更新"不用缓存。
- **更新日志**：有新版本时，"关于"的版本下面列出最新版本日志的前三条；点"更多信息"就地展开本面板到最新版本之间各版本的全部日志（`SettingsService.GetPanelReleaseNotes`）。点"更新"只弹确认框。日志随发布文件上传（`CHANGELOG.md`，英文界面取 `CHANGELOG.en.md`），和新版本走同一个下载地址，安装时用了镜像就从镜像取；按版本缓存在内存里。取不到时不显示日志，照常可以更新。
- **更新**：版本由面板自己决定（最新发布的版本，只升不降），不从请求里取。下载和节点升级走同一段代码（`internal/pkg/release`）：从 GitHub Release 或镜像下载（地址见下面的「下载地址和加速代理」），按 `SHA256SUMS` 核对，试运行一次 `version` 确认能在本机运行且版本对得上，替换可执行文件，然后原地重启（`exec`，进程号不变）。任何一步失败都不影响正在运行的面板。
- **镜像**：安装时用了 `--download-url` 的，地址记在 `<面板数据目录>/download-url`，只从这里下载，不换别的地址（和以前一样）。版本号仍要问 GitHub（连不上时经加速代理查，见下）：都查不到时检查不到新版本，要重新执行安装脚本升级。
- **下载地址和加速代理**（`release.Sources`）：没有镜像时依次尝试——记着的加速代理（`<面板数据目录>/github-proxy`，节点在 `<节点目录>/identity/github-proxy`）、直接连 GitHub、内置的加速代理（`release.GitHubProxies`，和安装脚本的 `GH_PROXIES` 是同一份列表，`TestInstallConstants` 检查）。一个地址失败（连不上、HTTP 出错、校验不一致）或太慢就换下一个：连接（含 TLS 握手）超过 10 秒、响应头超过 30 秒、连续 30 秒平均每秒不到 1 KB（和安装脚本的 `curl --connect-timeout 10 --speed-limit 1024 --speed-time 30` 一样），或者按开始以来的平均速度在 10 分钟的总时限内下载不完（例如中国大陆直连 GitHub，一直有数据但很慢）。试运行发现新版本在本机运行不了时不再换地址（文件已经按校验和核对过，换地址下载到的也是它）。全部失败时报第一个地址的错误和尝试的个数，每个地址的错误记在日志里。成功后记下用上的地址：经代理下载的写进 `github-proxy`，直接从 GitHub 下载的删掉它，下次先试。安装脚本在中国大陆网络经代理下载时也写这个文件，重新执行安装脚本时按当时的检测结果更新或删除。查最新版本时也一样：直接连不上 GitHub 时先经记着的代理、再依次经内置的代理查（代理会转回 GitHub 的重定向）；这样查到的版本号由代理决定，界面在版本号旁写明「查询自 <代理>」（`CheckPanelUpdateResponse.latest_source`，MCP 的 `check_panel_update` 返回 `latest_checked_via`）。更新进入重启阶段后，界面上写下载自哪个地址（`UpdateState.source`，节点的来自 `UpgradeResponse.source`）。
- **校验和信任**：完整性靠 `SHA256SUMS`。没有镜像时，开始下载之前先直接从 GitHub 取这个版本的 `SHA256SUMS`（最多 15 秒、64 KB，`release.githubSums`），不论地址的顺序：
  - **取到了**：之后每个地址（包括排在最前、记着的加速代理）给的 `SHA256SUMS` 里本机文件的值都必须和它一致，对不上就跳过这个地址、不下载它的文件。能连上 GitHub 的机器永远不会只信代理。
  - **GitHub 上没有这个版本**（HTTP 404），或 GitHub 上的 `SHA256SUMS` 里没有本机的架构：直接失败（「GitHub 上没有版本 vX.Y.Z，已停止下载」），不再试代理。代理可以谎报一个 GitHub 上没有的新版本，再提供自己的文件和校验值，这样的版本不能装。
  - **连不上 GitHub**（超时、连接失败、其他 HTTP 状态）：各地址按自己给的 `SHA256SUMS` 核对，信任用上的代理。这和安装脚本一样，是已接受的风险：中国大陆网络的安装本来就信任这几个代理。之后直接从 GitHub 拿到了 `SHA256SUMS`（例如校验文件拿到了、二进制太慢放弃了）时，后面的代理也要和它一致。
  - **经代理查到的版本号**：只在界面上写明「查询自 <代理>」，不直接当作可信的版本。点更新时按上面的规则核对：能连上 GitHub 时 GitHub 上没有这个版本就不装。节点升级的目标是面板自己正在运行的版本（`UpgradeRequest.version`），不是查到的最新版本，所以代理给的版本号不会直接下发给节点；节点下载时也走同一段代码，同样先向 GitHub 核对。
  - 镜像（`download-url`）是安装时指定的，只信任镜像，不向 GitHub 核对。试运行 `version` 只确认版本号，不是安全检查。
- **重启**：登录会话在数据库里，不用重新登录。更新在后台进行，界面每 2 秒查一次进度，面板用新版本回来后刷新页面；3 分钟没恢复时显示失败，要到服务器上看日志。进行中的部署等操作会中断（和手动重启一样）；项目容器由 Docker 运行，不受影响。
- **不能退回**：新版本启动时会迁移数据库，没有自动回滚。要回到旧版本，得用安装脚本的 `--version` 并恢复备份的数据库。
- 本地编译的版本（`dev`）和非 Linux 上的面板不能一键更新，页面上说明原因。

### 更新状态

面板和节点的更新进度记在面板的 `settings` 表（`update_state`，每个面板自己的，不同步），由 `SettingsService.GetUpdateStatus` 读取，只有管理员能查。刷新页面、换浏览器、面板重启后都还在，进行中不能再点一次。

- **阶段**：排队（一键升级时轮到它之前）、下载和替换、等它用新版本回来、失败。成功后记录删除；失败的记录留到下一次尝试或者节点已经是目标版本。
- **超时和打断**：下载和校验 10 分钟没完成算失败（面板取消请求，节点停止下载）；替换后 3 分钟没用新版本回来算失败。面板重启后，上一个进程的后台任务已经没了：下载中的算失败，排队的回到可以升级，已经在重启的节点接着等。
- **一键升级全部节点**：节点页的按钮把所有落后于面板、能升级的节点逐个升级，每个节点用新版本回来后才开始下一个，同时重启可能让顶替的租约续不上。顺序是只做热备或备份的节点、既有容器又做热备或备份的节点、只有容器的节点、其余节点（见 [control-plane.md](control-plane.md)）。下载阶段失败（包括超时）时节点还是原来的版本，记下原因后跳过，接着升级下一个；替换后没有用新版本回来时停下，后面的回到可以升级，以免新版本有问题时影响更多节点。
- **取消**：管理员可以在节点页取消全部升级，或在节点详情取消这个节点的升级（`NodeService.CancelNodeUpgrade`）：排队的不再升级；下载中的由面板通知节点停止（agent 的 `CancelUpgrade`：面板发给节点的请求不跟着面板取消，见 `internal/agent/detach.go`），节点确认后才算取消，节点还是原来的版本。已经替换、正在重启的不能取消。v0.20.0 以前的节点没有 `CancelUpgrade`，正在下载时不能取消（界面上不显示取消按钮），只能等它完成或超时。节点同一时间只做一次升级，取消的那次收尾之前再点升级，节点会拒绝。
- **右下角提示**：管理员在任何页面都能看到新版本、更新进度和失败原因，可以点进去查看。关掉的提示记在浏览器里，同一件事不再弹。面板有新版本时先提示更新面板，更新好以后才提示升级节点。

## webhook

每个容器的 webhook 地址带有独立的随机密钥，不经过登录和安全入口。需要面板能被公网访问，建议绑定域名。
