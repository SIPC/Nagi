## 设计原则

1. **概念最少**：用户只需理解节点、项目、容器（一份 compose 是一个容器组）。
2. **compose 是唯一的底层定义**：项目是一组一起工作的容器（前端、后端、数据库……），每个容器、每个容器组就是一份 compose 文件加少量元数据（环境变量、密钥），各自独立部署和回滚，随时可导出脱离平台。用镜像表单创建的单个容器（直接运行在线镜像，或者附带文件运行）也自动生成 compose，底层只有一套部署逻辑。项目里的容器不论在哪台机器上，都在同一个内网里，用名字互相访问。
3. **默认可上生产**：开箱即用的默认值必须是安全、可靠的；高级选项默认折叠。
4. **零外部依赖**：运行在 Linux 上，除 Docker 和 compose 插件（2.24 或更新版本）外，不依赖域名、外部 CA、云服务或数据库。
5. **配置在面板，数据在节点**：项目和容器的配置、版本记录、部署记录以面板为准；容器的运行文件、数据和快照在容器所在的节点上。节点缓存一份自己那部分容器的配置，面板挂掉时容器照常运行、重启、快照和顶替，只是暂时不能修改和部署；面板彻底丢失时，新面板从各节点的缓存把项目拼回来。一个节点同一时间只归一个面板管理；面板可以有备用面板，实时同步、平时只读，主面板坏了手动提升（见 [standby.md](standby.md)）。
6. **没说要动的就不动**：故障时只按用户事先的设置行事，没有设置就原地等待，不做猜测。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| 节点（Node） | 一台运行 `nagi agent` 的机器 |
| 项目（Project） | 一组一起工作的容器，存在面板上，不属于哪台机器。项目里的容器可以分布在不同节点上，不论在哪都能用名字互相访问；项目之间默认隔离，可以单独连接两个项目 |
| 容器（Container） | 项目里独立部署的单位：单个容器（由镜像表单生成），或者容器组（一份 compose，里面的每个 service 是组里的一个容器）。每个容器指定一个节点运行（容器组整组在同一个节点），各自部署、记版本、回滚、快照、迁移、顶替 |

## 组件

只有一个二进制 `nagi`，用子命令区分角色：

| 子命令 | 作用 |
| --- | --- |
| `nagi server` | 启动面板。默认同时启动一个内嵌 agent，单机即可使用；加 `--no-agent` 只运行面板，适合把面板单独放在一台不跑项目的机器上 |
| `nagi agent` | 启动节点，主动连接面板 |

```
            浏览器
              │ HTTPS :<面板端口>
   ┌──────────▼──────────┐
   │     nagi server      │  Web UI + 接口 + SQLite
   │ （项目配置的主人）   │  也加入 mesh
   └──▲──────────────▲───┘
      │ mTLS         │ mTLS           控制面：agent 主动连入面板端口
 ┌────┴─────┐   ┌────┴─────┐
 │nagi agent│◄─►│nagi agent│          数据面：WireGuard 全连接 mesh
 │ compose  │   │ compose  │
 │ Caddy    │   │ Caddy    │          所有对外流量从 Caddy 进入
 └──────────┘   └──────────┘
```

**依赖关系**：`internal/server` 和 `internal/agent` 互不引用，只共享 `internal/proto` 和不含业务逻辑的 `internal/pkg`。单机模式下内嵌 agent 也通过同一套协议与面板通信，不走捷径，保证单机与多机行为一致。

## MVP 范围

**包含**

- 节点一键加入
- 项目全流程：项目由多个容器组成，每个容器选一个节点运行，各自部署，也可以一起部署；修改先存草稿；更新、日志、终端；删除时容器目录默认保留
- 项目内网（项目里的容器跨节点自动互通）和项目连接（两个项目之间单独连通）
- 两种加容器的方式：填镜像表单（直接运行在线镜像，也可以附带文件），自动生成 compose；或者粘贴 compose，整份作为一个容器组
- 项目文件来源：面板上传压缩包、git 仓库拉取（deploy key，可选 webhook）、用户自己放
- 镜像：每天检查更新并在面板上提醒，手动更新；按节点配置镜像加速
- 版本历史与回滚：按容器记版本，配置、文件、镜像摘要一起回滚，可选同时恢复数据；部署记录可以把整个项目回到某次部署时的状态
- 对外访问统一走内嵌 Caddy：域名与自动 HTTPS、TCP/UDP 转发、界面上按服务开关
- 环境变量（项目共享变量、容器组变量、容器的环境变量三层）与密钥、私有镜像仓库认证、健康检查、资源限制
- 面板安全：一次性令牌初始化、可选 TOTP、登录限速、可选安全入口
- 监控与告警：节点、容器、健康检查、Caddy 指标存在节点本地；webhook 和 Telegram 告警
- 快照：按容器定时备份、恢复；可指定备份节点作为异地副本
- 手动迁移：把一个容器搬到另一个节点，复用顶替机制，不丢数据
- WireGuard 组网
- 配置存在面板，节点缓存自己那部分；面板丢失后从节点缓存重建；节点坏了且没有副本时，把容器重新部署到其他节点
- 信任的面板列表：移交节点给另一个面板
- 按容器指定顶替节点：无状态容器自动顶替，有状态容器告警后手动确认；原节点恢复后自动切回

**约束**：一个容器组的所有容器在同一个节点上；跨节点的容器之间只转发 TCP。

**不包含**：自动调度、一个容器同时运行多份（副本）、多面板同时管理、多用户、恢复演练、接管已有项目、顶替后的流量切换、在节点上构建、应用模板、镜像自动升级。

## 开发顺序

以下 8 步按旧模型（一个项目整体在一个节点上）已经完成。2026-10 改为现在的模型（项目在面板、容器分节点），按 [development.md](development.md#改为项目在面板容器分节点) 分步改造。

1. agent 自治 + 单个面板：节点加入、控制面、面板登录（信任列表和项目修订号从这一步起就按多面板设计，只是列表里暂时只有一个面板）
2. 项目全流程：草稿与部署、镜像表单、文件来源（git、用户自己放）、Caddy 出口（域名、HTTPS、TCP/UDP）、日志、终端
3. UI 打磨（从第一个版本开始持续进行）
4. 快照、版本、回滚
5. 监控与告警
6. 换面板与多面板：加入、移除面板，节点本地命令
7. WireGuard 组网，以及依赖它的面板上传文件、备份节点
8. 顶替节点与手动迁移：租约、见证人、热备

以后：自动调度。
